# v0.3.0 MCP and Beginner Workflow

## Outcome

A non-developer asks an MCP-connected agent to finish a project using ordinary language. The agent may analyze the repository and propose a small release, but cannot approve scope for the user, inject a shell command, bypass a pause, or declare completion without Shipping Harness evidence.

## User flow

```text
User goal
  → shipping_start
  → repository analysis
  → minimal scope + acceptance + short plan
  → explicit user approval
  → shipping_approve_scope
  → contract written and locked
  → shipping_execute / shipping_verify
  → blocker-only shipping_fix_blockers
  → shipping_close
```

The MCP client presents the proposal. Shipping Harness stores a proposal receipt, but approval remains a separate tool call with `confirm: true` and the exact proposal hash.

## MCP protocol surface

The STDIO process supports:

- `server/discover` for MCP 2026-07-28.
- `initialize` and `notifications/initialized` compatibility for MCP 2025-11-25 clients.
- `ping`.
- `tools/list`.
- `tools/call`.
- `notifications/cancelled` for best-effort cancellation bookkeeping.

Every stdout line is one JSON-RPC message. Diagnostics are written only to stderr.

## Tool surface

| Tool | Mutation | Approval rule |
|---|---:|---|
| `shipping_start` | proposal file only | No release mutation |
| `shipping_approve_scope` | contract/state/lock | Exact hash plus `confirm: true` |
| `shipping_execute` | agent evidence and source through configured adapter | Locked contract command only |
| `shipping_status` | none | Read-only |
| `shipping_verify` | evidence/state/issues | Existing acceptance contract |
| `shipping_fix_blockers` | state counter only | Existing blockers and budget |
| `shipping_pause` | state | Human authority action |
| `shipping_close` | release receipt/backlog/state | SHIPPABLE only |

## Repository analysis

The analyzer reads a bounded set of repository-owned files:

- `package.json`
- `pyproject.toml`
- `Cargo.toml`
- `go.mod`
- `Makefile`
- common README names
- top-level directory names

It never executes package scripts during analysis. Candidate acceptance commands are selected from known manifest fields and existing package scripts. The proposal includes confidence and diagnostics rather than pretending unsupported commands exist.

## Minimal-scope policy

The goal text is preserved as user intent. Deterministic defaults add only operational requirements needed to close a release:

1. Build or syntax validation when detected.
2. Existing test command when detected.
3. Existing lint/typecheck only when already configured.
4. Installation or run documentation when the repository already exposes an executable product.

Web UI, cloud services, mobile apps, multi-user support, architectural rewrites, and speculative refactors are excluded unless the goal explicitly requires them.

## Security invariants

1. MCP tools never accept a raw `command`, `shell`, `args`, or environment map.
2. Execution uses only an adapter command already present in the approved locked contract.
3. Proposal approval is rejected when Git SHA, root, release, or hash differs.
4. Paths must resolve under the selected Git repository.
5. Input messages and tool arguments have hard byte and depth limits.
6. Human pause and abort outrank agent requests.
7. Tool errors are visible to the model but cannot mutate release state after validation fails.

## Deferred absorption

v0.3.0 does not reproduce the complete Gajae, OMO, or Ouroboros runtimes. It absorbs only the minimum beginner-facing workflow needed before those larger capabilities can be justified:

- Gajae influence: a small goal-to-plan proposal, not a deep interview engine.
- OMO influence: a lifecycle-controlled tool surface, not a multi-agent team.
- Ouroboros influence: an immutable approved release contract, not evolutionary generations.

The deferred features have separate backlog IDs and cannot enter the v0.3.0 release without a new contract.
