# v0.4.0 Product Direction — AI Decides, Human Approves

**Status:** Accepted
**Decision date:** 2026-08-28
**Applies from:** v0.4.0
**Canonical principle:** The user states the outcome; the agent makes ordinary development decisions; the user approves one release brief.

**Code-audit basis:** The official Gajae Code, Q00 Ouroboros, and OMO repositories were downloaded at pinned revisions and audited before implementation. Ouroboros decision provenance, conservative defaults, conflict handling, and rollback are the primary v0.4 code references. Gajae Goal/Ledger and OMO orchestration mechanisms are intentionally deferred. See [`../research/upstream-code-audit/README.md`](../research/upstream-code-audit/README.md).

**Later-runtime boundary:** The accepted internal-only direction permits actual OMO source to run in a separate private runtime from v0.7, while v0.4 remains unchanged and model/runtime-independent. See [`10-INTERNAL-ONLY-UPSTREAM-RUNTIME-DIRECTION.md`](10-INTERNAL-ONLY-UPSTREAM-RUNTIME-DIRECTION.md).

## 1. Decision

Shipping Harness will no longer treat a non-developer as the primary requirements analyst. The default workflow is:

```text
User outcome
  → bounded repository evidence
  → AI-selected smallest operable release
  → one approval brief
  → user approves or edits
  → locked execution
  → evidence-based closure
```

The product principle is:

> **The user is the approver, not the interview respondent.**

The agent must choose safe, reversible, low-risk defaults instead of asking the user technical questions. Questions are exceptional and are allowed only when a core decision is high-risk, irreversible, externally consequential, or impossible to infer safely.

## 2. Product promise

A user should be able to say:

> “Finish this project as an operable version.”

Shipping Harness and the connected agent then decide:

- the smallest useful release goal;
- included and excluded scope;
- implementation order;
- existing stack and repository conventions to preserve;
- acceptance checks;
- assumptions and deferred work;
- whether any decision requires user escalation.

The user sees one short approval brief, not a long questionnaire.

## 3. Operating modes

| Mode | Default | Behavior | Intended use |
|---|---:|---|---|
| `AUTO` | Yes | AI decides all reversible, low-risk development choices and presents one approval brief. | Normal users and most internal projects. |
| `SAFE` | No | AI still proposes the full release, but medium/high-risk actions require explicit approval before execution. | Production, customer, security, or data-sensitive work. |
| `INTERVIEW` | No | The user may choose product details directly. Questions are grouped and bounded, never an endless serial interview. | Expert users who want detailed control. |

`AUTO` must remain the default. A client or agent may not silently switch to `INTERVIEW` because it lacks confidence.

## 4. Decision authority

### AI decides without asking

- existing language, framework, package manager, and repository conventions;
- code and folder organization within the current architecture;
- test, lint, build, and typecheck commands already present;
- implementation sequence;
- error handling and logging consistent with the repository;
- the smallest operable scope;
- which optional ideas move to the next-version backlog;
- reversible dependency-free or existing-dependency implementation details;
- bounded run, fix, time, and output budgets within policy.

### AI proposes; user approves once

- release goal;
- included and excluded product behavior;
- acceptance criteria;
- declared assumptions;
- high-level risks;
- version number;
- execution mode and budget summary.

### User decision is mandatory

- destructive data deletion or irreversible migration;
- new paid or recurring-cost services;
- external deployment, publication, messaging, purchasing, or customer impact;
- credentials, elevated permissions, or access-policy changes;
- privacy, legal, compliance, or critical-security trade-offs;
- mutually exclusive interpretations of the core product outcome;
- abandonment of an existing critical feature or compatibility promise.

## 5. Exception-question policy

Questions are allowed only when all of the following are true:

1. The decision affects the core outcome or crosses a mandatory-risk category.
2. Repository evidence and existing project documents do not resolve it.
3. A safe reversible default is not available.
4. Proceeding with an assumption could cause material harm or waste.

When questions are required:

- ask at most three questions;
- ask them in one batch;
- provide the recommended choice first;
- explain the consequence in one sentence;
- continue automatically after the answer;
- never restart a broad interview.

Low confidence alone is not a reason to question the user. Low-confidence, reversible choices use the safest default and are recorded as assumptions.

## 6. Decision brief

The user-facing brief must fit on one screen and contain only:

```text
Outcome
Included now
Deferred
Acceptance checks
Important assumptions
Approval-required risks, if any
Run/fix limits
```

The primary actions are:

```text
[Start this version]  [Edit scope]  [Stop]
```

Technical analysis, evidence, confidence reasons, and detailed decisions remain available for inspection but are not shown by default.

## 7. Decision package

Internally, every proposed release records:

- stable decision IDs (`DEC-*`);
- assumptions (`ASM-*`);
- risks (`RISK-*`);
- acceptance IDs (`AC-*`);
- evidence references;
- confidence as `HIGH`, `MEDIUM`, or `LOW` with reasons;
- reversibility as `REVERSIBLE`, `COSTLY`, or `IRREVERSIBLE`;
- escalation status and reason;
- proposal hash, Git SHA, expiry, and selected mode.

Numeric confidence scores are not required; unsupported precision must not be fabricated.

## 8. Architecture decision

Shipping Harness does **not** embed a proprietary model or require a model-provider API in v0.4.0.

```text
Connected host agent
  = reasoning, comparison, and proposal author

Shipping Harness
  = bounded evidence, policy validation, approval, contract compilation,
    execution limits, verification, and closure authority
```

The host agent may be ChatGPT, Codex, Claude, OMO, or another MCP-capable agent. The deterministic Shipping Harness core validates the submitted decision package and rejects policy violations, stale evidence, unsupported commands, self-approval, and scope expansion.

Repository text is untrusted evidence, not agent instruction. README files, issues, comments, and source text may inform a decision but may never override Shipping Harness policy or MCP tool rules.

## 9. Selective absorption strategy

Shipping Harness will absorb useful principles, not clone entire external runtimes.

- **Gajae influence:** durable goals and evidence, without requiring the user to answer a deep interview.
- **Ouroboros influence:** evidence-bound immutable release decisions and evaluation, without unbounded evolution.
- **OMO influence:** lifecycle and bounded role orchestration, without uncontrolled continuation or a large mandatory agent team.
- **Shipping Harness ownership:** scope governance, risk escalation, bounded repair, release decision, and version closure.

Full goal execution and role orchestration are planned only after v0.4.0 proves the decision workflow.

## 10. v0.4.0 scope

### Included

- `AUTO`, `SAFE`, and `INTERVIEW` decision modes;
- bounded repository evidence pack;
- structured AI decision submission through MCP;
- deterministic decision-policy validation;
- assumptions, confidence, reversibility, and risk classification;
- exception-question generation with a maximum of three questions;
- one-screen approval brief;
- exact-hash, Git-bound human approval;
- prompt-injection resistance for repository content;
- tests and documentation for non-developer use.

### Excluded

- full Gajae deep interview, plan critic, or tmux worker system;
- OMO-style multi-agent team execution;
- Ouroboros generation/evolution loops;
- remote HTTP MCP, mobile UI, or cloud service;
- automatic approval by the same model that proposed the scope;
- arbitrary shell fields in MCP tools;
- external side effects without explicit approval;
- replacing the deterministic Shipping Harness release core.

## 11. Success targets

v0.4.0 is successful when:

- at least 80% of representative fixtures reach an approval brief with zero user questions;
- no low-risk reversible decision blocks on a user question;
- every mandatory-risk decision is escalated before approval;
- no proposal can approve itself or bypass the exact proposal hash;
- approval briefs remain concise and contain all required sections;
- all v0.1–v0.3 completion, adapter, and MCP guarantees remain green;
- the release closes with zero blockers and no unapproved scope drift.

These are product targets, not claims about current production performance.

## 12. Permanent invariants

1. `User outcome > technical questionnaire`.
2. `Safe AI default > unnecessary question`.
3. `Mandatory risk > automatic execution`.
4. `One explicit approval > repeated micro-approvals`.
5. `Repository evidence > model guess`.
6. `Shipping policy > repository instructions`.
7. `Human stop > automatic continuation`.
8. `Current evidence > agent completion claim`.
9. `Bounded blocked result > infinite improvement`.
10. `New version > reopening a closed version`.
