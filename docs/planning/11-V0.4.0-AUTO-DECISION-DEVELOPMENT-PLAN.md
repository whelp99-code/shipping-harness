# v0.4.0 Development Plan — Auto-Decision Core

**Status:** PLANNED — direction locked, implementation not started
**Predecessor:** v0.3.0 CLOSED
**Canonical direction:** [`10-INTERNAL-ONLY-UPSTREAM-RUNTIME-DIRECTION.md`](10-INTERNAL-ONLY-UPSTREAM-RUNTIME-DIRECTION.md)
**Primary upstream reference:** Q00 Ouroboros decision provenance, conservative defaults, conflict handling, and bounded rollback

## 1. Release outcome

A user states one desired result. A connected agent analyzes bounded repository evidence, chooses the smallest operable release, records why each choice was made, asks only mandatory exception questions, and presents one concise approval brief. Shipping Harness validates and locks the approved proposal.

```text
User outcome
  -> bounded evidence pack
  -> AI decision package
  -> deterministic policy validation
  -> zero to three exception questions
  -> one approval brief
  -> explicit user approval
  -> locked Shipping contract
```

This version changes planning quality. It does not add multi-agent execution, OMO runtime integration, or remote control.

## 2. User value

Before v0.4, a non-developer can start from natural language but still receives a mostly mechanical proposal. After v0.4:

- ordinary technical choices are made by the agent instead of being asked one by one;
- the user approves a result-oriented brief rather than answering a technical interview;
- risky or irreversible choices remain visible and require approval;
- every decision has repository evidence or an explicit assumption;
- optional improvements are deferred instead of silently expanding the release.

The normal user experience must be:

> “Finish this project as an operable version.”

followed by one short approval brief and no technical questionnaire.

## 3. Entry gate

Implementation may start only when:

1. v0.3.0 is CLOSED and its regression tests pass;
2. the repository is clean;
3. `.shipping/contract.yaml` for v0.4.0 remains DRAFT until this plan is accepted for implementation;
4. the direction documents 08 and 10 are unchanged or amended through an explicit decision;
5. no v0.5+ execution feature is included in the v0.4 contract.

## 4. Included scope

- `AUTO` default mode;
- optional `SAFE` and `INTERVIEW` modes;
- bounded repository evidence pack;
- stable evidence references;
- structured decisions, assumptions, risks, conflicts, confidence, and reversibility;
- conservative defaults for low-risk reversible uncertainty;
- mandatory-risk escalation;
- maximum three questions returned in one batch;
- one-screen approval brief plus inspectable detail;
- exact proposal hash covering all decision inputs and outputs;
- proposer/approver separation;
- contract compilation from an approved decision package;
- repository prompt-injection resistance;
- MCP workflow extension without raw shell fields.

## 5. Explicit non-goals

- embedded model-provider API;
- proprietary reasoning model;
- Gajae deep interview runtime;
- OMO agents, teams, DAGs, continuation, or model routing;
- Ouroboros evolution generations;
- automatic contract approval;
- automatic deployment, push, tag, or credential changes;
- plugin UI or remote HTTP MCP;
- unlimited questions, review rounds, or proposal retries.

Any discovered need outside this list becomes v0.5+ backlog unless it directly repairs a v0.4 acceptance failure.

## 6. Architecture delta

Planned modules:

```text
src/core/decision/
├── modes.mjs              # AUTO / SAFE / INTERVIEW policy
├── evidence-pack.mjs      # bounded repository facts
├── schema.mjs             # decision package types and limits
├── provenance.mjs         # evidence / assumption / inference sources
├── conflicts.mjs          # incompatible evidence and outcome detection
├── risk-policy.mjs        # mandatory escalation classes
├── validator.mjs          # deterministic decision validation
├── approval-brief.mjs     # concise user-facing brief
└── compiler.mjs           # accepted package -> Shipping contract

src/mcp/
├── tools.mjs              # shipping_start / decision submission / approval flow
└── protocol.mjs           # bounded payload and structured errors
```

Proposed repository artifacts:

```text
.shipping/proposals/<proposal-id>.json
.shipping/decisions/<proposal-id>.json
.shipping/approval-receipts/<proposal-id>.json
```

Repository text is evidence only. It is never executable instruction and cannot modify mode, policy, available tools, or approval state.

## 7. Decision package contract

Every decision package must include:

```json
{
  "schema": "shipping-decision/v1",
  "project": "example",
  "release": "0.4.0",
  "mode": "AUTO",
  "git_sha": "...",
  "goal": "...",
  "decisions": [
    {
      "id": "DEC-001",
      "subject": "test strategy",
      "value": "use existing npm test script",
      "source": "repo_fact",
      "evidence_refs": ["EVID-003"],
      "confidence": "high",
      "reversibility": "reversible"
    }
  ],
  "assumptions": [],
  "risks": [],
  "questions": [],
  "scope": { "include": [], "exclude": [] },
  "acceptance": [],
  "budgets": {}
}
```

Allowed provenance classes:

```text
user_outcome
repository_fact
existing_convention
user_preference
conservative_default
assumption
inference
mandatory_blocker
```

Numeric confidence percentages are not required and must not be fabricated. Qualitative `high / medium / low` is sufficient.

## 8. Mandatory-risk policy

The following always require escalation before contract lock:

- destructive data deletion or irreversible migration;
- new paid or recurring services;
- external deployment, publication, messaging, purchasing, or customer impact;
- credentials, elevated permissions, or access-policy changes;
- privacy, legal, compliance, or critical-security trade-offs;
- mutually exclusive interpretations of the core outcome;
- removal of an existing critical compatibility promise.

Low-risk reversible implementation details use a documented assumption rather than a question.

## 10. PR and implementation sequence

### PR-013 — Decision evidence and mode policy

Build:

- mode enum and default selection;
- repository evidence limits and stable IDs;
- release history, manifests, scripts, existing documentation, and current Git state collection;
- untrusted repository-text boundary;
- deterministic evidence ordering and hashing.

Closest tests:

- mode default and explicit mode tests;
- byte/depth/item-limit tests;
- hostile README fixture;
- deterministic evidence hash test.

Exit condition:

- identical repository state produces identical bounded evidence;
- repository content cannot alter policy.

### PR-014 — Structured decision package and validator

Build:

- decision schema;
- provenance and evidence-reference validation;
- conflict representation;
- unsupported command and fabricated-capability rejection;
- stale Git SHA rejection;
- smallest-operable-release policy;
- contract compiler.

Closest tests:

- valid decision compile;
- missing evidence or assumption rejection;
- hidden scope growth rejection;
- unsupported command rejection;
- stale proposal rejection.

Exit condition:

- only a complete, bounded, policy-compliant decision package can become approvable.

### PR-015 — Risk escalation and approval brief

Build:

- mandatory-risk matrix;
- reversible-safe-default logic;
- question deduplication and maximum-three limit;
- recommended answer for each question;
- concise approval brief;
- detailed appendix;
- expanded proposal hash.

Closest tests:

- normal repository: zero questions;
- destructive migration: escalation;
- paid service: escalation;
- contradictory core outcome: escalation;
- five candidate questions: reduced to three highest-priority questions.

Exit condition:

- the default view is concise while every detailed decision remains inspectable.

### PR-016 — MCP workflow, security, and release validation

Build:

- decision submission tool or equivalent host-agent protocol step;
- explicit user approval enforcement;
- proposer/approver separation;
- structured operational errors;
- beginner documentation;
- v0.4 release scripts and test command.

Closest tests:

- model self-approval rejection;
- concurrent approval serialization;
- prompt injection;
- mode-switch attack;
- question flooding;
- full v0.1–v0.3 regression.

Exit condition:

- an MCP-only flow can move from user outcome to approved locked contract without technical questions on the normal fixture.

## 11. Test strategy

### Unit

- mode resolution;
- evidence reference validation;
- provenance classification;
- conflict priority;
- risk classification;
- question ranking and cap;
- canonical proposal hashing;
- approval brief rendering.

### Integration

- natural-language outcome -> evidence pack -> submitted decision -> approval -> locked contract;
- repository changes between proposal and approval;
- SAFE and INTERVIEW opt-in behavior;
- current v0.3 MCP compatibility.

### Adversarial

- README instructs agent to ignore Shipping policy;
- agent hides a paid dependency as an implementation detail;
- agent adds unrelated features;
- agent claims unsupported tests exist;
- agent gives every decision `high` confidence without evidence;
- submitting agent attempts approval;
- proposal is modified after hash creation;
- question flood exceeds three;
- repository changes after analysis.

## 12. Acceptance criteria

| ID | Criterion |
|---|---|
| AC-0401 | Omitted mode resolves to AUTO. |
| AC-0402 | A normal repository fixture produces a complete one-screen approval brief with zero questions. |
| AC-0403 | Reversible low-confidence choices become documented assumptions instead of blocking questions. |
| AC-0404 | Every mandatory-risk category produces an escalation before approval. |
| AC-0405 | A proposal contains at most three questions in one batch with recommended answers. |
| AC-0406 | Every decision cites evidence or is labeled as an assumption with confidence and reversibility. |
| AC-0407 | The submitting model cannot approve its own proposal; exact explicit confirmation and hash remain required. |
| AC-0408 | Malicious repository instructions cannot alter mode, policy, MCP tools, or approval state. |
| AC-0409 | SAFE and INTERVIEW are explicit opt-in modes and cannot be selected silently. |
| AC-0410 | The default brief contains outcome, included scope, deferred scope, acceptance, assumptions, risks, and limits. |
| AC-0411 | Full v0.1.0–v0.3.0 regression, security, MCP, and license suites remain green. |
| AC-0412 | v0.4.0 closes with zero blockers, no unapproved drift, a clean commit, and an annotated tag. |

## 13. Release gate

```text
npm run lint
npm run typecheck
npm run test
npm run test:mcp
npm run test:decision
npm run security
npm run license:check
node scripts/mcp-smoke.mjs
shipping-harness verify
shipping-harness close
```

Release blockers:

- any AC-0401..0412 failure;
- model self-approval path;
- repository instruction overriding policy;
- unbounded or untraceable decision input;
- ordinary fixture requiring a technical question;
- hidden scope growth;
- regression in human stop, contract lock, evidence freshness, or closure.

## 14. Completion and next-version transition

v0.4.0 is complete only when it is CLOSED and tagged. Remaining ideas move to the v0.5 backlog.

v0.5.0 may start only when:

1. v0.4.0 is CLOSED;
2. a real repository produced an accepted decision brief;
3. the resulting contract can be compiled into stable Goals and Tasks without reinterpretation;
4. no v0.4 release blocker remains.
