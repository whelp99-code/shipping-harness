# v0.5.0 Development Plan — Durable Goal and Evidence Runtime

**Status:** PLANNED — starts only after v0.4.0 is CLOSED
**Predecessor:** v0.4.0
**Primary upstream reference:** Gajae Code Goal/Ledger/evidence freshness and bounded failure handling
**Secondary reference:** Ouroboros durable blocked outcomes and specification alignment

## 1. Release outcome

The approved Shipping contract becomes durable Goal and Task state that survives process and conversation restarts. Completion is based on current evidence, not chat memory or an agent's DONE statement.

```text
Locked Shipping contract
  -> stable Goals
  -> stable Tasks and dependencies
  -> execution attempts
  -> checkpoints and evidence
  -> DONE / BLOCKED / PLANNING_STUCK
  -> Shipping verification and Finisher
```

This version remains single-agent first. It creates the durable execution substrate needed before plugin UX or OMO runtime complexity.

## 2. User value

- work resumes from a durable state rather than restarting from conversation history;
- the user can see what is done, blocked, and remaining;
- completed work is not repeated after a crash;
- the same failure cannot consume unlimited retries;
- task completion is tied to the current contract and Git SHA;
- optional reviewer debt cannot reopen a completed release goal.

## 3. Entry gate

v0.5 implementation starts only when:

1. v0.4.0 is CLOSED and tagged;
2. the approved decision package compiles into the locked contract without unresolved ambiguity;
3. v0.4 regression, security, and MCP tests pass;
4. no OMO source or Team/DAG feature is introduced;
5. a disposable repository fixture exists for crash/restart testing.

## 4. Included scope

- stable Goal and Task IDs;
- contract-to-goal/task compiler;
- requirement and acceptance links;
- dependency validation and cycle rejection;
- explicit task and goal state machines;
- append-only execution/checkpoint ledger;
- attempt, evidence, blocker, and retry receipts;
- atomic state snapshots;
- restart recovery;
- current contract/Git SHA evidence binding;
- repeated-failure fingerprinting;
- no-progress retry suppression;
- bounded planning and review outcomes;
- human pause/abort authority;
- Finisher remains independent from task state.

## 5. Explicit non-goals

- multi-agent team;

## 6. State model

### Goal states

```text
PENDING -> ACTIVE -> VERIFYING -> DONE
              |          |
              |          -> BLOCKED
              -> BLOCKED
PENDING/ACTIVE -> SUPERSEDED only through an approved new contract revision
```

### Task states

```text
PENDING -> READY -> RUNNING -> VERIFYING -> DONE
                       |          |
                       |          -> FAILED -> RETRY_READY
                       |                         |
                       |                         -> RUNNING
                       -> BLOCKED

Any non-terminal state -> PAUSED when Shipping is paused
Exhausted bounded path -> BLOCKED or PLANNING_STUCK
```

`DONE` is not accepted unless required evidence matches the current contract hash and Git SHA.

## 7. Repository state

Planned artifacts:

```text
.shipping/
├── goals.json
├── tasks.json
├── execution-ledger.jsonl
├── checkpoints/
│   └── <checkpoint-id>.json
├── attempts/
│   └── <task-id>/<attempt-id>.json
└── failure-fingerprints.json
```

Rules:

- state snapshots use atomic write-and-rename;
- the ledger is append-only;
- snapshots are derived state, not the sole audit source;
- completed task evidence stores hashes and references, not unbounded raw output;
- chat transcripts are never the source of truth.

## 10. PR and implementation sequence

### PR-017 — Goal and Task schema

Build:

- stable ID format;
- contract compiler;
- requirement/acceptance links;
- state transition tables;
- dependency validation;
- orphan, duplicate, and cycle rejection.

Tests:

- deterministic compile;
- duplicate IDs;
- missing acceptance consumer;
- self-cycle and multi-node cycle;
- invalid state transition.

Exit:

- every Task has a locked Goal and an acceptance or requirement consumer.

### PR-018 — Durable ledger and recovery

Build:

- append-only ledger records;
- atomic Goal/Task snapshots;
- checkpoints;
- attempt records;
- process-restart rebuild;
- corrupt-tail handling with explicit diagnostic.

Tests:

- restart after every state transition;
- partial snapshot write;
- truncated final JSONL line;
- replay does not rerun completed task;
- ledger order remains deterministic.

Exit:

- current state can be rebuilt after process restart without mutable command replay.

### PR-019 — Evidence freshness and repeated-failure guards

Build:

- contract hash and Git SHA binding;
- evidence freshness check before DONE;
- failure fingerprint from task, command, source SHA, and normalized error;
- retry budget;
- identical no-progress suppression;
- changed-source reset rule.

Tests:

- old SHA evidence rejected;
- same failure on same SHA stops;
- changed source permits a new bounded attempt;
- agent DONE text cannot bypass evidence;
- optional NEXT finding does not reopen DONE.

Exit:

- no task can loop indefinitely on unchanged state.

### PR-020 — Bounded planning, status, and adversarial validation

Build:

- PLANNING_STUCK terminal reason;
- bounded plan/review counters;
- concise Goal/Task status view;
- MCP status integration;
- human pause/abort propagation;
- v0.5 release test command and documentation.

Tests:

- planner/reviewer ping-pong limit;
- pause during RUNNING;
- abort before recovery;
- conflicting checkpoint state;
- reviewer attempts scope expansion;
- full v0.1–v0.4 regression.

Exit:

- the runtime ends in DONE, BLOCKED, or PLANNING_STUCK; never indefinite activity.

## 11. Test strategy

### Unit

- graph compiler and cycle detector;
- state transitions;
- ledger serialization;
- fingerprint normalization;
- freshness comparison;
- checkpoint selection.

### Integration

- locked contract -> compiled graph -> Generic/Codex task execution -> evidence -> task DONE;
- process kill and restart mid-task;
- completed task recovery;
- failed task retry after source change;
- MCP status and pause.

### Adversarial

- agent edits Goal/Task files directly;
- duplicate completion event;
- stale evidence copied into a new attempt;
- ledger tail corruption;
- cyclic graph inserted after compile;
- same error text with changed command;
- reviewer repeatedly reopens DONE;
- process restarts immediately before terminal write.

## 12. Acceptance criteria

| ID | Criterion |
|---|---|
| AC-0501 | A locked contract compiles deterministically into stable Goals and Tasks with requirement and acceptance links. |
| AC-0502 | Orphan tasks, duplicate IDs, invalid dependencies, and cycles are rejected before execution. |
| AC-0503 | Goal, Task, attempt, checkpoint, blocker, and evidence events are persisted in an append-only ledger. |
| AC-0504 | State is restored after process restart without replaying completed work. |
| AC-0505 | A Goal or Task cannot become DONE without current contract-hash and Git-SHA evidence. |
| AC-0506 | Identical failures on unchanged state stop at the configured retry limit. |
| AC-0507 | Changed source or approved task input creates a new bounded attempt without erasing prior evidence. |
| AC-0508 | Exhausted planning/review paths end in PLANNING_STUCK or BLOCKED with an inspectable reason. |
| AC-0509 | Human pause/abort overrides task recovery and continuation. |
| AC-0510 | Finisher and release closure remain independent from Goal/Task completion state. |
| AC-0511 | Full v0.1.0–v0.4.0 regression, MCP, security, and license suites remain green. |
| AC-0512 | v0.5.0 closes with zero blockers, clean state, release receipt, and annotated tag. |

## 13. Release gate

```text
npm run lint
npm run typecheck
npm run test
npm run test:goals
npm run test:mcp
npm run test:adversarial
npm run security
npm run license:check
shipping-harness verify
shipping-harness close
```

Blockers include:

- any task DONE without fresh evidence;
- restart replaying completed work;
- unbounded retry path;
- Goal/Task state overriding human stop or Finisher;
- graph node without locked consumer;
- any AC-0501..0512 failure.

## 14. Completion and next-version transition

v0.5.0 closes when one disposable and one real internal project can recover from interruption and finish with a durable Goal/Task/evidence history.

v0.6.0 may start only when:

1. v0.5.0 is CLOSED;
2. status can be rendered from durable state without reading raw ledger files manually;
3. normal start/approve/status/pause/close actions have stable MCP tools;
4. no CLI-only repair step is required for the tested normal flow.
