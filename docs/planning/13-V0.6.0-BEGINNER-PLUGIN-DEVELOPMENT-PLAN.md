# v0.6.0 Development Plan — Beginner Plugin and Local Agent Experience

**Status:** PLANNED — starts only after v0.5.0 is CLOSED
**Predecessor:** v0.5.0
**Product rule:** normal users do not operate Shipping Harness through project-specific CLI commands

## 1. Release outcome

A non-developer installs one local package, asks an agent to finish a project, approves one concise release brief, and monitors only meaningful states. The CLI remains an operator/debug surface but is hidden from normal use.

```text
Install once
  -> “Finish this project”
  -> approval card
  -> PLANNING / RUNNING / BLOCKED / SHIPPABLE / CLOSED
  -> completion card and deferred backlog
```

v0.6 packages the existing deterministic core and MCP workflow into a beginner-safe local product. It does not introduce OMO runtime complexity yet.

## 2. User value

- no manual `.shipping/contract.yaml` editing;
- no need to remember `lock`, `verify`, `fix`, or `close` commands;
- one clear approval step;
- simple status and blocker explanations;
- immediate pause/abort control;
- repair and reinstall without losing release state;
- full evidence remains available when needed, but does not clutter the default view.

## 3. Entry gate

v0.6 starts only when:

1. v0.5.0 is CLOSED and tagged;
2. Goal/Task status is available through stable MCP responses;
3. the normal MCP-only flow can start, approve, execute, verify, and close;
4. human pause is proven to override every execution path;
5. no internal OMO runtime is required for the beginner flow.

## 4. Included scope

- one supported local installation path;
- Shipping MCP server registration;
- Shipping skill and agent instructions;
- lifecycle and approval guidance;
- project selection and repository validation;
- natural-language start flow;
- approval, progress, blocker, completion, and pause surfaces;
- concise language suitable for non-developers;
- detailed evidence inspection action;
- doctor and repair;
- upgrade, uninstall, and reinstall while preserving `.shipping` state;
- compatibility report;
- local-only, no public listener;
- accessibility and error-recovery tests.

## 5. Explicit non-goals

- remote HTTP MCP;
- mobile connection to the Ubuntu server;
- team RBAC;
- customer accounts or tenancy;
- web dashboard;
- arbitrary shell input;
- hidden automatic approval;
- OMO internal runtime;
- public marketplace dependency;
- automatic push or deployment.

## 6. Product surfaces

### Approval surface

Must show only:

```text
Outcome
Included now
Deferred
How completion is proven
Important assumptions
Risks requiring approval
Execution limits
[Approve] [Edit scope] [Stop]
```

### Progress surface

User-visible states:

```text
PLANNING
AWAITING_APPROVAL
RUNNING
PAUSED
BLOCKED
SHIPPABLE
CLOSED
ABORTED
```

Internal Task details remain inspectable but are not shown by default.

### Blocker surface

Each blocker contains:

- plain-language reason;
- requirement or acceptance ID;
- evidence summary;
- whether the user must decide;
- recommended next action;
- remaining attempt/fix budget.

### Completion surface

Contains:

- closed version;
- required checks passed;
- blocker count zero;
- number of deferred items;
- release report location;
- whether commit/tag/push occurred;
- next-version suggestion without automatically starting it.

The plugin calls existing high-level MCP tools. It does not bypass or duplicate the core state machine.

## 8. Installation contract

The supported install flow must:

1. locate the Shipping Harness package;
2. verify Node and Git compatibility;
3. register the local STDIO MCP server in the selected agent host;
4. install the Shipping skill/instructions;
5. verify tool discovery;
6. run a read-only doctor check;
7. leave existing repository `.shipping` state untouched.

No credential import, package-manager global mutation beyond the documented install, or external network listener is allowed.

## 11. Test strategy

### Unit

- user-state mapping;
- concise renderers;
- install-plan generation;
- compatibility checks;
- destructive action annotations;
- evidence truncation and detail links.

### Integration

- install -> tool discovery -> start -> approve -> run -> verify -> close;
- pause and resume from host UI;
- doctor/repair after broken registration;
- uninstall/reinstall with active DRAFT and CLOSED fixtures.

### Adversarial

- model calls approval tool without user confirmation;
- plugin exposes command-like argument;
- malformed card hides risk;
- status says CLOSED while core says BLOCKED;
- installer writes outside allowed config locations;
- uninstall deletes repository evidence;
- host does not support a renderer and must fall back to structured text safely.

## 12. Acceptance criteria

| ID | Criterion |
|---|---|
| AC-0601 | One documented local install path registers the MCP server, skill, and agent instructions. |
| AC-0602 | A normal user can start a release without editing JSON/YAML or running project-specific CLI commands. |
| AC-0603 | The normal flow presents one concise approval surface before execution. |
| AC-0604 | Progress surfaces truthfully map core state to PLANNING, RUNNING, PAUSED, BLOCKED, SHIPPABLE, or CLOSED. |
| AC-0605 | Every blocker surface includes reason, evidence, required action, and remaining budget. |
| AC-0606 | The user can pause or abort from the connected agent surface and the core stops continuation. |
| AC-0607 | Doctor and repair recover common registration/install faults without resetting repository release state. |
| AC-0608 | Upgrade, uninstall, and reinstall preserve contract, ledger, evidence, and closed receipts. |
| AC-0609 | No local plugin tool exposes arbitrary shell, public listener, customer endpoint, or automatic approval. |
| AC-0610 | Detailed evidence remains inspectable without appearing in the default concise view. |
| AC-0611 | Full v0.1.0–v0.5.0 regression, MCP, security, and license suites remain green. |
| AC-0612 | v0.6.0 closes with a successful beginner scenario, zero blockers, clean commit, and annotated tag. |

## 13. Release gate

```text
npm run lint
npm run typecheck
npm run test
npm run test:mcp
npm run test:plugin
npm run test:usability
npm run security
npm run license:check
node scripts/plugin-smoke.mjs
shipping-harness verify
shipping-harness close
```

Release blockers:

- normal flow requires manual config or project CLI;
- UI state disagrees with core state;
- approval can be self-triggered by the model;
- pause does not stop execution;
- repair/uninstall deletes Shipping state;
- public listener or raw command surface exists;
- any AC-0601..0612 failure.

## 14. Completion and next-version transition

v0.6 is complete when a non-developer fixture can install, approve, monitor, pause, recover, and receive a CLOSED release without learning the CLI.

v0.7 may start only when:

1. v0.6.0 is CLOSED;
2. the user-facing workflow is stable enough that OMO complexity remains hidden behind the same surfaces;
3. Shipping work orders and Goal/Task state are stable;
4. a separate private runtime repository/workspace and rollback location are prepared.
