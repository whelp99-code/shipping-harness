# v0.8.0 Development Plan — Bounded Team and DAG Orchestration

**Status:** CONDITIONAL PLAN — implementation requires v0.7 pilot evidence
**Predecessor:** v0.7.0
**Activation rule:** observed coordination bottleneck first; OMO feature availability alone is not justification

## 1. Release outcome

Larger internal projects can use a bounded multi-role team and dependency graph generated from locked Shipping Goals. Shipping remains the control plane, the Finisher stays outside the OMO team, and successful nodes are preserved while only failed or changed nodes are retried.

```text
Locked Goals/Tasks
  -> bounded graph compiler
  -> Planner / Builder / Tester / Reviewer
  -> node receipts and evidence
  -> selective retry/amend
  -> Shipping verification
  -> independent Finisher
```

## 2. Business justification gate

Before v0.8 scope can be locked, v0.7 pilot evidence must show at least one of:

- independent tasks are serialized and materially delay completion;
- one agent repeatedly loses context across distinct technical domains;
- test/review work blocks implementation despite clear parallel boundaries;
- selective node retry would avoid expensive full-task reruns;
- a real project needs durable coordination across more than one executor.

The evidence must also show that v0.7 already closes releases reliably. If coordination overhead is likely to exceed benefit, v0.8 is cancelled or reduced to better single-runtime routing.

## 3. User value

- larger work can progress in parallel without the user managing agents;
- each role has a clear purpose;
- failed parts can be retried without redoing successful parts;
- the user still sees only release-level status and blockers;
- agent disagreement or review ping-pong ends with a bounded reason;
- Team/DAG can be turned off without losing Shipping state.

## 4. Included scope

- Shipping Goal/Task to DAG compiler;
- stable graph fingerprint bound to contract hash and Git SHA;
- dependency, scope, and acceptance validation;
- logical roles: Planner, Builder, Tester, Reviewer;
- Finisher outside the team;
- task-category and model routing within approved policy;
- maximum four team members;
- default maximum two parallel members;
- default delegation depth one;
- node-level time, turns, tool, retry, and cost metadata;
- durable node status and receipts;
- node-scoped retry, amend, steer, and cancel;
- successful-node evidence preservation;
- no-progress, oscillation, repetitive-review, and role-ping-pong detection;
- crash recovery and completion deduplication;
- direct/single-runtime fallback;
- pilot benchmark comparing execution modes.

## 5. Explicit non-goals

- unlimited nodes, members, depth, parallelism, turns, retries, or time;
- agent-created top-level Goals;
- current-release scope evolution;
- Finisher as a team member;
- autonomous push, merge, deploy, or customer communication;
- enabling all OMO Team/DAG features;
- cross-project DAG;
- customer-facing collaboration;
- permanent use of Team/DAG when measured completion does not improve.

## 6. Graph contract

Each node must include:

```json
{
  "node_id": "NODE-001",
  "shipping_task_id": "TASK-001",
  "role": "builder",
  "depends_on": ["NODE-000"],
  "requirement_ids": ["REQ-..."],
  "acceptance_ids": ["AC-..."],
  "allowed_paths": ["src/**"],
  "expected_outputs": ["source change", "test evidence"],
  "budgets": {
    "turns": 8,
    "tool_calls": 80,
    "retries": 1,
    "wall_clock_seconds": 1800
  }
}
```

A graph is invalid when:

- a node lacks a locked Goal/Task consumer;
- a dependency is missing or cyclic;
- scopes overlap incompatibly without an explicit merge node;
- graph limits exceed Shipping policy;
- an agent or reviewer can create top-level scope;
- no acceptance consumer exists for a node result.

## 7. Role policy

### Planner

- decomposes only locked Goals;
- cannot add product scope;
- produces node boundaries and dependency rationale;
- stops after one accepted plan plus one bounded correction.

### Builder

- writes only allowed paths;
- cannot approve its own evidence;
- returns changed paths and execution receipts.

### Tester

- runs or adds tests within locked acceptance scope;
- cannot weaken required checks;
- classifies infrastructure failures separately from product failures.

### Reviewer

- maps findings to requirement or acceptance IDs;
- may create BLOCKER or NEXT recommendations;
- cannot reopen successful unrelated nodes;
- repeated equivalent findings are deduplicated.

### Finisher

Finisher is Shipping-owned and outside the team. It considers deterministic evidence and blocker policy only after team execution settles.

## 8. Default bounds

```yaml
max_nodes_per_run: 24
max_team_members: 4
max_parallel_members: 2
max_depth: 1
max_node_retries: 1
max_graph_amendments: 1
max_review_cycles: 2
max_role_ping_pong: 2
max_wall_clock_minutes: 120
unlimited_values_allowed: false
```

Larger values require a later contract and evidence. Zero must never mean unlimited.

## 9. No-progress and oscillation policy

The graph stops when any applies:

- the same node failure fingerprint repeats on unchanged source;
- two graph amendments alternate between equivalent states;
- reviewer and builder repeat the same dispute without new evidence;
- node completion count does not increase across the configured evaluation window;
- a role sends work back to another role more than the ping-pong limit;
- graph or release budget is exhausted.

Terminal outcomes are `BLOCKED`, `PLANNING_STUCK`, or `ORCHESTRATION_STALLED` with evidence.

## 11. PR and implementation sequence

### PR-030 — Shipping Goal to OMO DAG compiler

Build:

- graph schema;
- stable graph fingerprint;
- Goal/Task/requirement/acceptance mapping;
- dependency and cycle validation;
- scope-overlap policy;
- graph-size and budget validation.

Tests:

- deterministic graph compile;
- orphan node;
- cycle;
- missing acceptance consumer;
- conflicting path ownership;
- stale contract/Git binding.

Exit:

- only a valid locked Shipping graph can reach OMO.

### PR-031 — Bounded team and role policy

Build:

- four role profiles;
- routing and model provenance;
- member/parallel/depth admission;
- tool and path policy;
- external Finisher boundary;
- member lifecycle and cancellation mapping.

Tests:

- agent attempts top-level Goal creation;
- Finisher requested as team member;
- depth or member overflow;
- unavailable model route;
- reviewer writes source;
- Builder changes forbidden path.

Exit:

- role capabilities are explicit and bounded by Shipping policy.

### PR-032 — Node recovery, retry, amend, and stall controls

Build:

- node receipts and evidence;
- selective retry;
- one bounded graph amendment;
- successful-node preservation;
- duplicate completion suppression;
- failure fingerprint;
- oscillation and ping-pong detectors;
- crash recovery.

Tests:

- one failed node with two successful siblings;
- retry only failed node;
- changed dependency invalidates only downstream nodes;
- duplicate completion;
- runtime crash;
- repeated review dispute;
- graph amendment oscillation.

Exit:

- failed work does not erase valid unrelated evidence and cannot loop indefinitely.

### PR-033 — Team/DAG benchmark and pilot validation

Build:

- comparable fixtures for direct agent, v0.7 runtime, and v0.8 Team/DAG;
- metrics collector;
- coordination-overhead report;
- enable/disable decision record;
- rollback to v0.7 execution profile.

Metrics:

- ship rate;
- false-done rate;
- elapsed time;
- token/cost estimate when available;
- human interventions;
- rerun count;
- successful-node reuse;
- coordination overhead.

Exit:

- Team/DAG remains enabled only when pilot evidence shows real completion benefit without weakening governance.

## 12. Test strategy

### Unit

- graph compile and fingerprint;
- dependency frontier;
- role policy;
- budget admission;
- selective invalidation;
- stall detector;
- receipt deduplication.

### Integration

- four-role graph completes a fixture;
- one node fails and retries;
- pause cancels active members;
- runtime restarts and resumes owned nodes;
- Team/DAG disabled and v0.7 fallback used;
- Finisher verifies after team settlement.

### Adversarial

- agents create hidden nodes;
- node writes another node's path;
- planner expands scope;
- reviewer creates unsupported blocker;
- child spawns deeper child;
- graph requests unlimited value;
- role ping-pong;
- repeated equivalent graph amendment;
- late completion after cancel;
- cross-session team revival.

## 13. Acceptance criteria

| ID | Criterion |
|---|---|
| AC-0801 | v0.8 activation is backed by recorded v0.7 pilot evidence of a real coordination bottleneck. |
| AC-0802 | Every graph node maps to a locked Goal/Task and requirement or acceptance consumer. |
| AC-0803 | Missing dependencies, cycles, stale bindings, invalid scope, and oversized graphs are rejected. |
| AC-0804 | Finisher is outside the OMO team and no agent can expand top-level release scope. |
| AC-0805 | Members, parallelism, depth, time, turns, tools, retries, amendments, and graph size remain within policy; unlimited values are impossible. |
| AC-0806 | Failed or changed nodes can be retried/amended without rerunning unrelated successful nodes. |
| AC-0807 | No-progress, oscillation, repetitive review, and role ping-pong end with an inspectable terminal reason. |
| AC-0808 | Pause/abort/cancel prevents child continuation and late results cannot change Shipping state. |
| AC-0809 | Crash recovery preserves node ownership and deduplicates completion delivery. |
| AC-0810 | Team/DAG can be disabled and the release can continue through the approved v0.7 or direct fallback path. |
| AC-0811 | Benchmark evidence compares direct, v0.7, and v0.8 modes and records coordination overhead. |
| AC-0812 | v0.8.0 closes only when Team/DAG improves a real pilot without any regression in contract, stop, evidence, or Finisher authority. |

## 15. Completion and next-version transition

v0.8 is complete when the measured Team/DAG mode is either:

- accepted because it improves real completion under all Shipping invariants; or
- deliberately disabled with evidence that v0.7 remains the better default.

v0.9 may start only after local execution, pause, recovery, backup state boundaries, and runtime pin management are stable enough to expose through an authenticated internal gateway.
