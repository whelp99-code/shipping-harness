# v0.9.0 Development Plan — Internal Remote Control and Operations

**Status:** PLANNED — starts only after local runtime stability is proven
**Predecessor:** v0.8.0 or v0.7.0 when Team/DAG remains disabled
**Boundary:** authenticated owner/company-internal access only

## 1. Release outcome

The owner can use web/mobile agent clients to approve, monitor, pause, and receive completion reports for allowlisted projects on internal development servers. The gateway exposes Shipping operations, never arbitrary shell access.

```text
Authenticated internal client
  -> project allowlist
  -> signed proposal/approval
  -> Shipping MCP gateway
  -> local Shipping Core
  -> optional private OMO runtime
```

## 2. User value

- control Ubuntu-hosted development from a phone or another trusted client;
- see only projects explicitly allowed;
- receive blocker and completion notifications;
- approve the exact release proposal remotely;
- pause execution immediately;
- recover after server, gateway, or runtime restart;
- back up and restore without losing evidence authority.

## 3. Entry gate

v0.9 starts only when:

1. v0.7 local OMO runtime is stable and rollback is proven;
2. any enabled v0.8 Team/DAG mode is stable or disabled;
3. local plugin/MCP workflows are CLOSED and regression-clean;
4. project allowlist semantics are defined;
5. Shipping and minimum OMO state boundaries are documented;
6. no public/customer tenancy requirement exists;
7. a threat model and internal network deployment target exist.

## 4. Included scope

- authenticated internal remote gateway;
- encrypted transport;
- replay protection;
- owner/company identity mapping;
- explicit project allowlists;
- per-project read/approve/execute/pause permissions;
- signed proposal and approval receipts;
- remote status, approval, pause, blocker, evidence summary, and completion actions;
- notifications for approval-required, BLOCKED, and CLOSED;
- request and audit IDs;
- rate and payload limits;
- backup/restore for Shipping repository state;
- minimum required private OMO runtime state backup;
- upgrade, migration, rollback, and disaster-recovery runbooks;
- health, runtime pin, queue, execution, and completion metrics;
- cross-project isolation;
- mobile/web pilot against internal Ubuntu server.

## 5. Explicit non-goals

- anonymous public endpoint;
- customer tenancy;
- billing;
- public SaaS;
- remote arbitrary shell;
- remote editing of contract bytes;
- remote budget expansion;
- remote override of local pause/abort;
- public OMO runtime exposure;
- automatic public DNS or internet exposure;
- customer-facing SLA.

## 6. Security model

Authority order remains:

```text
local human pause/abort
  > locked Shipping contract
  > Shipping policy and budgets
  > authenticated remote approval
  > execution runtime requests
```

The gateway is not a second control plane. It invokes existing high-level Shipping operations and returns existing receipts.

### Required controls

- TLS or equivalent encrypted internal transport;
- authenticated session with short-lived credentials;
- project allowlist checked on every request;
- action permission checked after project resolution;
- nonce/timestamp/replay cache for mutating requests;
- signed proposal/approval receipt;
- exact project root, release ID, proposal hash, and Git SHA binding;
- bounded request size/depth/rate;
- no command, argv, environment, or raw path execution field;
- secret redaction before audit persistence;
- local pause checked immediately before every mutating action.

## 7. Remote tool surface

Allowed high-level operations:

```text
shipping_projects_list
shipping_status
shipping_start
shipping_approve_scope
shipping_execute
shipping_pause
shipping_resume
shipping_fix_blockers
shipping_verify
shipping_close
shipping_evidence_summary
```

Dangerous actions require explicit client confirmation. The gateway does not expose adapter launch commands or shell arguments.

## 8. Signed approval receipt

```json
{
  "schema": "shipping-remote-approval/v1",
  "request_id": "...",
  "actor_id": "...",
  "project_id": "...",
  "release_id": "...",
  "proposal_id": "...",
  "proposal_hash": "sha256:...",
  "git_sha": "...",
  "approved_at": "...",
  "expires_at": "...",
  "nonce": "...",
  "signature": "..."
}
```

A receipt is rejected when expired, replayed, signed by an unauthorized actor, bound to the wrong project/release/SHA, or already consumed where one-time semantics apply.

## 9. Backup and restore boundary

### Back up

- `.shipping/contract.yaml` and lock;
- state, Goal/Task snapshots, ledgers, issues, backlog;
- release receipts;
- evidence manifests and required logs/digests;
- proposal and approval receipts;
- runtime pin/compatibility manifests;
- OMO task state required for owned non-terminal work;
- configuration excluding raw provider credentials where possible.

### Restore requirements

- realpath/project identity is revalidated;
- contract and evidence hashes are rechecked;
- non-terminal work remains paused until ownership and runtime health are proven;
- terminal work is not replayed;
- restored approval receipts cannot be replayed;
- restore never changes CLOSED to active;
- missing runtime state produces BLOCKED, not guessed recovery.

## 10. Operations and observability

Health surfaces:

- gateway process and version;
- Shipping Core version;
- private OMO runtime pin and compatibility;
- project state counts;
- active and paused releases;
- runtime queue and child count;
- continuation/fix budget remaining;
- failed acceptance checks;
- last successful backup and restore drill;
- notification delivery status.

Logs and metrics must not expose repository secrets, prompts containing credentials, raw tokens, or provider credential stores.

## 12. PR and implementation sequence

### PR-034 — Internal remote gateway

Build:

- authenticated encrypted transport;
- session and actor model;
- project allowlist;
- per-action permissions;
- bounded remote MCP/tool gateway;
- replay and rate protection;
- audit IDs and structured errors.

Tests:

- unauthenticated request;
- wrong project;
- permission mismatch;
- replay;
- expired session;
- oversized/deep request;
- command-injection field;
- cross-project path attempt.

Exit:

- only an authenticated authorized actor can call an allowed high-level Shipping operation for an allowlisted project.

### PR-035 — Remote approval and notifications

Build:

- signed approval receipt;
- exact proposal/project/release/SHA binding;
- one-time approval consumption where required;
- approval-required, blocker, pause, and completion notifications;
- notification delivery ledger and retry cap.

Tests:

- wrong signature;
- wrong proposal hash;
- reused nonce;
- stale Git SHA;
- notification duplicate;
- notification failure does not alter release state.

Exit:

- remote approval is auditable and cannot be replayed or transferred to another release.

### PR-036 — Backup, restore, migration, and rollback

Build:

- versioned backup manifest;
- encrypted or access-controlled backup destination policy;
- integrity verification;
- restore-to-paused rule;
- schema migration and rollback;
- private OMO pin/artifact rollback;
- restore drill command and report.

Tests:

- backup during RUNNING;
- gateway crash during backup;
- corrupted archive;
- missing evidence file;
- restore CLOSED release;
- restore non-terminal OMO task;
- migration rollback.

Exit:

- a tested backup can restore authority and evidence links without replaying terminal work.

### PR-037 — Security, operations, and mobile pilot

Build:

- operational dashboards/status summaries;
- runbooks;
- incident workflow;
- denial-of-service bounds;
- mobile/web pilot client path;
- cross-project and multi-session adversarial suite.

Tests:

- authorization bypass;
- request forgery;
- token leakage;
- replay flood;
- project enumeration;
- backup exfiltration attempt;
- local pause versus remote resume race;
- gateway/runtime/server restart sequence.

Exit:

- the owner can safely control an allowlisted Ubuntu project remotely and recover from a restart or failed upgrade.

## 13. Test strategy

### Unit

- permission evaluation;
- allowlist resolution;
- signature and nonce validation;
- rate/payload limit;
- backup manifest and integrity;
- restore state rules;
- notification deduplication.

### Integration

- remote start/approve/status/pause/verify/close;
- local pause while remote execute arrives;
- gateway restart;
- private runtime restart;
- backup/restore of DRAFT, PAUSED, BLOCKED, and CLOSED states;
- remote client with Team/DAG disabled or enabled.

### Adversarial

- arbitrary command field;
- symlinked project allowlist path;
- actor switches project ID after signature;
- replay approval;
- stale proposal approval;
- request floods;
- cross-project receipt substitution;
- remote resume after local abort;
- backup contains secrets;
- restore replays completed task.

## 14. Acceptance criteria

| ID | Criterion |
|---|---|
| AC-0901 | All remote access is authenticated, encrypted, replay-protected, bounded, and restricted to explicit project allowlists. |
| AC-0902 | Per-project permissions prevent unauthorized read, approval, execution, pause, or close actions. |
| AC-0903 | No remote schema exposes raw command, argv, environment, arbitrary path execution, or policy override. |
| AC-0904 | Remote approval is signed and bound to exact actor, project, release, proposal hash, Git SHA, expiry, and nonce. |
| AC-0905 | Expired, replayed, transferred, wrong-SHA, or unauthorized approvals are rejected. |
| AC-0906 | A trusted web/mobile client can view status, approve, pause, inspect blockers, and receive completion notification. |
| AC-0907 | Local pause/abort remains stronger than any remote execute or resume request. |
| AC-0908 | Notifications are deduplicated and notification failure cannot change release state. |
| AC-0909 | Backup/restore preserves contract, Goal/Task state, evidence links, receipts, runtime pin, and CLOSED authority. |
| AC-0910 | Restored non-terminal work remains paused until ownership and runtime health are proven; terminal work is never replayed. |
| AC-0911 | Cross-project isolation, upgrade, migration, rollback, health, and incident runbooks pass operational drills. |
| AC-0912 | v0.9.0 closes after an internal mobile/web pilot, restore drill, security suite, all regressions, and zero blockers. |

## 16. Completion and next-version transition

v0.9 is complete when the remote path is safer than direct server access for the supported Shipping actions, and recovery is proven rather than documented only.

v1.0 may start only when:

1. local and remote workflows are stable;
2. schema changes are known and migratable;
3. representative projects have closed through direct, OMO, and any approved Team/DAG modes;
4. operations, backup, restore, and rollback evidence exists;
5. no external/customer product requirement has appeared.
