# v1.0.0 Development Plan — Stable Internal Shipping Control Plane

**Status:** PLANNED — final stabilization release
**Predecessor:** v0.9.0
**Product boundary:** personal and company-internal operation only

## 1. Release outcome

Shipping Harness becomes a stable internal product that turns a user outcome into a CLOSED software version through bounded decision-making, durable Goal/Task state, beginner-safe agent UX, optional private OMO execution, optional evidence-approved Team/DAG, authenticated internal remote control, and auditable operations.

```text
User outcome
  -> AI decision and one approval
  -> locked release contract
  -> durable Goals and Tasks
  -> direct or private OMO execution
  -> deterministic verification
  -> independent Finisher
  -> CLOSED release and backlog
```

v1.0 does not mean all possible features are implemented. It means the accepted internal product can be installed, operated, upgraded, recovered, audited, and used repeatedly without changing its core authority model.

## 2. Stable product promise

A representative non-developer can:

1. ask an agent to finish a project;
2. approve one concise release brief;
3. monitor RUNNING, PAUSED, BLOCKED, SHIPPABLE, or CLOSED;
4. pause or abort at any time;
5. receive a version with current evidence and a deferred backlog;
6. use local or authenticated internal remote control;
7. recover after restart or failed upgrade;
8. do this without learning project-specific CLI commands.

## 3. Entry gate

v1.0 implementation starts only when:

- v0.4 through v0.9 accepted release paths are CLOSED or deliberately disabled with evidence;
- schema inventory is complete;
- migration paths from supported prior versions are known;
- private OMO runtime pin/update/rollback is proven;
- backup/restore and incident drills have passed;
- representative internal pilots exist;
- no unresolved direction, licensing, security, or release-authority blocker remains.

## 6. Stable invariants

The following are release-blocking invariants for v1.0 and every later version:

1. agent text alone never proves completion;
2. evidence must match current contract hash and Git SHA;
3. unapproved scope drift blocks release;
4. human pause/abort wins over continuation, remote requests, recovery, and OMO state;
5. budgets are finite and unlimited values are invalid;
6. acceptance contract outranks reviewer preference;
7. NEXT/IGNORE debt does not block closure;
8. Finisher remains Shipping-owned and independent;
9. OMO/Team/DAG completion is an execution claim until Shipping verifies it;
10. CLOSED versions require a new version contract for further work;
11. internal-only direction blocks public/customer distribution;
12. unavailable dependencies produce truthful fallback or durable BLOCKED.

## 7. Stable architecture

```text
Agent host / internal client
        |
        v
Shipping Plugin + Local/Remote MCP
        |
        v
Shipping Governance Core
├── Decision and Approval
├── Contract and Scope
├── Goal/Task Runtime
├── Evidence and Gate
├── Issue Triage
├── Finisher and Closure
├── Adapter/Runtime Registry
└── Operations and Audit
        |
        +--> Direct Codex/Generic adapters
        |
        +--> Private Internal OMO Runtime
              ├── task/routing/recovery
              └── optional bounded Team/DAG
```

The private OMO runtime can be absent or disabled without corrupting Shipping Core state.

## 8. Schema lifecycle policy

Each stable schema must define:

- schema identifier and version;
- required and optional fields;
- canonical hashing rules;
- size/depth/item limits;
- unknown-field policy;
- migration owner;
- backward/forward compatibility window;
- redaction rules;
- immutable versus amendable fields;
- examples and invalid fixtures.

A migration cannot:

- change a CLOSED release to active;
- make stale evidence current;
- remove human stop;
- widen scope or budgets;
- convert NEXT into BLOCKER or DONE without explicit policy;
- trust previously untrusted runtime claims.

## 9. Supported environment and compatibility matrix

The final matrix records at least:

- supported Ubuntu and macOS versions;
- Node version;
- Git version expectations;
- supported agent hosts;
- supported local and remote MCP protocols;
- Shipping Core version;
- private OMO upstream and internal patch pins;
- bridge schema compatibility;
- Team/DAG enablement status;
- backup schema version;
- tested upgrade and rollback pairs.

Unsupported combinations return a clear diagnostic and cannot be reported as live/healthy.

## 10. Completion benchmark

### Scenarios

- small existing Node project;
- Python or mixed-stack repository;
- broken build with clear blocker;
- scope-creep temptation;
- stale evidence after source change;
- repeated identical failure;
- process/runtime crash;
- pause during active execution;
- optional OMO model unavailable;
- Team/DAG coordination fixture when enabled;
- backup/restore and upgrade/rollback.

### Compared modes

```text
A. direct coding agent
B. Shipping governance with direct adapter
C. Shipping + private OMO runtime
D. Shipping + approved Team/DAG mode
```

### Metrics

- ship rate;
- false-done rate;
- scope-drift incidence;
- stale-evidence acceptance rate;
- fix and retry cycles;
- human interventions;
- elapsed time;
- token/cost estimate when available;
- recovery success;
- completed-node reuse;
- user-visible question count;
- backup/restore and rollback success.

### Minimum quality thresholds

- false SHIPPABLE transitions: 0 in benchmark and adversarial suites;
- human-stop violations: 0;
- accepted stale evidence: 0;
- unapproved scope changes: 0;
- unlimited execution values: 0;
- normal AUTO fixture technical questions before brief: 0;
- all completion claims have current evidence: 100%;
- every supported state restores or fails with an explicit BLOCKED reason;
- benchmark reports trade-offs honestly even when a simpler mode performs better.

## 16. Definition of Done

v1.0.0 is done when:

- the accepted internal product promise works repeatedly;
- every required acceptance criterion passes;
- release blockers equal zero;
- governance invariants remain intact across every supported path;
- operations and recovery are proven;
- optional work is moved to the next roadmap;
- the version is CLOSED and not reopened.

After v1.0, any improvement starts from a new version contract. The stable release is not kept open for indefinite refinement.
