# v1.0.2 Development Plan — Proposal Safety Hardening

**Status:** PLANNED — mandatory patch after first OMP field run  
**Predecessor:** v1.0.1 CLOSED  
**Direction:** user is approver; AUTO is default; no development before canonical approval

## 1. Release outcome

Prevent an agent from presenting an unready, duplicated, mode-switched, dirty-baseline, or weakly verified proposal as approvable.

```text
one user outcome
  -> one canonical active proposal
  -> truthful state
  -> strong-enough acceptance
  -> explicit human approval or no execution
```

## 2. Problems proven by the first field run

- repeated `shipping_start` created three independent proposals;
- the host changed `AUTO -> SAFE -> AUTO` without user authorization;
- unresolved questions coexisted with an `APPROVABLE` label;
- `shipping_status` said UNINITIALIZED although pending proposals existed;
- `git diff --check` alone could become the authority-bearing acceptance set;
- dirty source was reported, but not represented as the canonical proposal state.

## 3. Included scope

### Canonical proposal state

Add one derived state used by MCP, status, approval, and UI:

- `PLANNING`
- `NEEDS_INPUT`
- `DIRTY_BASELINE`
- `NEEDS_ACCEPTANCE`
- `READY_FOR_APPROVAL`
- `APPROVED`
- `SUPERSEDED`
- `EXPIRED`

`READY_FOR_APPROVAL` is the only pre-approval state accepted by `shipping_approve_scope`.

### Idempotent start and supersession

- fingerprint active proposals by normalized goal, release, mode, Git SHA, and project root;
- return the existing active proposal for identical `shipping_start` calls;
- supersede older active proposals only when the requested decision materially changes;
- preserve all revisions and supersession links for audit.

### Mode authority

- omitted mode always resolves to `AUTO`;
- a host agent cannot change the active proposal mode by calling `shipping_start` again;
- non-AUTO mode requires an explicit `modeAuthorizedByUser: true` signal and a matching user-origin receipt;
- plugin guidance must forbid silent mode switching.

### Acceptance floor

- classify fallback-only acceptance as weak;
- `git diff --check` may be supplemental but never sufficient for a software release;
- weak acceptance produces `NEEDS_ACCEPTANCE` and cannot be approved;
- documentation-only repositories may use a bounded documentation-specific acceptance floor.

### Pending proposal status

- `shipping_status` reports the newest active proposal even before release state exists;
- expose canonical proposal ID, version, mode, state, readiness, dirty paths count, question count, acceptance strength, and next action;
- never print “not started” while an active proposal exists.

## 4. Explicit non-goals

- nested workspace selection;
- arbitrary command submission through MCP;
- `shipping_refine`;
- executing project code during analysis;
- automatic baseline commit or stash;
- adding product features to a target repository.

### PR-043 — Mode and acceptance authority

## 6. Acceptance criteria

| ID | Required result |
|---|---|
| AC-102-001 | Identical `shipping_start` calls return the same proposal ID and do not create another active proposal. |
| AC-102-002 | A materially changed request supersedes the previous active proposal with an audit link. |
| AC-102-003 | A host cannot change AUTO to SAFE or INTERVIEW without explicit user mode authorization. |
| AC-102-004 | Questions remaining always produce `NEEDS_INPUT`; approval is rejected. |
| AC-102-005 | Dirty source always produces `DIRTY_BASELINE`; approval is rejected. |
| AC-102-006 | Fallback-only `git diff --check` produces `NEEDS_ACCEPTANCE`; approval is rejected. |
| AC-102-007 | A pending proposal appears in `shipping_status` with one canonical state. |
| AC-102-008 | OMP 15.10.12 discovers and calls the patched MCP surface. |
| AC-102-009 | Full regression, security, license, package-install, and adversarial suites pass. |
| AC-102-010 | Release is CLOSED, annotated tag `v1.0.2` points to the closure commit, and worktree is clean. |

## 7. Adversarial validation

- duplicate calls racing concurrently;
- goal whitespace/case variations intended to create duplicates;
- AUTO/SAFE flip by the same proposer;
- crafted proposal file with mismatched state and approval status;
- stale active index;
- questions removed from presentation but retained in decision;
- dirty paths hidden in nested Git status output;
- weak fallback renamed to look like a test.

## 8. Installation gate

Build a tagged local package, install it to an isolated prefix, connect through OMP 15.10.12, and prove:

```text
pending proposal -> truthful status
weak gate -> approval denied
identical start -> same proposal
```

Only then close and install to the user-local prefix.
