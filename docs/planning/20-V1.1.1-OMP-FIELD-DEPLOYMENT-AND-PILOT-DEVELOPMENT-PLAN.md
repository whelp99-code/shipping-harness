# v1.1.1 Development Plan — OMP Field Deployment and Nested-Project Pilot

**Status:** IMPLEMENTED — completion authority remains the CLOSED receipt and annotated tag

**Predecessor:** v1.1.0 CLOSED

**Target environment:** Ubuntu `jm` user, OMP 18.0.10 through the existing `omo-balance` router and standalone `omp-core`; OMP 15.10.12 compatibility lane; local STDIO MCP; personal/company-internal use

## 1. Release outcome

Package, install, and operate the v1.1 feature set as OMP's main development harness, then prove it against an EvoHarvest-shaped real project without permitting false approval, false completion, target-source mutation, or OMP replacement.

## 2. Included scope

### Tagged package and user-local upgrade

- create a deterministic `v1.1.1` package from the closure candidate;
- verify package identity, version, SHA-256, and clean isolated install;
- upgrade `~/.local/lib/node_modules/shipping-harness` and command links;
- preserve rollback metadata and the previously working package;
- never publish to a public registry.

### OMP main-harness upgrade

- detect and retain the installed OMP wrapper/core version;
- preserve and back up `~/.omp/agent` configuration;
- register the installed `shipping-harness-mcp` as global STDIO MCP;
- expose nine tools including `shipping_refine`;
- keep approval mode `always-ask`;
- automatically allow planning/status/verification only;
- require user confirmation for scope approval, refine operations that contain user decisions, execution, blocker fix, pause/resume/abort, and close;
- update `AGENTS.md` and the Shipping skill through one delimited managed block;
- preserve unrelated MCP servers, approval policies, model roles, credentials, and router configuration.

### Field pilot

Run a non-destructive planning pilot against an EvoHarvest-shaped fixture and read-only analysis against the actual available repository:

1. detect the nested runtime workspace;
2. generate one AUTO proposal;
3. verify pending status is truthful;
4. refine the same proposal when a workspace answer is required;
5. confirm authority-bearing acceptance contains `make verify`, `make package`, and root `git diff --check` with correct `cwd` values;
6. remain `AWAITING_APPROVAL`;
7. do not approve, commit, stash, reset, or modify target source;
8. record a bounded pilot receipt with no source code or secret content.

### Operational evidence

- deterministic installer and package receipt;
- exact OMP version and worker-smoke receipt;
- MCP protocol and nine-tool inventory;
- approval policy hash;
- target-project read-only pilot summary;
- backup path and digest-checked rollback command;
- no-publication declaration.

## 3. Explicit non-goals

- resolving the target application's existing dirty worktree automatically;
- executing production deployment;
- claiming sandbox, Temporal, GitHub App, or customer-production readiness without evidence;
- modifying or updating OMP core, the router, provider credentials, or model routing;
- enabling Team/DAG;
- public package publication or customer distribution.
