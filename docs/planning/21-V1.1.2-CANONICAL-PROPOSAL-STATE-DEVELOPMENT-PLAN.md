# v1.1.2 Development Plan — Canonical Proposal State

**Status:** PLANNED — implementation begins only after the contract is committed and locked
**Predecessor:** v1.1.1 CLOSED
**Direction:** personal/company-internal, OMP as host, Shipping as sole release authority

## 1. Problem

A proposal can currently serialize `canonicalState: DIRTY_BASELINE` while nested decision and approval-brief fields still say `APPROVABLE`. The current OMP skill reads the canonical field, but another client could read a legacy field and misrepresent approval readiness. Refinement can also create a new revision even when no authority-bearing fact changed.

## 2. Release outcome

One canonical proposal state controls every user-facing projection and approval gate. Legacy serialized proposals remain hash-valid and are projected safely without silent rewrites. Approval checks include exact `cwd`, and no-op refinement is idempotent.

## 3. Included scope

- canonical proposal-state projection for storage and MCP output;
- normalization of `decision.approvalStatus`, `approvalBrief.status`, `readyForApproval`, and user view from one state;
- safe read projection for legacy contradictory proposal files without rewriting them;
- exact `cwd` in approval-brief acceptance entries;
- no-op `shipping_refine` detection with `changed: false` and no revision archive;
- real refinement revision/hash-chain preservation;
- OMP 18.0.10 and 15.10.12 MCP regression coverage;
- version, plugin, compatibility, traceability, and operator documentation updates.

## 4. Non-goals

- baseline commit, stash, reset, or discard automation;
- runtime-file classification;
- work-theme or component-graph analysis;
- new MCP tools;
- OMP core/model-router changes;
- push, deploy, publication, Team/DAG, or public listeners.

## 5. Requirements

- **REQ-CANON-001:** exactly one proposal state is authority-bearing.
- **REQ-CANON-002:** non-ready states cannot project an approval-ready label.
- **REQ-CANON-003:** legacy stored proposals remain hash-valid and unmodified on read.
- **REQ-CANON-004:** approval brief acceptance entries include command and `cwd`.
- **REQ-CANON-005:** no-op refinement does not increment revision or create an archive.
- **REQ-CANON-006:** only canonical `READY_FOR_APPROVAL` can pass scope approval.

## 6. Implementation sequence

### PR-053 — Canonical state projection

Create a projection function that derives the canonical state, maps it to a non-authoritative decision label, rebuilds the approval brief status, and controls `readyForApproval`.

### PR-054 — Safe legacy reads and approval brief cwd

Project old proposal records at read/response time without changing stored bytes or invalidating hashes. Include `cwd` in each approval-brief acceptance row.

### PR-055 — Idempotent refinement and adversarial validation

Compare authority-bearing proposal content before archiving. A no-op returns the current revision with `changed: false`; meaningful changes still create the next immutable revision.

## 8. Adversarial tests

- dirty proposal carrying a forged legacy APPROVABLE label;
- unresolved or weak proposal carrying ready flags;
- stale legacy file projected without rewrite;
- repeated no-op refine attempts;
- changed workspace/question/mode that must still form a valid revision chain;
- direct approval attempt based only on a nested legacy field.

## 9. Rollback and release gate

Rollback is the annotated `v1.1.1` tag and its user-local package. Release closure requires all contract commands to pass, zero blockers/unknowns, fresh Git-bound evidence, a CLOSED receipt, an annotated `v1.1.2` tag at the closure commit, and a clean worktree.
