# v1.3.0 Development Plan — Project Intelligence and Acceptance Coverage

**Status:** PLANNED — implementation is forbidden until v1.2.0 is CLOSED
**Predecessor gate:** v1.2.0 CLOSED, annotated tag valid, clean worktree

## 1. Release outcome

Shipping explains a mixed-stack project and its current work in concrete product language, then proves that every changed product area is covered by an authority-bearing acceptance check. Side-effecting package checks run in isolation and cannot dirty the operator worktree.

## 2. Included scope

- bounded component graph with primary and supporting stacks;
- detect Python, Node.js, Playwright, shell, Alembic, Rust, Go, and repository-owned task surfaces where evidenced;
- cluster dirty product changes into one to three evidence-backed work themes;
- recommend a concrete release goal without overriding explicit user outcome;
- map changed product paths to acceptance commands and exact `cwd`;
- classify uncovered product changes as NEEDS_ACCEPTANCE;
- describe command side effects and run package/release checks in a temporary worktree or equivalent isolated copy;
- require deterministic/idempotent package output where repository evidence supports it;
- one-screen approval projection with details expandable separately.

## 3. Non-goals

- semantic claims unsupported by repository evidence;
- executing production deploys or external integrations;
- auto-approving inferred goals;
- automatic product-code changes during planning;
- new MCP tools, public runtime, Team/DAG, or OMP core changes.

## 4. Requirements

- **REQ-INTEL-001:** mixed-stack components are explicit and path-bound.
- **REQ-INTEL-002:** work themes cite changed paths and remain bounded to three.
- **REQ-COVER-001:** each product change maps to acceptance evidence or blocks approval.
- **REQ-COVER-002:** acceptance commands retain exact `cwd` and side-effect classification.
- **REQ-ISOLATE-001:** side-effecting checks cannot mutate the source worktree.
- **REQ-ISOLATE-002:** non-deterministic package results become a blocker.

## 5. Implementation sequence

### PR-060 — Component and stack graph

Build path-bound component records and a primary/supporting stack summary from tracked manifests, source roots, test frameworks, migrations, and scripts.

### PR-061 — Work themes and concrete goal

Cluster current changed product paths into bounded themes and produce an evidence-backed goal recommendation while preserving the explicit user goal as authority.

### PR-062 — Acceptance coverage matrix

Map changed paths/components to selected acceptance commands. A product path with no coverage forces NEEDS_ACCEPTANCE.

### PR-063 — Isolated side-effect verification and one-screen pilot

Annotate side effects, execute package/release checks in isolation, compare repeated output digests where applicable, and render one concise approval card.

## 7. Rollback and release gate

Rollback is `v1.2.0`. Closure requires mixed-stack and coverage fixtures, isolated package verification, non-destructive EvoHarvest pilot, zero blockers/unknowns, fresh evidence, CLOSED receipt, annotated `v1.3.0`, and clean source.
