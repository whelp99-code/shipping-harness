# v1.4.0 Development Plan — Evidence-First Plain Brief

**Status:** PLANNED — implementation begins only after this plan and the release contract are committed and locked
**Predecessor:** v1.3.1 CLOSED, annotated tag `v1.3.1`, clean source, installed OMP main harness healthy
**Product boundary:** personal and company-internal use only; no public package publication or customer deployment

## 1. Problem

Shipping Harness already derives the correct canonical proposal state, baseline classification, workspace, version evidence, acceptance commands, coverage, blockers, and next action. However, the connected host model still turns those fields into the final prose shown to the user. This produces three avoidable failures:

1. exact technical evidence appears before the decision a non-developer needs;
2. model choice changes length, terminology, emphasis, and the proposed next sentence;
3. detailed paths, hashes, and command metadata can bury the one safe action the user should take.

The release must reduce model dependence without weakening any authority, evidence, approval, isolation, stop, or closure rule.

## 2. Release outcome

Shipping Core compiles its existing mechanical evidence into one deterministic Korean beginner report with these fixed sections:

```text
문제점
개선안
다음 진행 플랜
요약
```

The report also provides exactly one next action and, where appropriate, one exact phrase the user may submit. Detailed paths, hashes, commands, and evidence references remain available separately. OMP renders the Shipping-generated report as the default result instead of rewriting state or next-action semantics.

## 3. Non-negotiable invariants

v1.4.0 must not change:

- the canonical proposal state machine;
- approval readiness or `shipping_approve_scope` authority;
- Git, contract, evidence freshness, acceptance coverage, blocker, or closure semantics;
- human pause/abort priority;
- generated-artifact isolation and determinism policy;
- the exactly nine MCP tools;
- OMP core, router, providers, model routing, credentials, or executable bytes;
- EvoHarvest source, approval, or execution during the field pilot;
- the rule that only Shipping state `CLOSED` proves version completion.

## 4. Architecture

### 4.1 Mechanical brief fact graph

Add a deterministic `briefFactGraph` derived only from already-computed Shipping authority data:

- canonical state;
- baseline counts, blocking paths, plan hash, and preservation state;
- workspace and version evidence;
- work themes and acceptance coverage;
- acceptance command/`cwd`/side-effect/isolation metadata;
- blocker and unknown counts;
- evidence freshness and closure readiness;
- one next-action code.

Each fact carries:

```json
{
  "code": "BASELINE_NOT_PRESERVED",
  "authority": "mechanical",
  "evidenceRefs": ["baseline.planHash", "baseline.blockingPaths"],
  "confidence": "exact"
}
```

Model advisory text can be displayed separately but may never alter facts, state, approval, acceptance, next action, or closure.

### 4.2 Deterministic action envelope

Compile one action envelope from canonical state:

```json
{
  "currentState": "DIRTY_BASELINE",
  "allowedNow": ["REVIEW_BASELINE", "STOP"],
  "forbiddenNow": ["APPROVE_SCOPE", "EXECUTE", "CLOSE"],
  "requiresHumanApproval": true,
  "nextAction": "REVIEW_BASELINE",
  "exactUserPhrase": "이 기준선만 보존해."
}
```

There is exactly one primary next action. A host model cannot invent a different permitted action.

### 4.3 Korean plain brief compiler

Compile `plainBrief` from the fact graph and action envelope:

```json
{
  "schema": "shipping-harness/plain-brief-v1",
  "state": "DIRTY_BASELINE",
  "headline": "아직 새 개발을 시작할 수 없습니다.",
  "problems": [],
  "improvements": [],
  "nextPlan": [],
  "summary": "",
  "userAction": {
    "code": "REVIEW_BASELINE",
    "label": "기준선 보존 계획 검토",
    "exactPhrase": "이 기준선만 보존해."
  },
  "details": {
    "available": true,
    "evidenceRefs": []
  },
  "quality": {},
  "hash": "..."
}
```

The compiler must cover proposal states and active release states. It must use plain Korean, summarize path groups by counts and roles, and keep exact technical data in structured details.

### 4.4 Default MCP rendering

`shipping_start`, `shipping_refine`, and `shipping_status` return:

- `plainBrief` structured content;
- a deterministic Markdown/text rendering of the same brief;
- unchanged detailed authority fields for inspection.

The text renderer always uses the order:

```text
현재 상태
문제점
개선안
다음 진행 플랜
요약
지금 할 일
```

### 4.5 OMP presentation contract

Update the installed Shipping Skill and managed AGENTS block so the host:

1. renders `plainBrief` first and verbatim;
2. does not restate canonical state, readiness, or next action in new prose;
3. places optional model advice under a clearly non-authoritative `AI 참고 의견` heading;
4. keeps technical evidence expandable or after the beginner report;
5. never substitutes model text for Shipping evidence.

## 5. Selected Paperthin-inspired principles

Paperthin remains an external conceptual reference only. No Paperthin runtime, automatic update, skill catalog, or copied source is added. Original deterministic checks implement these general principles:

- **read-understanding:** the brief goal and current state do not contradict authority data;
- **one-next-action:** exactly one primary action is emitted;
- **single source of truth:** all projections share one fact graph and action envelope;
- **debloat:** bounded sections, item counts, and byte size;
- **independent verification:** acceptance proof is mechanical and not model self-evaluation;
- **post-output QA:** every compiled brief passes a deterministic quality report before exposure.

The design record must state that the implementation is original and that Paperthin is not a runtime dependency.

## 6. Performance and reliability requirements

- no additional LLM/model call;
- no additional Git subprocess in normal brief compilation;
- no network access;
- no new MCP tool;
- `plainBrief` and rendered text together remain bounded;
- compilation failure falls back to existing raw authority output without changing readiness or state;
- identical authority input produces byte-stable `plainBrief.hash` regardless of host model;
- beginner projection remains below 8 KiB unless detailed evidence is separately requested;
- median compile overhead in fixture benchmark is below 5% of existing proposal projection time and below 5 ms on the local test host.

## 10. Adversarial cases

- host model says the dirty proposal is ready;
- host model replaces the one next action with a menu;
- host model recommends reset/discard;
- model advisory text is inserted into evidence fields;
- duplicate or contradictory problem statements appear;
- exact path list floods the beginner output;
- acceptance command self-certifies a model-produced claim;
- renderer throws or returns oversized output;
- old OMP Skill rewrites the report;
- a tenth tool is introduced;
- target project is modified during the pilot;
- OMP executable bytes change during installation.

## 11. Rollback

Source rollback is annotated tag `v1.3.1`. Installation rollback uses the exact backup ID and command written to `~/.omp/agent/shipping-harness-install.json`. Any source, package, OMP hash, doctor, MCP, brief-hash, performance, or EvoHarvest fingerprint mismatch keeps deployment incomplete and triggers automatic installer rollback or a visible blocker.
