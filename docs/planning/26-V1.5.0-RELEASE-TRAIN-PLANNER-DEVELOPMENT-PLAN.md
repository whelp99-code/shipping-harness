# v1.5.0 Development Plan — Release Train Planner

**Status:** PLANNED — implementation begins only after this plan is committed and the v1.5.0 contract is locked
**Predecessor gate:** v1.4.0 CLOSED, annotated tag valid, clean worktree
**Product boundary:** personal and company-internal use; no public SaaS, push, deployment, or customer action

## 1. Release outcome

A user states one final product outcome. Shipping Harness compiles a deterministic rolling release train of one to five sequential versions from Git, manifests, current baseline, project type, acceptance evidence, and the explicit outcome. The first version is detailed enough to become the current Shipping contract. Later versions retain value, entry, exit, rollback, and replan gates but deliberately contain less implementation detail until their predecessor closes.

## 2. User value

The user no longer has to invent a technical roadmap. They can see:

- the final outcome;
- the minimum sequence of versions needed to reach it;
- what practical value each version adds;
- what must be true before each version begins and ends;
- what is intentionally deferred;
- which future details will be recalculated rather than guessed early.

The planner does not execute, approve, close, or weaken a release.

## 3. Included scope

- add a stable `shipping-harness/release-train-v1` authority document;
- compile 1–5 monotonically increasing semantic versions;
- use rolling detail levels: `CURRENT_FULL`, `NEXT_BOUNDED`, `FUTURE_GATES`;
- derive project profiles from existing mixed-stack, component, command, and path evidence;
- add deterministic value gates so a version cannot exist only to make tests easier;
- bind the first train release to the proposal’s exact release, scope, acceptance commands, and Git SHA;
- add prerequisites, entry gates, exit gates, rollback requirements, and replan triggers for every release;
- keep future release implementation details advisory and non-authoritative;
- expose the train through the existing `shipping_start`, `shipping_refine`, and `shipping_status` structured output;
- persist the approved train atomically when the current proposal is locked;
- keep one active train identity and deterministic hash for identical repository evidence;
- add a concise Korean train summary to the existing plain brief without exposing long paths by default;
- add schemas, examples, migration-safe projection, docs, traceability, and OMP presentation rules;
- retain the exact nine-tool MCP surface.

## 4. Non-goals

- automatic implementation or automatic close;
- adding a tenth MCP tool;
- model-written roadmap authority;
- detailed speculative tasks for distant versions;
- automatic Git commit, stash, reset, deletion, push, merge, or deployment;
- changing current proposal, evidence, pause/abort, blocker, SHIPPABLE, or CLOSED semantics;
- enabling Team/DAG;
- treating a roadmap as proof that a release is complete.

## 5. Architecture

### 5.1 Train authority

```text
explicit final outcome
+ current Git SHA
+ project/workspace/version evidence
+ baseline classification
+ component graph and work themes
+ repository-owned acceptance commands
+ project profile templates
        ↓
Release Train Compiler
        ↓
release-train-v1 + deterministic hash
```

Repository prose and model suggestions may be shown as advisory context but cannot alter the train hash, current release contract, or approval state.

### 5.2 Rolling planning depth

- current release: exact scope, command/cwd acceptance, paths, value gate, rollback, and exit gate;
- next release: value, prerequisites, bounded scope, project-type completion classes, rollback and replan gates;
- later releases: value, entry/exit gate, risk class, and explicit replan requirement only.

### 5.3 Mandatory release fields

Each release contains:

- stable release and requirement IDs;
- semantic version and predecessor;
- user-visible value statement;
- value-gate criteria;
- prerequisites and entry gate;
- included and excluded outcomes;
- technical acceptance classes and exact commands where mechanically known;
- risk profile and autonomy recommendation;
- rollback requirement;
- replan triggers;
- exit gate and next-release transition condition;
- planning depth and authority level.

## 6. Implementation sequence

### PR-072 — Release train schema and deterministic compiler

Create the core schema, profile classifier, semantic-version sequencing, value gates, planning depths, hash normalization, and fail-closed validation.

### PR-073 — Proposal, persistence, and plain-brief integration

Attach the train to proposal authority, include it in proposal fingerprints, persist it only on exact proposal approval, expose it through status/refine/start, and render a bounded Korean summary.

### PR-074 — Rolling-plan refinement and transition safety

Allow only bounded train preferences through existing refinement fields, protect the current release contract, detect stale Git/manifest evidence, and require replan rather than silently rewriting future versions.

### PR-075 — Verification, documentation, and field pilots

Add deterministic fixtures for clean, dirty, monorepo, web/API, database, CLI, weak-acceptance, and value-insufficient projects; run model-independence and hostile-input tests; update OMP rules and user docs.

## 7. Requirements

- **REQ-TRAIN-001:** one explicit final outcome compiles to 1–5 sequential versions.
- **REQ-TRAIN-002:** identical authority evidence produces the same train hash regardless of model or key order.
- **REQ-TRAIN-003:** semantic versions are strictly increasing and the current release equals the proposal release.
- **REQ-TRAIN-004:** every version has a non-empty measurable value gate.
- **REQ-TRAIN-005:** the current release is fully detailed; future detail decreases with distance.
- **REQ-TRAIN-006:** every version has entry, exit, rollback, and replan gates.
- **REQ-TRAIN-007:** future plans cannot change current contract authority or approval readiness.
- **REQ-TRAIN-008:** an approved train is persisted atomically and bound to proposal hash, Git SHA, and contract hash.
- **REQ-TRAIN-009:** stale or contradictory evidence returns `REPLAN_REQUIRED` rather than silent plan mutation.
- **REQ-TRAIN-010:** the existing nine MCP tools expose the train without raw commands or free-form future paths.
- **REQ-TRAIN-011:** the beginner view explains the version sequence and current stage in bounded Korean text.
- **REQ-TRAIN-012:** no new model call, network call, or unbounded repository scan is required.

## 10. Rollback

Source rollback is annotated tag `v1.4.0`. Train persistence is additive under `.shipping`; rollback never rewrites a closed release. A failed train migration or validation leaves the existing single-release proposal and state readable and blocks automatic use of the train.
