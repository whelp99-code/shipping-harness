# v1.6.0 Development Plan — Policy-Authorized Autopilot

**Status:** PLANNED — implementation begins only after v1.5.0 is CLOSED, tagged, and clean
**Predecessor gate:** v1.5.0 Release Train Planner proven in field fixtures
**Authority boundary:** policy may authorize reversible local development; external consequence remains human-owned

## 1. Release outcome

Shipping Harness executes an approved release train inside a pre-authorized operating policy. For every transition it produces exactly one deterministic decision: `AUTO`, `NOTIFY`, `ASK`, or `STOP`. Low-risk reversible local work may progress through baseline preservation, contract activation, implementation work orders, verification, bounded blocker repair, and automatic `CLOSED`. Irreversible, external, security, data, licensing, cost, or value-reducing decisions require a human-readable exception or stop.

## 2. User value

The user no longer approves technical hashes, file lists, ordinary local commits, routine verification, or safe version closure. They define the outcome and one operating policy. Shipping handles the repeatable engineering loop and asks only about consequences a non-developer can understand.

## 3. Included scope

- add stable `autopilot-policy-v1`, `autopilot-decision-v1`, and `autopilot-state-v1` documents;
- compile a default-deny internal policy with explicit permissions and consequence boundaries;
- classify each proposed action as `AUTO`, `NOTIFY`, `ASK`, or `STOP` from mechanical facts;
- distinguish `CLOSED` from `RELEASED` and keep production/public release human-authorized;
- allow policy-authorized local baseline preservation and local Git commits through exact path/hash receipts;
- activate only the current train release and require predecessor `CLOSED` before advancing;
- issue bounded host-agent work orders instead of raw shell commands;
- run existing acceptance, classify findings, and use bounded blocker-only repair cycles;
- automatically close only when policy, value, evidence, rollback, scope, and acceptance gates all pass;
- advance to the next planned release only after a clean, committed closure and replan check;
- transition to `REPLAN_REQUIRED`, `ASK`, or `STOP` when evidence or value changes materially;
- provide deterministic Korean notifications and exception questions based on effects, not technical details;
- preserve pause/abort precedence and exact nine-tool MCP surface;
- provide a dry-run/default mode before enabling apply.

## 4. Non-goals

- production deploy, public release, customer communication, purchasing, or paid API activation;
- automatic destructive migration, data deletion, auth/permission weakening, security-policy change, or license change;
- arbitrary command execution or model-authored policy authority;
- unlimited retries, unlimited versions, Team/DAG enablement, or background execution;
- bypassing current Shipping contracts, evidence freshness, blocker classification, or closure receipts;
- treating `CLOSED` as `RELEASED`.

## 5. Policy model

### 5.1 Decision classes

- `AUTO`: reversible local action explicitly allowed by policy;
- `NOTIFY`: allowed action with an auditable after-the-fact user notice;
- `ASK`: meaningful product/external consequence requiring user choice;
- `STOP`: missing evidence, forbidden consequence, or unsafe/no-rollback condition.

### 5.2 Default policy

Default policy allows read-only analysis and deterministic local verification. It may optionally allow exact local commits, bounded source edits, blocker repair, and local close. It denies external network writes, production, public release, data destruction, security weakening, license changes, cost, secrets, and unbounded execution.

### 5.3 Consequence classes

Mechanical classifiers cover:

- filesystem and Git reversibility;
- data-state and migration effects;
- authentication, authorization, secret, and security-policy effects;
- network/external/public effects;
- monetary and licensed-dependency effects;
- core-value reduction or acceptance weakening;
- rollback availability;
- unknown and conflicting evidence.

## 6. Execution state machine

```text
POLICY_READY
  -> TRAIN_READY
  -> RELEASE_PREPARING
  -> BASELINE_PRESERVING
  -> CONTRACT_ACTIVATING
  -> IMPLEMENTING
  -> VERIFYING
  -> FIXING_BLOCKERS
  -> SHIPPABLE
  -> CLOSING
  -> RELEASE_CLOSED
  -> REPLAN_CHECK
  -> NEXT_RELEASE | TRAIN_COMPLETE
```

Any state may transition to `PAUSED`, `ASKING`, `REPLAN_REQUIRED`, `STOPPED`, or `ABORTED` according to human authority and policy.

## 8. Requirements

- **REQ-POLICY-001:** policy is stable, hash-bound, explicit, bounded, and default-deny.
- **REQ-POLICY-002:** every action resolves to exactly one of AUTO/NOTIFY/ASK/STOP.
- **REQ-POLICY-003:** model text cannot grant permission or alter a decision.
- **REQ-POLICY-004:** external, production, public, cost, license, destructive-data, security, and auth consequences are never AUTO under the default policy.
- **REQ-AUTO-001:** only one release is active and its predecessor must be CLOSED.
- **REQ-AUTO-002:** automatic baseline/commit actions are exact-path, exact-head, hash-bound, reversible, and receipt-backed.
- **REQ-AUTO-003:** implementation occurs only through locked scope and bounded host work orders or configured adapters.
- **REQ-AUTO-004:** blocker repair is bounded and cannot add optional features or weaken acceptance.
- **REQ-AUTO-005:** automatic close requires policy permission, value gate, fresh evidence, rollback, zero blockers, zero unknowns, and no scope drift.
- **REQ-AUTO-006:** `CLOSED` and `RELEASED` are separate authority states.
- **REQ-AUTO-007:** material evidence change produces `REPLAN_REQUIRED`, not silent plan mutation.
- **REQ-AUTO-008:** pause/abort immediately outrank every automatic transition.
- **REQ-AUTO-009:** restart/recovery resumes from durable receipts without replaying completed mutations.
- **REQ-AUTO-010:** the nine-tool MCP surface remains bounded; no raw policy, shell, credential, push, or deploy field is added.
- **REQ-AUTO-011:** the user sees only consequence-based ASK questions and concise notifications.
- **REQ-AUTO-012:** every automatic mutation has a deterministic audit and rollback reference.

## 11. Rollback

Source rollback is `v1.5.0`. Autopilot defaults to dry-run. Applied state keeps append-only action receipts and exact rollback references. A rollback never deletes a closed release or reopens it; it pauses the train and requires a new higher release or explicit recovery policy.
