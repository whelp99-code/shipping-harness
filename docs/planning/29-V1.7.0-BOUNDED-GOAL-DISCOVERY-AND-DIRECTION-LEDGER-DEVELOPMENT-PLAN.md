# v1.7.0 Development Plan — Bounded Goal Discovery and Direction Ledger

**Status:** PLANNED — implementation starts only after this plan and the exact release contract are committed and locked
**Predecessor gate:** v1.6.1 is CLOSED, annotated-tagged, and clean
**Purpose:** complete the missing front half of Shipping Harness: understand the repository first, ask only product-level questions that mechanical evidence cannot answer, record the accepted direction immutably, then hand it to the existing Release Train and policy autopilot

## 1. Release outcome

A user may provide an incomplete or broad outcome without becoming a technical interview respondent. Shipping analyzes repository evidence first, distinguishes facts from decisions, compiles at most three material product questions, supplies a conservative reversible recommendation for each, accepts explicit answers or delegated recommended defaults, compares bounded direction candidates, runs one deterministic plan critic, and records the accepted direction in an append-only decision ledger. The resulting direction becomes the input to the existing release-train planner; it never grants execution, approval, verification, close, deployment, or RELEASED authority by itself.

## 2. User value

The user can start with language such as:

```text
이 프로젝트를 실제 내부에서 쓸 수 있게 완성해.
```

Shipping should answer repository-known questions itself and ask only decisions such as:

```text
누가 가장 먼저 사용할까요?
권장안: 현재 사용자와 회사 내부 운영자를 우선합니다.
```

The user may answer directly or delegate:

```text
권장안으로 결정해.
```

After the bounded discovery closes, Shipping presents one accepted direction, explicit non-goals, success criteria, and the version train. It does not restart a broad interview later unless a recorded replan trigger fires.

## 3. Included scope

- repository-evidence-first discovery with no extra model or network call;
- deterministic ambiguity detection for product outcome, primary user, operating boundary, and mutually exclusive core direction;
- zero questions when the explicit goal and repository evidence are already sufficient;
- at most three grouped questions per discovery round and at most two meaningful rounds;
- questions phrased in plain product language, never implementation trivia;
- conservative reversible `recommendedChoice` for every question;
- explicit answer and one-step delegated-recommendation handling through the existing `shipping_refine` tool;
- one to three deterministic direction candidates with benefits, costs, risks, evidence, and non-goals;
- one bounded direction critic that checks evidence coverage, conflicts, value loss, acceptance weakness, rollback, and external consequences;
- an accepted direction only after every material question is resolved and critic blockers are zero;
- immutable hash-chained decision ledger recording creation, recommendations, answers, delegated defaults, critic result, accepted direction, supersession, and replan triggers;
- accepted direction projection in proposal, status, beginner brief, Release Train, and OMP skill contract;
- same repository, Git SHA, goal, and answers produce the same authority hash regardless of host-model prose;
- exact nine MCP tools retained;
- read-only real-project and disposable fixture pilots;
- security inventory, compatibility, handover, beginner, MCP, and operational documentation updates.

## 4. Explicit non-goals

- a long consultancy-style or technical interview;
- asking the user to choose frameworks, libraries, file paths, commands, database tables, or test tools;
- model-generated questions or answers becoming Shipping authority;
- automatic acceptance of destructive, external, authentication, security, privacy, legal, license, cost, production, public, or customer-impact decisions;
- changing the locked release contract from interview prose;
- reopening or continuously evolving the current version after it is CLOSED;
- installing, vendoring, copying, or invoking the full Paperthin runtime or skill catalog;
- multi-model voting as evidence;
- adding a tenth MCP tool;
- enabling Team/DAG in this release;
- Git push, production deployment, customer communication, purchase, credential changes, or public release.

## 5. Architecture

```text
Explicit user outcome
        ↓
Repository Decision Evidence
        ↓
Goal Discovery Compiler
  - facts already answered
  - material ambiguities
  - safe recommended defaults
  - direction candidates
        ↓
Bounded Direction Critic
        ↓
NEEDS_INPUT or DIRECTION_READY
        ↓
Append-only Decision Ledger
        ↓
Accepted Direction
        ↓
Existing Release Train Planner
        ↓
Existing Policy Autopilot
```

### 5.1 Goal Discovery Compiler

New Shipping-owned module:

```text
src/core/goal-discovery.mjs
```

Inputs:

- explicit goal;
- mechanical decision evidence;
- selected workspace and version evidence;
- baseline and project intelligence;
- prior question resolutions;
- current proposal ID and revision.

Output:

```json
{
  "schema": "shipping-harness/goal-discovery-v1",
  "status": "READY|NEEDS_INPUT|BLOCKED",
  "questions": [],
  "candidates": [],
  "critic": {},
  "direction": {},
  "modelAuthority": false,
  "hash": "sha256"
}
```

### 5.2 Material question policy

Questions are allowed only when the missing decision can change user value, release boundaries, external consequence, or the meaning of completion.

Allowed dimensions:

1. **Primary outcome** — only when the goal is too generic to establish a value gate.
2. **Primary user** — only when different users imply materially different behavior or acceptance.
3. **Operating boundary** — local/personal, company-internal, or external/production when not mechanically clear.
4. **Core direction conflict** — only when two mutually exclusive product outcomes remain.

Technical implementation questions are forbidden.

### 5.3 Direction candidates

Candidate count is one to three. Candidate order and hashes are deterministic. Candidate types may include:

- `PRESERVE_AND_STABILIZE`;
- `DELIVER_CORE_WORKFLOW`;
- `OPERATE_AND_RECOVER`.

A candidate contains:

- user-visible outcome;
- primary user;
- operating boundary;
- included value;
- explicit non-goals;
- success criteria;
- risks and rollback expectations;
- evidence references;
- confidence and reversibility;
- no executable command authority.

### 5.4 Bounded Direction Critic

The critic is deterministic and runs once per authority-bearing discovery revision. It checks:

- every claim cites mechanical evidence or a recorded assumption;
- no unresolved question remains;
- core value is not deferred out of the current train;
- acceptance remains strong enough;
- rollback and external consequences are explicit;
- selected direction does not contradict the explicit user goal;
- no future release gains current command authority;
- the current version is finite and closable.

The critic may return `PASS`, `NEEDS_INPUT`, or `STOP`; it cannot modify the direction silently.

### 5.5 Immutable Decision Ledger

New module and runtime record:

```text
src/core/decision-ledger.mjs
.shipping/decision-ledger.jsonl
```

Every entry includes:

- sequence;
- occurred time;
- proposal ID and revision;
- event type;
- question or direction ID;
- choice and provenance;
- evidence references;
- prior event hash;
- event hash;
- `modelAuthority: false`.

The ledger is bounded, append-only, hash chained, path contained, and fail-closed on corruption, replay, oversized input, stale proposal binding, or sequence gaps.

## 7. Requirements

- **REQ-DISCOVERY-001:** analyze repository evidence before compiling any question.
- **REQ-DISCOVERY-002:** bypass discovery questions when the goal is materially sufficient.
- **REQ-DISCOVERY-003:** emit at most three material product questions and never technical implementation questions.
- **REQ-DISCOVERY-004:** every question has one conservative reversible recommended choice and evidence references.
- **REQ-DISCOVERY-005:** support explicit answers and delegated recommended defaults through existing `shipping_refine`.
- **REQ-DISCOVERY-006:** terminate after at most two meaningful discovery revisions; unresolved material ambiguity becomes durable STOP rather than an endless interview.
- **REQ-DISCOVERY-007:** host-model labels or prose cannot alter questions, recommendations, candidates, critic result, direction, or hashes.
- **REQ-DIRECTION-001:** generate one to three bounded deterministic candidates with user value and explicit non-goals.
- **REQ-DIRECTION-002:** run one deterministic critic and expose its evidence-bound findings without silent mutation.
- **REQ-DIRECTION-003:** accept a direction only when material questions and critic blockers are zero.
- **REQ-DIRECTION-004:** feed the accepted direction into the existing Release Train while preserving the original explicit goal and provenance.
- **REQ-DIRECTION-005:** future train releases remain advisory and require replan after predecessor CLOSED.
- **REQ-LEDGER-001:** persist all discovery and direction authority events in an append-only hash chain.
- **REQ-LEDGER-002:** reject tamper, replay, stale proposal binding, sequence gaps, oversized history, and path escape.
- **REQ-LEDGER-003:** preserve answer provenance as explicit user, delegated recommendation, or mechanical fact.
- **REQ-LEDGER-004:** model prose, task completion text, and critic text alone never become approval, acceptance, close, or release evidence.
- **REQ-BOUNDARY-001:** retain exactly nine MCP tools and no raw command surface.
- **REQ-BOUNDARY-002:** infinite current-version evolution and full Paperthin runtime remain explicit tested non-goals.

## 12. Rollback

Source rollback is annotated tag `v1.6.1`. User installation rollback uses the v1.7.0 install receipt and stored package digest. Rollback preserves the decision ledger as audit history, pauses any non-terminal work, and never turns discovery or direction records into release authority.
