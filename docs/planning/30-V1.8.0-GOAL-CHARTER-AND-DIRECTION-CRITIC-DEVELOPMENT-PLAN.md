# v1.8.0 Development Plan — Goal Charter and Direction Critic Binding

**Status:** PLANNED — implementation starts only after this plan is committed and the exact v1.8.0 contract is locked
**Predecessor gate:** v1.7.0 is CLOSED at annotated tag `v1.7.0`
**Purpose:** turn the bounded discovery result into one immutable, independently readable Goal Charter that is bound to the approved proposal, locked contract, Git baseline, Release Train, Decision Ledger, and replan policy

## 1. Release outcome

A ready v1.7 direction becomes a structured Goal Charter before scope approval. The charter records the final outcome, primary user, operating boundary, value, included results, non-goals, measurable success criteria, assumptions, evidence, rollback, replan triggers, candidate hash, critic hash, and discovery hash. Before approval it is a non-authoritative preview. At approval Shipping accepts and persists exactly that charter, binds it to the proposal/revision/hash, current Git SHA, contract hash, baseline SHA, Release Train hash, approver class, and Decision Ledger event, and exposes it through the existing nine MCP tools.

The charter never grants command, model, approval, closure, deployment, external-write, public, customer, cost, data, authentication, security, license, or `RELEASED` authority. A later request that changes its outcome, primary user, operating boundary, non-goals, success criteria, rollback, or accepted hash requires a new proposal/replan and cannot silently mutate a locked or CLOSED release.

## 2. User value

The user can inspect one durable answer to:

```text
무엇을 완성하는가?
누가 쓰는가?
어디까지 운영하는가?
이번 버전에서 하지 않는 것은 무엇인가?
무엇으로 성공을 증명하는가?
언제 다시 계획해야 하는가?
```

The coding model may implement the charter, but it cannot rewrite it.

## 3. Included scope

- deterministic Goal Charter preview compiled from `goalDiscovery.direction`, critic, user/delegated resolutions, repository evidence, and current proposal identity;
- stable `shipping-harness/goal-charter-v1` schema and runtime-authentic example;
- explicit `PROPOSED` and `ACCEPTED` charter states;
- accepted-charter binding to proposal ID/revision/hash, Git SHA, release, project, contract hash, baseline SHA, Release Train hash, approver type, and acceptance time;
- atomic persistence at `.shipping/goal-charter.json` only during successful scope approval;
- Decision Ledger `direction.accepted` event includes Goal Charter hash and contract binding;
- Release Train source/binding exposes the accepted charter hash without granting future-release authority;
- `shipping_start`, `shipping_refine`, `shipping_approve_scope`, `shipping_status`, plain brief, OMP Skill, resources, and handover expose the charter through the existing nine tools;
- replan/supersession checks reject stale, tampered, foreign, or silently changed charters;
- bounded size, deterministic preview hash, no model/network calls, and read-only real-project pilot.

## 4. Excluded scope

- new MCP tools or raw command fields;
- model-selected authority or multi-model voting;
- Paperthin runtime or automatic skill execution;
- OMO Team/DAG activation;
- Ouroboros-style infinite mutation of the current version;
- automatic push, merge, deployment, publication, purchase, customer contact, credential change, or `RELEASED`;
- reopening v1.7.0 or any CLOSED release;
- weakening existing Release Train, Autopilot, acceptance, rollback, blocker, unknown, pause, or abort gates.

## 5. Architecture

```text
Repository evidence + explicit goal
        ↓
Bounded Goal Discovery
        ↓
Direction candidates + deterministic critic
        ↓
Goal Charter preview (PROPOSED / no authority)
        ↓
Exact scope approval and contract lock
        ↓
Accepted Goal Charter
  proposal + Git + contract + baseline + train binding
        ↓
Decision Ledger direction.accepted
        ↓
Release Train + Policy Autopilot
```

### Authority order

1. Human pause/abort.
2. Accepted Goal Charter and locked Shipping contract.
3. Policy Autopilot consequence decision.
4. Current Git-bound acceptance evidence.
5. Shipping SHIPPABLE/CLOSED gate.
6. OMO or host-agent task state.
7. Model prose.

## 7. Replan policy

A new proposal is required when any accepted authority field changes, when Git/manifest evidence invalidates the charter, when success criteria cannot be proven, when a core non-goal must be removed, when rollback disappears, or when external/data/auth/security/license/cost consequences appear. Replanning may supersede a proposed charter; it never edits an accepted charter in place and never reopens a CLOSED release.

## 8. Requirements

- **REQ-CHARTER-001:** compile one deterministic Goal Charter preview from a ready discovery direction.
- **REQ-CHARTER-002:** reject charter generation while questions or critic blockers remain.
- **REQ-CHARTER-003:** preserve explicit/delegated answer provenance and evidence references.
- **REQ-CHARTER-004:** atomically persist one accepted charter only after valid scope approval.
- **REQ-CHARTER-005:** bind accepted charter to proposal, Git, contract, baseline, Release Train, and approver evidence.
- **REQ-CHARTER-006:** include the charter hash in Decision Ledger acceptance and Release Train binding.
- **REQ-CHARTER-007:** expose the charter through existing MCP/status/plain-brief/OMP surfaces without a tenth tool.
- **REQ-CHARTER-008:** reject tamper, stale hashes, foreign proposal/Git/contract/train binding, and in-place accepted-charter mutation.
- **REQ-CHARTER-009:** require replan for authority-bearing direction changes.
- **REQ-CHARTER-010:** maintain false READY/CLOSED/RELEASED, model authority, and target mutation at zero.
- **REQ-CHARTER-011:** preserve all v1.7.0 interview, Ledger, Release Train, Autopilot, OMP, security, and operational behavior.
- **REQ-CHARTER-012:** add no model or network call to proposal/status compilation.
