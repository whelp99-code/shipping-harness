# Shipping Harness v1.8.2 — Plain Brief Budget Hotfix

## 1. 문제

Orca-JARVIS의 실제 `DIRTY_BASELINE` Proposal을 Shipping Harness v1.8.1로 재스캔했을 때, 사용자용 `plainBrief`의 렌더링 텍스트는 1,716바이트였지만 구조화 JSON은 8,538바이트로 고정 한도 8,192바이트를 초과했다. 안전 판정은 유지됐으나 `plainBriefText`가 제거되어 일반 사용자가 다시 긴 raw authority 결과를 읽어야 했다.

## 2. 원인

`plainBrief`가 동일한 사실을 여러 위치에 중복 투영했다. 특히 Canonical State에서 파생 가능한 승인 준비 여부, 값이 0인 BLOCKER·UNKNOWN, 별도 `releaseTrain` 요약과 중복되는 Release Train Fact, 스키마와 `modelAuthority=false`로 이미 표현되는 Compiler Fact가 Fact Graph에 반복 저장됐다.

## 3. 고정 원칙

- 8,192바이트 제한을 늘리지 않는다.
- 전체 Action Envelope와 금지 행동은 유지한다.
- 문제점·개선안·다음 진행 플랜·요약·지금 할 일을 유지한다.
- 모든 사용자 문장과 남은 Fact는 기계적 증거에 연결한다.
- 모델은 승인·실행·종료 권한을 갖지 않는다.
- MCP 도구는 정확히 9개를 유지한다.

## 4. 구현

1. Fact Graph에서 파생 가능하거나 값이 0인 중복 Fact를 조건부 생략한다.
2. Canonical State와 Primary Next Action은 항상 유지한다.
3. BLOCKER·UNKNOWN Fact는 0보다 클 때만 포함한다.
4. Approval Readiness Fact는 실제 `READY_FOR_APPROVAL`일 때만 포함한다.
5. 별도 Release Train 요약과 중복되는 Fact 및 Compiler 설명 Fact는 제거한다.
6. Orca-JARVIS 형태의 Dirty Baseline·3개 Goal 질문·4단계 Release Train Fixture를 추가한다.

## 5. 완료조건

- 실제 형태 Fixture의 `quality.healthy=true`.
- 구조화 출력은 7,680바이트 이하, 렌더링은 4,096바이트 이하.
- `REVIEW_BASELINE`과 전체 금지 행동이 유지됨.
- 남은 Fact가 모두 `mechanical`이며 증거 참조를 보유함.
- 모델 라벨에 따른 Hash 차이 0.
- 기존 Plain Brief·MCP·Autopilot Field·전체 Release Verify 통과.
- BLOCKER 0, UNKNOWN 0, Scope Drift 0, 현재 Git SHA 증거 Fresh.

## 6. 운영 검증

태그 설치 후 Orca-JARVIS의 같은 Proposal을 `shipping_refine(rescan=true)`로 재투영한다. 제품 Git HEAD와 기존 제품 변경은 그대로 유지하면서 `plainBriefText`가 생성되고 Goal Discovery 상태가 노출되는지 확인한다.
