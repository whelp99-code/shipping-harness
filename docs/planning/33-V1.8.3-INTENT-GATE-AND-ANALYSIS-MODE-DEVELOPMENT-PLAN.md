# v1.8.3 Development Plan — Intent Gate and Analysis Mode

**Status:** IMPLEMENTED ON FEATURE BRANCH — release preparation waits for an explicit commit request  
**Predecessor:** v1.8.2 CLOSED  
**Purpose:** prevent terse or ambiguous user prompts from being expanded into planning, implementation, or Autopilot without first completing read-only project analysis and confirming the requested workflow boundary.

## 1. Problem

A prompt such as `이 프로젝트 분석해. 쉬핑하네스로` previously produced a generic Goal Discovery and Release Train before the user confirmed whether they wanted analysis only, planning, implementation, or full Autopilot. `DIRTY_BASELINE` could also dominate the beginner report and hide the unresolved workflow intent.

This was safe against mutation, but wrong for user intent:

- analysis was described as if development had already been requested;
- a Release Train appeared before its purpose was authorized;
- Goal Discovery questions existed but were hidden behind baseline handling;
- the default path was not explicitly read-only;
- users could not tell whether they were approving analysis, planning, development, or closure.

## 2. Release outcome

Shipping Harness introduces one deterministic Intent Gate before Goal Discovery and Release Train planning.

```text
user prompt
→ read-only repository analysis
→ Intent Gate
→ ANALYZE_ONLY / PLAN_ONLY / IMPLEMENT / AUTOPILOT
→ bounded Goal Discovery only when planning is authorized
→ Goal Charter and Release Train only after direction is ready
→ implementation approval only for IMPLEMENT or AUTOPILOT
```

The Intent Gate does not add an MCP tool, model call, network call, command authority, approval authority, closure authority, or deployment authority.

## 3. Stable modes

| Mode | Meaning | Planning | Implementation | Autopilot |
|---|---|---:|---:|---:|
| `ANALYZE_ONLY` | Show read-only evidence and stop | No | No | No |
| `PLAN_ONLY` | Confirm direction and produce a non-executing version plan | Yes | No | No |
| `IMPLEMENT` | Enter the existing approval-gated implementation flow | Yes | Yes | No |
| `AUTOPILOT` | Enter the existing policy-authorized Autopilot flow | Yes | Yes | Yes |

The default for an ambiguous prompt is always `ANALYZE_ONLY`.

## 4. Canonical proposal states

- `INTENT_CONFIRMATION_REQUIRED`: read-only analysis is complete; one workflow-boundary question remains.
- `ANALYSIS_COMPLETE`: the user requested analysis only; no planning or mutation authority exists.
- `PLAN_COMPLETE`: Goal Charter and Release Train are ready as a non-executing plan.
- Existing `NEEDS_INPUT`, `DIRTY_BASELINE`, `NEEDS_ACCEPTANCE`, and `READY_FOR_APPROVAL` remain authoritative for planning and implementation flows.

Intent confirmation is evaluated before `DIRTY_BASELINE`, so a dirty repository cannot hide the user-intent question. The dirty baseline remains visible evidence and blocks implementation after intent and direction are resolved.

## 5. Requirements

- `REQ-INTENT-183-001` — Every `shipping_start` completes read-only analysis before asking the user anything.
- `REQ-INTENT-183-002` — Terse or ambiguous analysis prompts produce exactly one `Q-INTENT-001` workflow-boundary question.
- `REQ-INTENT-183-003` — The ambiguous-request default is `ANALYZE_ONLY`.
- `REQ-INTENT-183-004` — Explicit analysis-only language produces `ANALYSIS_COMPLETE` without Goal Discovery, Goal Charter, or Release Train.
- `REQ-INTENT-183-005` — `PLAN_ONLY` may create Goal Discovery, Goal Charter preview, and Release Train, but cannot be approved or executed.
- `REQ-INTENT-183-006` — Only explicitly confirmed `IMPLEMENT` or `AUTOPILOT` intent can reach `READY_FOR_APPROVAL`.
- `REQ-INTENT-183-007` — Intent confirmation occurs through existing `shipping_refine`; MCP remains exactly nine tools.
- `REQ-INTENT-183-008` — Host-model prose and hidden request fields cannot change the deterministic Intent Gate hash.
- `REQ-INTENT-183-009` — Unsafe intent answers requesting approval bypass, automatic production release, or authority escalation fail closed.
- `REQ-INTENT-183-010` — `DIRTY_BASELINE` cannot suppress the intent question or trigger baseline mutation before intent confirmation.
- `REQ-INTENT-183-011` — Goal Charter and authoritative Release Train remain null until intent permits planning and Goal Discovery is ready.
- `REQ-INTENT-183-012` — The beginner report explains analysis completion, the one workflow choice, and the non-mutating default in Korean.
- `REQ-INTENT-183-013` — Intent Gate has a frozen JSON Schema and deterministic example.
- `REQ-INTENT-183-014` — Existing OMP 18.0.10, approval policy, Pause/Abort priority, CLOSED != RELEASED, and external-consequence boundaries remain unchanged.

## 6. Scope

### Included

- deterministic request-intent classifier;
- one workflow-boundary question with four modes;
- read-only analysis completion state;
- non-executing plan completion state;
- Goal Discovery, Goal Charter, Release Train, and approval gating;
- MCP and OMP user-view projections;
- stable schema and example;
- unit, MCP, integration, adversarial, schema, and real-project read-only tests;
- beginner, MCP, traceability, security, compatibility, and handover documentation.

### Excluded

- a tenth MCP tool;
- natural-language model classification;
- automatic baseline commit;
- automatic scope approval;
- automatic production deployment or public release;
- data deletion, authentication, security, license, cost, customer, or credential changes;
- OMO Team/DAG default activation;
- Paperthin runtime dependency;
- infinite mutation of the current version.

## 7. Acceptance criteria

1. Focused Intent Gate unit, MCP, and adversarial tests pass.
2. Stable schema suite passes with the new Intent Gate document and example.
3. `이 프로젝트 분석해. 쉬핑하네스로` yields:
   - read-only analysis complete;
   - `INTENT_CONFIRMATION_REQUIRED`;
   - exactly one intent question;
   - default `ANALYZE_ONLY`;
   - no Goal Discovery, Goal Charter, or Release Train;
   - no approval, execution, verification command, commit, or close.
4. Selecting `ANALYZE_ONLY` yields `ANALYSIS_COMPLETE`.
5. Selecting `PLAN_ONLY`, then resolving bounded product questions, yields `PLAN_COMPLETE` with no implementation authority.
6. Explicit `IMPLEMENT` and `AUTOPILOT` requests retain the existing approval and policy gates.
7. Hostile model text, preloaded Goal Charter/Release Train, invalid choices, and dirty-baseline ordering fail closed.
8. MCP inventory remains exactly nine tools and exposes no raw command surface.
9. Orca-JARVIS read-only field pilot preserves Git HEAD, tracked source bytes, and dirty status.
10. Full `npm run release:verify` passes with `TMPDIR` redirected from the saturated `/tmp` tmpfs to a user-owned home-disk cache.
11. `git diff --check` passes.

## 8. Rollback

The implementation is isolated on branch `intent-gate-v1.8.3`. Before an explicit commit, rollback is deletion of the uncommitted branch changes. After a future commit and release, rollback must use the predecessor annotated tag and OMP main-harness backup receipt; no production state is modified by this development batch.

## 9. Completion boundary

This batch is implementation-complete only when the focused, adversarial, stable, real-project read-only, and full regression gates pass. It is not release-closed, tagged, installed, pushed, merged, or published until the user explicitly requests the corresponding Git and installation actions.
