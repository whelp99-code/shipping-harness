# Shipping Harness v1.9.0 — Engineering Infrastructure and Maintainability

## 1. 문제

v1.8.2 시점의 리포 평가(2026-09-12) 결과, 제품 개념·안전 경계·릴리즈 거버넌스는 9점대였으나 반복 가능한 엔지니어링 인프라가 낮았다.

| 항목 | 점수 | 근거 |
|---|---:|---|
| 툴링·CI | 4 | CI 없음. ESLint·Prettier·tsc 없음. 자체 lint는 탭·후행공백·문법만, typecheck는 import 해석만 검사 |
| 유지보수성 | 5 | 단일 기여자. `release:verify`가 `npm run` 21개 체인. doc audit 필수 파일 47개 하드코딩. 일회성 pilot 스크립트 잔존. 예외를 삼키는 `catch {}` 24곳 |
| 문서 | 6 | README에 버전 섹션 23개 누적. MCP.md 뒤에 버전별 섹션 누적. README 헤더 v1.8.1 vs package 1.8.2 불일치 |
| 배포·사용성 | 6 | 절대경로 tgz 설치. 설치 경로 3가지 병존 |
| 코드 구조 | 7 | `callShippingTool` 487줄, `refineScopeProposal` 203줄, CLI if 체인 302줄. export 함수 JSDoc 247/366 |
| 테스트 | 8 | 커버리지 측정 없음. 릴리즈 급 슈트가 `npm test` 밖에 분산 |

## 2. 목표

동작(권한 정책·MCP 툴 9개·스키마·상태 기계·출력 형식)을 바꾸지 않고, 위 여섯 항목을 모두 8점 이상으로 올린다.

## 3. 고정 원칙

- 런타임 `dependencies`는 계속 0개다. 도구는 `devDependencies`에만 들어간다.
- `.shipping/` 런타임 파일은 `release prepare` 외의 방법으로 수정하지 않는다.
- MCP 툴 이름·입력 스키마·출력 필드, CLI 명령·옵션·종료 코드, 모든 `schemas/v1` 스키마는 바이트 단위로 동일하게 유지한다. 리팩터링은 기존 테스트 193개와 릴리즈 슈트가 안전망이다.
- 사람 정지·계약·증거·Judge 순의 권한 순서와 안전 경계(`docs/HANDOVER.md`)는 손대지 않는다.
- 새 파일은 ESM `.mjs`, `node:` 접두 builtin, JSDoc 타입을 따른다.
- 커밋은 단계별로 하나 이상 남기되, `lock`·`close`·태그는 수행하지 않는다. 그것은 소유자의 승인 행위다.

## 4. 구현 단계

### Phase A — 릴리즈 준비와 정적 분석 도구

1. `node bin/shipping-harness.mjs release prepare --version 1.9.0 --goal "Repeatable engineering infrastructure: CI, static analysis, coverage, documentation restructure, and maintainability refactors without changing Shipping authority, MCP surface, or schemas"` 를 실행해 DRAFT를 만든다. `package.json` version을 `1.9.0`으로 올린다.
2. `.shipping/contract.yaml`의 acceptance를 아래로 교체한다(ID는 `AC-190nn`).
   - AC-19001 `npm run check` (lint, typecheck, build, test)
   - AC-19002 `npm run lint:eslint`
   - AC-19003 `npm run typecheck:tsc`
   - AC-19004 `npm run test:coverage` (임계값 포함)
   - AC-19005 `npm run release:verify`
   - AC-19006 `git diff --check`
3. `devDependencies`에 `eslint`(최신 10.x), `@eslint/js`, `globals`, `typescript`(최신 5.x), `@types/node`를 추가하고 `package-lock.json`을 커밋한다. `--ignore-scripts` 설치 관행을 유지한다.
4. `eslint.config.mjs`(flat config)를 추가한다. 대상은 `src/ bin/ scripts/ test/ packages/`. `@eslint/js` recommended + `no-unused-vars`(args: after-used, `_` 접두 허용), `no-empty`(빈 catch는 주석이 있을 때만 허용), `eqeqeq`, `prefer-const`, `no-var`, `no-implicit-globals`. 기존 자체 lint(탭·후행공백)는 `scripts/lint.mjs`에 그대로 두고 `npm run lint`가 둘 다 실행하게 한다.
5. `tsconfig.json`을 추가한다. `allowJs`, `checkJs`, `noEmit`, `strict: false`에서 시작하되 `noImplicitAny: false`, `strictNullChecks: true`, `module: NodeNext`, `target: ES2022`, `types: ["node"]`, include는 `src/**/*.mjs bin/**/*.mjs packages/**/*.mjs`. `npm run typecheck:tsc`는 `tsc -p tsconfig.json`. 기존 `scripts/typecheck.mjs`는 유지하고 `npm run typecheck`가 둘 다 실행하게 한다.
6. ESLint와 tsc가 보고하는 모든 오류를 고친다. 실제 버그로 판단되는 것은 테스트를 먼저 추가한다. tsc 오류가 300개를 넘으면 `strictNullChecks`를 끄고 그 사실을 이 문서 6장에 기록한다.
7. `scripts/security-check.mjs`는 `dependencies`만 검사하므로 그대로 두되, `devDependencies`가 `bin/`·`src/`·`packages/`에서 import되지 않는지 검사하는 규칙을 추가한다.
8. `.nvmrc`(`22`)와 `.editorconfig`(LF, 2 spaces, no trailing whitespace, final newline)를 추가한다.
9. `npm test`에 `--experimental-test-coverage`를 붙인 `npm run test:coverage`를 추가하고, `scripts/run-tests.mjs`가 `--coverage` 인자를 받으면 라인 커버리지 임계값(초기값: 현재 측정치에서 2%p 낮춘 값, 정수)을 `--test-coverage-lines`로 강제하게 한다. 측정치를 이 문서 6장에 기록한다.
10. `../dev-wiki/decisions/2026-09-12-shipping-harness-정적분석-CI-도입.md`에 ADR을 쓴다(커밋하지 않는다). 내용: 런타임 의존성 0을 유지하면서 devDependencies로 ESLint·tsc를 도입하는 결정, 대안(자체 스크립트 유지), 결과.

### Phase B — 코드 구조와 유지보수성

1. `src/mcp/tools.mjs`의 `callShippingTool`을 툴 이름 → 핸들러 맵으로 분해한다. 핸들러는 `src/mcp/handlers/<tool>.mjs` 또는 `src/mcp/handlers.mjs` 하나에 두고, `SHIPPING_TOOLS` 정의는 그대로 둔다. 공통 전처리(인자 검증·권한 확인·오류 정규화)는 한 곳에 남긴다. 목표: 어떤 함수도 80줄을 넘지 않는다.
2. `src/cli.mjs`의 if 체인을 `command → handler` 테이블로 바꾼다. `main(argv)` 시그니처, `handleCliError`, 종료 코드, `renderHelp` 출력은 동일해야 한다.
3. `src/core/proposals.mjs`의 `refineScopeProposal`·`createScopeProposal`·`approveScopeProposal`을 검증/계산/기록 단계로 분해한다. 80줄 목표.
4. `catch {}` 및 `catch (…) {}` 24곳을 전수 조사해 (a) 의도적 무시면 한 줄 주석으로 이유를 남기고, (b) 오류를 알아야 하는 곳이면 `ShippingError`로 변환하거나 진단 필드에 기록한다. 결과 표를 이 문서 6장에 남긴다.
5. `release:verify`의 `npm run` 21개 체인을 `scripts/release-verify.mjs` 하나로 옮긴다. 각 단계를 이름·명령·소요 시간·결과로 기록하고, 독립 단계는 CPU 수만큼 병렬 실행하며, 끝에 실패 요약을 출력한다. `npm run release:verify`는 이 스크립트를 호출한다. `--list`로 단계 목록만 출력하는 옵션을 둔다.
6. `scripts/` 중 특정 버전 작업에만 쓰였고 어떤 npm script·테스트·doc audit에서도 참조되지 않는 파일(`amend-v09-packaging-scope.mjs`, `omo-amend-v07-contract.mjs`, `v1-amend-plugin-test-scope.mjs`, `omo-v0.7-gate.mjs`, `evoharvest-intelligence-pilot.mjs` 등 실제 grep으로 확인)을 `scripts/archive/`로 옮기고 `scripts/archive/README.md`에 각 파일이 어느 버전에 쓰였는지 적는다. `package.json` `files`와 lint 대상에서 제외한다.
7. `scripts/v1-doc-audit.mjs`의 하드코딩 `required` 목록을 (a) 항상 필요한 핵심 문서 목록(README, BACKLOG, HANDOVER 등)과 (b) `docs/planning/*.md`·`schemas/v1/*.schema.json`·`schemas/v1/examples/*.example.json`·`docs/reports/*.json` 디렉터리 스캔으로 나눈다. 스캔 규칙: 모든 스키마에 예제가 있어야 하고, 계획 문서 번호가 연속이어야 한다. 기존에 검사하던 필드 리포트 검증 로직은 유지한다.
8. export 함수 중 JSDoc이 없는 119개에 `@param`·`@returns`를 채운다. tsc가 이를 타입으로 쓴다.

### Phase C — 문서 구조

1. `CHANGELOG.md`를 새로 만들고 README의 `## Version boundaries` 아래 버전 섹션 23개와 `docs/MCP.md` 하단의 버전별 섹션(v0.9, v1.7.0, v1.8.1 등)을 여기로 옮긴다. Keep a Changelog 형식, 최신 버전이 위.
2. README를 다음 구조로 재작성한다(120줄 이하): 한 문장 정의 → 왜 필요한가(현재 Why 축약) → 핵심 보장 → 설치(한 가지 권장 경로 + 나머지는 링크) → 5분 사용(CLI와 MCP 각각) → 릴리즈 흐름 그림 → 안전 경계 → 문서 지도(문서를 역할별로 묶은 표: 시작/운영/설계/계획/보고) → 라이선스. 버전 표기는 한 곳만 두고 `package.json`과 같아야 한다.
3. `scripts/v1-doc-audit.mjs`에 규칙을 추가한다. README와 `docs/HANDOVER.md`에 나타나는 `Current release train`·`v1.x.y` 헤더 버전이 `package.json` version과 같아야 한다. CHANGELOG의 최상단 항목 버전도 같아야 한다.
4. `docs/MCP.md`를 버전 누적 없이 현재 동작 기준으로 재구성한다. 버전 이력은 CHANGELOG로 보낸다. 툴 9개의 이름·목적·입력·전제 상태·결과를 표 하나로 정리한다.
5. 설치 문서를 `docs/operations/INSTALL-UPGRADE-ROLLBACK.md` 하나로 모은다. 권장 경로는 "태그된 커밋에서 `npm pack` 후 `npm install --global --prefix ~/.local <tgz>`"이며, GitHub Release 첨부 tgz 설치를 향후 경로로 적는다(실제 Release 생성은 이 버전 범위 밖).
6. `AGENTS.md`에 "버전 하나를 처음부터 끝까지 닫는 실습 절차" 섹션을 추가한다. `release prepare`부터 태그까지 실제 명령과 각 단계에서 확인할 파일을 적는다.
7. 한/영 혼용은 다음 규칙으로 정리한다. 코드 주석·스키마·CLI 출력은 영어. `docs/planning`은 한국어 유지. README·MCP·HANDOVER는 영어 유지, `docs/BEGINNER-QUICKSTART-KO.md`가 한국어 진입점. 이 규칙을 AGENTS.md에 적는다.

### Phase D — CI

1. `.github/workflows/ci.yml`: push와 pull_request에서 Node 22와 24 매트릭스로 `npm ci --ignore-scripts`, `npm run check`, `npm run lint:eslint`, `npm run typecheck:tsc`, `npm run test:coverage`, `npm run security`, `npm run license:check`를 실행한다. `git diff --check`도 포함한다.
2. `.github/workflows/release-verify.yml`: `workflow_dispatch`와 태그 push(`v*`)에서 Node 22로 `npm run release:verify`를 실행하고 `dist/BUILD-MANIFEST.json`을 아티팩트로 올린다.
3. 두 워크플로 모두 `permissions: contents: read`, 타임아웃 20분, 캐시는 `actions/setup-node`의 npm 캐시만 쓴다. 외부 액션은 `actions/checkout`과 `actions/setup-node`만 허용하고 메이저 버전으로 고정한다.
4. README 상단에 CI 배지를 넣는다. 원격 저장소 URL은 `git remote get-url origin`으로 확인하고, 원격이 없으면 배지를 생략하고 그 사실을 6장에 적는다.

## 5. 완료조건

- `npm run check`, `npm run lint:eslint`, `npm run typecheck:tsc`, `npm run test:coverage`, `npm run release:verify`, `git diff --check`가 모두 통과한다.
- `src/`·`packages/`에 80줄을 넘는 함수가 없다(`scripts/lint.mjs`에 함수 길이 검사를 추가해 강제한다. 기존 위반이 남으면 허용 목록에 넣고 6장에 적는다).
- MCP 툴 9개의 `SHIPPING_TOOLS` JSON, `schemas/v1/**`, `renderHelp()` 출력이 v1.8.2와 바이트 단위로 같다(테스트로 고정한다: `test/stable/surface-freeze.test.mjs`가 해시를 비교한다).
- README 120줄 이하, 버전 표기가 `package.json`과 일치하고 doc audit이 이를 검사한다.
- `.shipping/state.json`은 `DRAFT`·release `1.9.0`이며 lock·close·태그는 수행되지 않았다.
- 런타임 `dependencies`는 0개다.

## 6. 실행 기록

### Phase A

- **devDependencies 설치**: `eslint@^10.10.0`, `@eslint/js@^10.0.1`, `globals@^17.12.0`,
  `typescript@^5.9.3`, `@types/node@^22.20.2`를 `npm install --save-dev --ignore-scripts`로
  설치했다. `package.json` `dependencies` 필드는 여전히 없음(0개).
- **ESLint**: `eslint.config.mjs`(flat config)를 신설했다. 대상 `src/ bin/ scripts/ test/
  packages/`, ignore `node_modules/ dist/ scripts/archive/`. 초기 오류 **31건** → 수정 후
  **0건**(`npm run lint:eslint`). 오류는 대부분 미사용 import/변수, `let x = <초기값>`
  뒤 항상 재할당되는 무의미한 초기값(`no-useless-assignment`), 이유 주석 없는 빈 catch,
  불필요한 정규식 이스케이프였다. 실질적 동작 변경 없이 죽은 코드 제거·주석 추가·
  이스케이프 정리로 해결했다(`src/core/proposals.mjs`의 제어문자 제거 정규식만
  `eslint-disable-next-line no-control-regex` 예외 처리 — 의도된 보안 sanitize이므로).
- **tsc**: `tsconfig.json` 신설(`allowJs`+`checkJs`+`noEmit`, `strict:false`,
  `noImplicitAny:false`, **`strictNullChecks:true` 유지** — 초기 오류가 300개 미만이라
  끄지 않았다). 초기 오류 **237건** → 수정 후 **0건**(`npm run typecheck:tsc`).
  - 가장 큰 단일 원인(약 60여 건)은 `invariant(condition, code, message)` 계열 어서션
    헬퍼(`src/core/errors.mjs`, `packages/internal-remote/policy.mjs`,
    `packages/omp-main-harness/io.mjs`, `packages/stable-control/errors.mjs`)에 JSDoc
    `@returns {asserts condition}`가 없어 `possibly null/undefined` 오류가 연쇄된 것이었다.
    네 곳 모두에 어서션 시그니처를 추가해 대부분 해소했다.
  - 나머지는 개별 함수의 JSDoc `@param`/`@returns` 누락 또는 부정확(예: `Record<string,
    any>`를 스프레드하면 인덱스 시그니처가 사라지는 TS의 알려진 동작, `let x = []`
    형태의 빈 배열/객체 리터럴이 `never[]`/`{}`로 굳어지는 추론, `new Error()`에 임의
    속성을 붙일 때 타입 캐스트 누락)였다. 모두 타입 주석만 보강했고 런타임 동작은
    바꾸지 않았다. 유일하게 로직을 만졌던 곳(`packages/shipping-plugin/installer/cli.mjs`의
    `--host` 처리)은 되돌렸다 — 처음에는 알 수 없는 host 값을 `'generic'`으로 조용히
    강제하도록 고쳤으나, 이는 `plan.mjs`가 런타임에 `ERR_PLUGIN_HOST`로 명시적으로
    거부하던 것과 동작이 달라져 되돌리고 타입만 `string`으로 넓혔다.
  - `npm test`(193개) 전부 통과 상태를 유지했다(회귀 없음).
- **devDependency 런타임 유입 방지**: `scripts/security-check.mjs`에 `bin/`·`src/`·
  `packages/`의 모든 import 지정자를 스캔해 `package.json` `devDependencies` 이름과
  겹치면 실패시키는 규칙을 추가했다.
- **`.nvmrc`**(`22`), **`.editorconfig`**(LF, space 2, 최종 개행, 후행공백 제거;
  `.md`는 후행공백 규칙 예외)를 신설했다.
- **커버리지**: `node --test --experimental-test-coverage`로 전체 스위트(`test/unit`

  통과한다(exit 0).
