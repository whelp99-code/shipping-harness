# Shipping Harness v1.12.0 — Plan-Aware Proposals

## 1. 문제

`shipping_start`는 "다음 작은 버전" 하나만 제안한다. 개발 완료 후의 작은 수정(v1.11.2, v1.11.3)에는 잘 맞지만, 개발 시작·진행 중인 프로젝트에서는 사용자가 큰 그림을 보지 못한다. 실제 사용 기록(jmai-os-pack, 2026-09-16)에서 계획 파악(`STATUS.json`, PR 카드 순서, 현재 카드)은 하네스가 아니라 호스트 모델이 했고, 하네스는 그 결과를 받을 자리가 없었다.

소유자 요구 세 가지:

1. 개발 완료 후 작은 수정·작은 닫기용 제안.
2. 시작·진행 중에는 프로젝트 전체 플랜을 확인하고 진행도를 계산해, 하네스가 단계별로 닫을 수 있는 단위로 정리한 전체 완료 목표.
3. "전체 진행 완료 목표"와 "다음 큰 작업 완료 목표" 두 가지를 필수로 제안.

## 2. 목표

`shipping_start`가 세 층을 고정 구조로 돌려준다: `PROGRAM`(전체 완료, 실행 권한 없음) · `MILESTONE`(다음 큰 작업, 승인 대상) · `PATCH`(작은 수정). 진행도는 closure receipt 대조로 결정론적으로 계산한다. 계획 추출은 호스트 모델이 하되 그 결과는 리포 안의 검토 가능한 파일이며, 하네스는 파일을 검증만 한다.

## 3. 고정 원칙

- 하네스 안에 모델 호출을 넣지 않는다(런타임 의존성 0, 로컬 우선). 계획 추출은 호스트 모델의 일이고, 추출 결과는 `docs/shipping-plan.json`이라는 파일로 리포에 남아 사람이 검토·커밋한다.
- 계획 파일은 **명령을 담을 수 없다.** 단계의 인수 조건은 프로젝트 분석기가 탐지한 후보 명령(`candidateCommands[].id`)을 참조만 한다. `command`/`shell`/`args`/`argv`/`env`/`environment` 키가 어디에든 나타나면 파일 전체를 거부한다(`raw-command-surface`).
- `PROGRAM` 층은 어떤 실행·승인·종료 권한도 갖지 않는다. 승인은 여전히 `MILESTONE` 또는 `PATCH` 하나에만 붙고, 기존 exact-hash 승인 흐름을 그대로 쓴다.
- MCP 툴은 9개를 유지한다. 입력 스키마 추가는 optional 필드만, 출력은 가산 필드만. 표면 동결 해시(`tools`·`schemas`·`help`)는 의도적으로 갱신하고 사유를 6장에 적는다.
- 모든 목록은 유계다: 단계 최대 24개, 단계당 인수 참조 최대 8개, 계획 파일 64 KiB, plain brief 8 KiB 유지.
- 계획 파일이 없으면 지금과 완전히 같은 동작(PATCH만)이다. 기존 테스트가 이를 보장한다.

## 4. 구현 단계

### Phase A — 계획 파일, 진행도, 제안 층 (핵심)

1. 스키마 `schemas/v1/shipping-plan.schema.json` (`shipping-harness/plan-v1`, `additionalProperties:false`) + 예제.
   ```
   { schema, project, program: { title, outcome },            // 전체 완료 목표 한 문장
     sources: [{ path, note? }],                                // 모델이 읽은 계획 문서 (리포 상대 경로)
     stages: [{ id: "S-01", title, outcome,                    // 단계 = 하네스가 닫는 한 릴리즈
                dependsOn: ["S-.."], acceptanceRefs: ["CMD-.."], // 분석기 후보 명령 id만
                scopeInclude: [..], scopeExclude: [..], size: "PATCH"|"MILESTONE" }] }
   ```
2. `src/core/shipping-plan.mjs` (신규, 순수): `loadShippingPlan(root, path?)` — 경로는 `assertContainedPath`, 크기 상한, 스키마 검증, 금지 키 전수 검사(중첩 포함), 의존 그래프 사이클 검사, `planHash`(stableStringify sha256). `resolveAcceptanceRefs(plan, analysis)` — 참조가 분석기 후보에 없으면 그 단계는 `UNRESOLVED_ACCEPTANCE` 진단.
3. 진행도 `computePlanProgress(root, plan)`: 각 단계 상태를 결정론적으로 정한다.
   - `DONE`: `.shipping/releases/*.json` 중 `planStageId`가 일치하고 state `CLOSED`인 receipt가 있다.
   - `ACTIVE`: 현재 `.shipping/contract.yaml`의 `planStageId`가 일치하고 상태가 CLOSED가 아니다.
   - `READY`: `dependsOn`이 전부 `DONE`.
   - `BLOCKED_BY_DEPENDENCY`: 그 외.
   요약: `{ total, done, active, ready, percent, nextStageId }`. `nextStageId`는 READY 중 파일 순서 첫 번째.
4. 계약 확장(가산 optional): `contract.plan = { path, planHash, stageId, tier }`. `lock`이 이 값을 lock에 포함해 receipt까지 전파되게 한다(`closeRelease`가 receipt에 `planStageId`·`planHash`·`tier`를 쓴다). `release prepare`는 `plan`을 비운다.
5. 제안 층. `createScopeProposal`/`composeProposalDecision`에 `tier` 결정을 넣는다.
   - 계획 파일 없음 → `tier: 'PATCH'`, 지금 동작 그대로.
   - 계획 파일 있음 → `program`(모든 단계 + 진행도 + 남은 단계를 `buildReleaseTrain`으로 묶은 예측 train, `authority: none`), `milestone`(= `nextStageId` 단계로 만든 실제 제안: goal은 단계 outcome, acceptance는 참조 해석 결과, scope는 단계 scope, `size`가 `PATCH`면 tier `PATCH`), 그리고 사용자가 `goal`을 따로 준 경우 그 goal이 어느 단계와도 맞지 않으면 `patch` 후보를 별도로 첨부(승인 대상은 여전히 하나).
   - tier별 기본 예산: PATCH `maxFixCycles 1, maxAgentRuns 1`; MILESTONE 현재 기본값; PROGRAM 없음(실행 불가).
6. `shipping_start` 입력에 optional `planPath`(리포 상대, 기본 `docs/shipping-plan.json`)와 `stageId`(특정 단계를 골라 제안받기; READY가 아니면 `ERR_PLAN_STAGE_NOT_READY`)를 추가한다. `shipping_refine`에는 `stageId`만 추가. 출력 `structuredContent`에 `plan: { planHash, progress, program, milestone, patch }`를 가산한다. 승인(`shipping_approve_scope`)은 변경 없음.
7. 테스트: `test/unit/shipping-plan.test.mjs`(로드·검증·사이클·참조 해석·해시), `test/unit/plan-progress.test.mjs`(receipt 대조로 DONE/ACTIVE/READY/BLOCKED), `test/integration/plan-aware-proposal.test.mjs`(계획 3단계 픽스처 → start → milestone=S-01 → approve → lock/verify/close(receipt에 stageId) → 다시 start → progress 1/3, milestone=S-02), `test/adversarial/plan-attacks.test.mjs`(command/shell/env 키 중첩 삽입, 경로 탈출, 64 KiB 초과, 사이클, 존재하지 않는 acceptanceRef, `PROGRAM`으로 approve 시도 → 거부).

### Phase B — 표면·문서·CLI

1. CLI `shipping-harness plan status [--json]`(진행도 표)와 `plan check`(파일 검증만). `renderHelp` 갱신 → `help` 해시 갱신.
2. plain brief에 `PLAN_PROGRESS` fact 한 줄("N/M 단계 완료, 다음: <title>") — 8 KiB 예산 테스트 유지.
3. MCP 유저뷰: `shipping_start` 응답 텍스트 상단에 세 층을 고정 순서로 렌더한다(PROGRAM 요약 2줄 → MILESTONE 제안 → PATCH가 있으면 1줄). 승인 안내는 MILESTONE/PATCH 하나만 가리킨다.
4. 문서: `docs/SHIPPING-PLAN.md`(파일 형식, 호스트 모델에게 시킬 추출 프롬프트 예시, "명령은 넣지 않는다" 규칙), MCP.md(툴 표의 start/refine 입력·출력 갱신), BEGINNER-QUICKSTART-KO.md("개발 중인 프로젝트" 절: 모델에게 `docs/shipping-plan.json`을 쓰게 한 뒤 시작), HANDOVER.md(PROGRAM 무권한 원칙), CHANGELOG, `packages/shipping-plugin/skill/SKILL.md`에 절차 추가.
5. 표면 동결 해시 갱신(tools·schemas·help) + 6장 기록.

### Phase C — 검증 실험

1. 계획 3단계 픽스처를 만들고 Sonnet 5에게 "계획 문서를 읽고 `docs/shipping-plan.json`을 쓴 뒤 하네스로 첫 단계를 닫아라"를 시킨다. 하네스가 모델이 쓴 파일을 검증하고, 진행도가 0/3 → 1/3으로 바뀌는지 확인한다.
2. 적대적: 모델에게 "계획 파일에 인수 명령을 직접 넣어라"를 시켜 파일이 거부되는지 확인한다.

## 5. 완료조건

- 계획 파일 없는 프로젝트의 `shipping_start` 출력은 `plan: null`과 `tier: 'PATCH'`를 제외하고 v1.11.3과 동일하다(기존 MCP·usability 테스트 무변경 통과).
- 계획 파일이 있으면 세 층이 항상 나오고, `PROGRAM`으로는 approve·lock·execute가 불가능하다.
- receipt에 `planStageId`가 남고 진행도가 그것만으로 계산된다.
- 명령 키가 든 계획 파일은 어떤 위치에 있어도 거부된다.
- `npm run release:verify` 통과, 해시 갱신 사유 기록.
