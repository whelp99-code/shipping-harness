# Shipping Harness v1.12.1 — Plan File Update Rules

## 1. 문제

v1.12.0의 계획 파일(`docs/shipping-plan.json`)은 검증과 진행도 계산은 하지만 **갱신**에 대한 규칙이 없다. 프로젝트에 이미 계획 파일이 있을 때 호스트 모델이 "계획 파일을 써라"는 지시로 덮어쓰면 단계 id가 바뀌고, 진행도는 receipt의 `planStageId`로만 계산되므로 닫힌 단계가 0으로 되돌아간다. 원본 계획 문서가 바뀌어도 계획 파일이 낡았다는 신호가 없다.

## 2. 갱신의 정의 (소유자와 합의, 2026-09-16)

계획 파일은 **증거가 붙은 부분은 불변, 증거가 없는 부분만 가변**인 문서다. 증거 = 그 단계의 CLOSED receipt 또는 현재 잠긴 계약.

| 단계 상태 | 근거 | id | 제목·outcome·scope·acceptanceRefs·size | dependsOn | 삭제 |
|---|---|---|---|---|---|
| DONE | CLOSED receipt에 `planStageId` | 불변 | 불변 | 불변 | 불가 |
| ACTIVE | 현재 계약 `plan.stageId` | 불변 | 불변 | 불변 | 불가 |
| 미착수 (READY·BLOCKED) | 없음 | 가변 | 자유 | 자유(사이클 금지) | 가능 |

- 새 단계 추가는 항상 가능. 단 DONE·ACTIVE 단계의 `dependsOn`에 새 항목을 넣는 것은 과거 재작성이므로 거부.
- 갱신은 같은 경로의 파일을 고쳐 쓰는 것이다. 경로는 `docs/shipping-plan.json` 하나로 고정하며 `--plan`/`planPath`로 다른 경로를 주면 거부한다(`ERR_PLAN_PATH_FIXED`).
- 방향은 항상 원본 문서 → 계획 파일. 하네스가 원본을 고치는 일은 없다.
- 닫힌 단계를 바꿔야 한다면 갱신이 아니라 새 계획이다: `program.supersedes = <이전 planHash>`를 명시해야 하며, 하네스는 "이전 계획의 완료 단계 N개가 계승되지 않음"을 보고하고 진행도를 새 계획 기준으로 다시 센다.

## 3. 고정 원칙

- 모든 검사는 결정론적이며 receipt·계약·파일 해시만 본다. 모델 판단은 입력이 아니다.
- 스키마는 가산만(`revision`, `sources[].sha256`, `program.supersedes`, receipt `planStage` 스냅샷). `additionalProperties:false` 유지. 표면 동결 해시(`schemas`, 필요시 `help`) 갱신과 사유 기록.
- v1.12.0에서 만든 계획 파일(`revision`·해시 없음)은 계속 읽히며, 첫 갱신 때 `revision: 1`과 해시를 채우도록 경고한다(`PLAN_LEGACY_FORMAT`). 차단하지 않는다.

## 4. 구현 단계

### Phase A — 스냅샷과 검사 (핵심)

1. `closeRelease`가 receipt에 `planStage: { id, title, outcome, dependsOn, acceptanceRefs, scopeInclude, scopeExclude, size }` 스냅샷을 쓴다(계약에 `plan`이 있을 때). `release.schema.json` 가산.
2. `lock`이 lock 파일에 같은 스냅샷을 쓴다(ACTIVE 단계의 불변 근거). `lock.schema.json` 가산.
3. `src/core/shipping-plan.mjs`에 `auditPlanHistory(root, plan)` 추가: receipt와 현재 lock에서 DONE·ACTIVE 단계 스냅샷을 모아 파일과 대조한다. 결과 `{ ok, violations: [{ stageId, kind: 'MISSING'|'CHANGED'|'DEPENDS_ON_REWRITTEN', field?, expected, observed, evidence }] }`. 위반이 있으면 `ERR_PLAN_HISTORY_LOST`를 던지는 `assertPlanHistory`.
4. `loadShippingPlan`·`shipping_start`·`shipping_refine`·`lock`·`plan check`·`plan status`가 `assertPlanHistory`를 거친다. `plan status`와 `plan check`는 던지지 않고 위반을 출력하며 exit 1.
5. `program.supersedes`가 현재 receipt들의 `planHash` 중 하나와 일치하면 이력 검사를 건너뛰고 `PLAN_SUPERSEDED` 진단(계승되지 않은 완료 단계 수 포함)을 붙인다. 일치하지 않으면 `ERR_PLAN_SUPERSEDES_UNKNOWN`.
6. `planPath`가 기본값과 다르면 `ERR_PLAN_PATH_FIXED`. MCP 입력의 `planPath`는 스키마에서 제거하지 않고(툴 해시 유지) 값이 기본값이 아니면 거부한다.

### Phase B — 드리프트와 이력

1. `sources[].sha256`(optional). 있으면 현재 파일 해시와 비교해 다르면 `PLAN_SOURCE_DRIFT` 경고(경로별). `plan status`·제안·plain brief에 노출. 차단 없음. 원본 파일이 없으면 `PLAN_SOURCE_MISSING` 경고.
2. `revision`(양의 정수, optional). `.shipping/plan-history.jsonl`에 `{ at, revision, planHash, previousPlanHash, changedStages: {added, modified, removed}, sourceDrift }`를 append한다. 기록 시점은 `plan check`·`shipping_start`·`lock`이 새 `planHash`를 처음 볼 때. `revision`이 직전 기록보다 작으면 `ERR_PLAN_REVISION_REGRESSED`. 같은 revision에 다른 해시면 `ERR_PLAN_REVISION_REUSED`. 이력 파일은 append-only이며 Phase A의 상태 무결성 체인과 같은 `prev`/`digest`를 쓴다.
3. `plan check --json`에 `history: { lastRevision, lastPlanHash, entries }`와 `sourceDrift` 포함. `plan status` 텍스트에 드리프트 경고 줄.

### Phase C — 문서와 프롬프트

1. `docs/SHIPPING-PLAN.md`: "갱신의 정의" 표를 그대로 싣고, 모델용 프롬프트를 "있으면 먼저 `plan check --json`으로 닫힌 단계를 확인하고, 닫힌·진행 중 단계는 한 글자도 바꾸지 말며, 원본 변경은 미착수 단계 수정이나 새 단계 추가로만 반영하고, `revision`을 1 올리고 `sources[].sha256`을 다시 계산하라"로 교체.
2. `docs/MCP.md`, `docs/BEGINNER-QUICKSTART-KO.md`, `packages/shipping-plugin/skill/SKILL.md`, HANDOVER(불변 규칙 한 줄), CHANGELOG.

### Phase D — 검증 실험

1. v1.12.0 실험 픽스처(3단계, S-01 닫힘)를 재현한 뒤 Sonnet 5에게 "로드맵이 바뀌었다(4단계 추가, 2단계 이름 변경). 계획 파일을 갱신하라"를 시킨다. 기대: S-01 불변, S-02 수정, S-04 추가, revision 2, 이력 1건.
2. Haiku 4.5에게 "계획 파일을 처음부터 다시 써라(id를 stage-1 형식으로)"를 시킨다. 기대: `ERR_PLAN_HISTORY_LOST`로 거부, 진행도 유지.

## 5. 완료조건

- 닫힌·진행 중 단계의 id·내용·dependsOn 변경과 삭제가 모두 거부되고, 미착수 단계 변경과 새 단계 추가는 허용된다(테스트로 각각 고정).
- v1.12.0 형식 파일은 경고만 받고 계속 동작한다.
- receipt와 lock에 단계 스냅샷이 남고, 이력 파일이 append-only 체인으로 유지된다.
- `npm run release:verify` 통과, 해시 갱신 사유 기록.

## 6. 실행 기록

### Phase A

구현 범위: 4장 Phase A 1~6단계 + 테스트. Phase B(`revision`·`sources[].sha256`·`.shipping/plan-history.jsonl`)와 Phase C 문서는 손대지 않았다. `.shipping/contract.yaml` AC-112101이 지목하는 `test/unit/plan-revision.test.mjs`는 Phase B 산출물이므로 만들지 않았다 — AC-112101은 Phase B가 그 파일을 추가할 때 비로소 그대로 통과한다.

스냅샷(2장 표의 "증거")
- `src/core/contract.mjs`: `lockContract`가 계약에 `plan`이 있으면 계획 파일에서 그 단계를 읽어 lock에 `planStage: { id, title, outcome, dependsOn, acceptanceRefs, scopeInclude, scopeExclude, size }`를 쓴다. 이때 계획 파일도 함께 감사하므로, 이미 닫힌 receipt와 모순되는 파일 위에서는 lock 자체가 성립하지 않는다.
- `src/core/gate.mjs`: `closeRelease`가 같은 스냅샷을 receipt에 쓴다. 닫는 시점에 파일이 없거나 깨졌거나 그 단계를 더 이상 정의하지 않으면 `ERR_PLAN_UNAVAILABLE_AT_CLOSE`로 닫기를 거부한다 — 단계는 자기 정의 없이 닫힐 수 없다. 이력 위반은 `ERR_PLAN_HISTORY_LOST` 그대로 전파한다.

검사(`src/core/shipping-plan.mjs`)
- `auditPlanHistory(root, plan)`: 모든 CLOSED receipt(`planStageId` 보유)와 현재 lock(상태가 CLOSED가 아닐 때만 — 닫힌 뒤에는 receipt가 증거이고 남은 lock은 낡은 사본이다)에서 스냅샷을 모아 파일과 대조한다. 단계가 사라졌으면 `MISSING`, 스냅샷 필드가 다르면 `CHANGED`(field·expected·observed), `dependsOn`이 다르면 `DEPENDS_ON_REWRITTEN`. 반환은 `{ ok, violations, protectedStageIds }`이고 각 위반은 근거 경로(receipt 또는 `.shipping/contract.lock`)를 달고 다닌다. v1.12.0 receipt는 `planStage`가 없으므로 단계 id만 고정된다(경고 없이 계속 동작, 3장 규칙).
- `assertPlanHistory`는 `ShippingError('ERR_PLAN_HISTORY_LOST', …, { violations })`를 던진다. 메시지는 `Plan file rewrites stages that already carry evidence: <stageId> <KIND>[ <field>] (<evidence>); …`(최대 12건).

배선
- `loadShippingPlan(root, path, { auditHistory: true })`가 단일 관문이다. `shipping_start`/`shipping_refine`(`proposals.mjs` → `plan-proposal.mjs`), `lock`, `close`, CLI `plan status`/`plan check`가 모두 이 경로를 쓴다.
- `proposals.mjs`의 PATCH 강등 규칙을 고쳤다: `ERR_PLAN_HISTORY_LOST`·`ERR_PLAN_SUPERSEDES_UNKNOWN`·`ERR_PLAN_PATH_FIXED`는 강등되지 않고 요청 자체를 거부한다. 코드 주석에 사유를 남겼다 — **깨진 파일은 권한이 없으므로 PATCH로 내려가도 잃는 것이 없지만, 다시 쓴 파일은 이미 존재하는 증거를 고쳐 쓰려는 시도이므로 PATCH-with-diagnostic으로 내려보내면 그 재작성이 그대로 인정되고 그 위에서 계속 제안이 나온다.**
- CLI `plan status`/`plan check`는 위반을 `VIOLATION: <stageId> <KIND>[ <field>] (evidence: <path>)` 줄로 출력하고 exit 1 한다(스택 없음). `--json`이면 `{ ok:false, error:{ code, message, details.violations } }`. `plan check`는 정상 시 `protectedStageIds`(증거가 붙어 불변인 단계)를 추가로 출력한다.
- MCP는 `ShippingError` → tool error 경로 그대로다.

`program.supersedes`(가산, optional sha256)
- 값이 CLOSED receipt 중 하나의 `planHash`와 일치하면 이력 검사를 건너뛰고, 진행도는 **새 계획 해시와 같은 `planHash`를 가진 receipt만** 세어 0부터 다시 시작하며, 진단 `PLAN_SUPERSEDED: <n> completed stages from plan <hash8> are not inherited`를 붙인다(`computePlanProgress(root, plan, { planHash })` 가산). 어느 receipt와도 일치하지 않으면 `ERR_PLAN_SUPERSEDES_UNKNOWN`.

고정 경로
- `loadShippingPlan`이 `DEFAULT_PLAN_PATH`(`docs/shipping-plan.json`) 외의 값을 `ERR_PLAN_PATH_FIXED`로 거부한다. MCP `planPath`와 CLI `--plan` 입력은 그대로 두었으므로 `tools`·`help` 해시는 불변이고, 받아들이는 값만 좁아졌다. 기존 테스트 3개를 갱신했다: `test/unit/shipping-plan.test.mjs`(경로 거부 코드), `test/unit/plan-cli.test.mjs`(`--plan` 오버라이드 → 거부), `test/mcp/plan-tiers.test.mjs`·`test/adversarial/plan-attacks.test.mjs`(탈출 경로가 이제 `ERR_PLAN_PATH` 이전에 `ERR_PLAN_PATH_FIXED`로 막힌다).

테스트(신규 3개, 15건)
- `test/unit/plan-history.test.mjs`: 위반 종류별(MISSING·CHANGED·DEPENDS_ON_REWRITTEN), 미착수 단계 수정 허용, 새 단계 추가 허용, DONE 단계의 `dependsOn`에 새 단계를 넣으면 거부, lock이 ACTIVE 단계를 지키고 CLOSED 상태에서는 receipt가 그 역할을 인계, v1.12.0 receipt(스냅샷 없음)는 id만 고정, supersedes 수락/미상, 고정 경로.
- `test/integration/plan-update.test.mjs`: 실제 CLI로 계획 작성 → S-01 바인딩·lock → verify → close → receipt·lock 스냅샷 일치 확인 → S-02 자유 수정 + S-04 추가 → `plan check` 통과, 진행도 1/4 → S-01 제목 변경 → `plan check` exit 1 + `VIOLATION:` 줄 + `ERR_PLAN_HISTORY_LOST` → 복원 → 다시 통과. 그리고 계획 파일이 사라진 상태의 close가 `ERR_PLAN_UNAVAILABLE_AT_CLOSE`로 거부되는지.

### Phase B

구현 범위: 4장 Phase B 1~3단계 + `test/unit/plan-revision.test.mjs`(AC-112101이 지목하던 파일) + 기존 테스트 확장.

`sources[].sha256`(가산, `src/core/shipping-plan.mjs`)
- `validateSource`가 `sha256`(64자 소문자 hex)을 받는다. `loadShippingPlan` 내부의 새 `auditPlanSources(root, plan.sources)`가 해시가 있는 소스마다 `assertContainedPath` 경유로 파일을 읽어 `hashFile`(기존 `crypto.mjs`)로 비교한다: 다르면 `PLAN_SOURCE_DRIFT: <path> changed since the plan was written (plan <hash8>, now <hash8>)`, 파일이 없으면 `PLAN_SOURCE_MISSING: <path>`. 해시가 없는 소스가 하나라도 있으면(또는 `plan.revision`이 없으면) `PLAN_LEGACY_FORMAT: sources carry no sha256; set revision and source hashes on the next update`(또는 `revision`만 없을 때는 "plan carries no revision" 문구) 진단을 한 번만 붙인다. 전부 차단 없음. `loadShippingPlan`의 반환에 `sourceDrift: [{path, expected, observed}]`와 `legacyFormat: boolean`을 추가했다 — `diagnostics`(문자열)는 그대로 두어 기존 소비처(`plan-proposal.mjs`의 `binding.diagnostics` 스프레드, 즉 `shippingPlan.diagnostics`)가 코드 변경 없이 그대로 노출한다.
- `plan status`는 `PLAN_SOURCE_DRIFT`·`PLAN_SOURCE_MISSING`·`PLAN_LEGACY_FORMAT` 진단만 `WARNING: ` 접두를 붙여 출력하고(`PLAN_SUPERSEDED` 등 기존 진단은 그대로), `Revision: <n> (history entries: m)` 줄을 추가했다. `plan check --json`은 `sourceDrift`·`legacyFormat`·`history`를 추가했다.

`revision`과 `.shipping/plan-history.jsonl`(신규 `src/core/plan-history.mjs`)
- `runtimePaths`에 `planHistory` 경로 추가. 새 모듈은 `.shipping/ledger.jsonl`과 같은 체인 헬퍼(`state-integrity.mjs`의 `ledgerEventDigest`·`verifyLedgerChain`)를 그대로 재사용한다: 각 줄은 `{schema, id, at, revision, planHash, previousPlanHash, changedStages:{added,modified,removed}, sourceDrift:[path,...], stages:[{id,snapshot}], prev, digest}`.
- `readPlanHistory`는 체인을 검증하고 깨졌으면 `ERR_PLAN_HISTORY_TAMPERED`를 던진다(빈 파일은 빈 배열, 에러 아님).
