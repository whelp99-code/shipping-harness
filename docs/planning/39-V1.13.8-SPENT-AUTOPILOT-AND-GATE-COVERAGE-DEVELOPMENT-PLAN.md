# Shipping Harness v1.13.8 — 소진된 자동조종 정책과 게이트 커버리지

## 1. 문제

### 1.1 닫힌 릴리스에 묶인 정책이 영원히 "활성"이다

second-brain-app 워크트리에서 1.0.2 를 CLOSE 한 뒤 1.0.3 을 승인하려다 빠져나올 수
없는 상태가 보고되었다. 재현 경로는 이렇다.

1. 1.0.2 를 CLOSE 하면 `autopilot-state.phase` 가 `RELEASE_CLOSED` 가 된다. 정책 파일은
   그대로 남는다.
2. 새 제안으로 1.0.3 을 승인한다.
3. `approveManually` 가 **먼저** `approveScopeProposal` 을 호출해 상태를 LOCKED 로
   확정한다.
4. 그 다음 `activateAutopilot` 이 `ERR_AUTOPILOT_ACTIVE` 를 던진다. `TERMINAL_PHASES` 는
   `TRAIN_COMPLETE` 와 `ABORTED` 뿐이고 `RELEASE_CLOSED` 가 없기 때문이다.

결과는 출구가 없는 상태다. 재시도는 `ERR_APPROVAL_STATE`(이미 LOCKED), 검증은
`STALE_POLICY_BINDING`(계약 해시·베이스라인·트레인 해시·현재 릴리스가 모두 불일치),
연속성 경로는 새 트레인이라 성립하지 않는다. 두 개의 별개 결함이다.

- **A. 수명주기**: 닫힌 릴리스에 묶인 정책은 소진된 것이다. 아무것도 막아서는 안 된다.
- **B. 원자성**: 승인이 먼저 커밋되고 활성화가 나중에 실패하면 되돌릴 방법이 없다.

### 1.2 게이트가 돌리지 않는 테스트가 아홉 개 있었다

`npm test` 는 `unit`, `integration`, `adapter`, `mcp`, `adversarial` 다섯 루트만
걷는다. `release:verify` 의 17 스텝에는 `test:autopilot`, `test:usability`,
`test:omp-main` 이 없었고, `test/team-dag` 는 npm 스크립트조차 없었다. 즉 네 디렉터리
아홉 파일을 **아무도 돌리지 않았다**.

그 결과 v1.13.0 의 베이스라인 자동 커밋이 `test/autopilot/field-matrix.test.mjs` 를
깨뜨린 채 다섯 릴리스(v1.13.0 ~ v1.13.7)를 통과했다. 그동안 `release:verify` 는
매번 17/17 초록을 보고했다. 무엇을 안 돌리는지 모르는 게이트는 게이트가 아니다.

이것은 새로운 종류의 실수가 아니다. v1.12.0 단계에서 "release:verify 가 usability
스위트를 돌리지 않는다" 는 보고를 받고도 기록만 하고 고치지 않았다. `ERR_RELEASE_DRIFT`
를 "Gotcha" 로 문서에 적어 넣고 v1.13.7 까지 방치한 것과 같은 모양이다. 아는 구멍을
적어두는 것은 막는 것이 아니다.

### 1.3 게이트를 열자 드러난 것들

구멍을 막고 네 스위트를 실제로 돌리자 두 개가 더 나왔다.

- `npm pack --json` 은 npm 12 에서 배열이 아니라 패키지 이름 키 객체를 낸다. 다섯
  호출부가 모두 배열을 가정해 `Cannot read properties of undefined (reading
  'filename')` 로 죽는다. 스크립트 셋뿐 아니라 `packages/omp-main-harness/package.mjs`
  의 OMP 설치·백업 production 경로가 포함된다.
- `scripts/v1-final-smoke.mjs` 는 설치된 버전이 `1.0.0` 이기를 기대하는 리터럴을 그대로
  들고 있었다. 이 스크립트가 처음 쓰인 릴리스에 굳은 값이다.

### 1.4 그리고 1.1 을 고치자 드러난 잠복 결함

A 를 고쳐 소진된 정책의 교체를 허용하자, 교착이 사라진 것이 아니라 approve 에서
verify 로 **옮겨갔다**. `activateAutopilot` 이 `createEvent(null, …)` 로 원장 이벤트를
만들어 시퀀스를 1 로 되돌리기 때문이다. 자동조종 원장은 저장소 전체를 관통하는 단일
append-only 체인이라, 디스크에 `…#4, #1` 이 남고 이후 모든 읽기가
`ERR_AUTOPILOT_SEQUENCE` 로 죽는다. 재활성화가 애초에 거부되던 동안에는 이 경로에
닿을 수 없어 잠복해 있었다.

## 2. 목표

닫힌 릴리스에 묶인 정책은 소진된 것으로 다루고, 성공할 수 없는 활성화는 아무것도
잠그기 전에 거부하며, 모든 테스트 디렉터리는 게이트에서 닿거나 사유가 적힌 채
제외되게 한다.

## 3. 고정 원칙

- 변형을 끝낸 뒤 오류를 내지 않는다. 실패는 상태를 건드리기 전에 난다.
- 원장은 하나의 체인이다. 어떤 경로도 시퀀스를 되돌리지 않는다.
- 게이트에서 빠지는 것은 결정이다. 사유를 코드에 적지 않으면 빠질 수 없다.
- skip 은 숨기지 않는다. `release:verify` 가 WARNING 으로 드러낸다.

## 4. 구현 단계

### Phase A — 수명주기와 원자성 (1.1)

- `isSpentAutopilotBinding(root, boundRelease, currentRelease)`: 묶인 릴리스의 종료
  영수증이 있고 현재 릴리스와 다르면 소진. 영수증이 없으면 소진이 아니라 부실/변조이므로
  닫힌 채로 실패한다.
- `assertAutopilotActivatable(root, nextRelease)`: `approveManually` 가
  `approveScopeProposal` 보다 **먼저** 부른다. 실패 시 "nothing was approved or locked"
  를 알린다.
- `autopilotStatus` 가 `spent` 를 내고 `enabled` 를 `policy.enabled && !spent` 로 낸다.

### Phase B — 원장 연속성 (1.4)

- `activateAutopilot` 이 `createEvent(existingState ?? null, …)` 로 기존 체인에
  이어붙인다.

### Phase C — 게이트 커버리지 (1.2)

- `scripts/release-verify-steps.mjs` 로 `STEPS` 를 분리하고 `UNGATED_SUITES` /
  `UNGATED_SCRIPTS` 에 제외 사유를 적는다.
- 스텝 추가: `test:autopilot`, `test:usability`, `test:omp-main`, `test:team-dag`,
  `smoke:omp-main`, `verify:gate-coverage`. 17 → 23 스텝.
- `scripts/test-suite-coverage.mjs`: `test/<suite>/` 와 모든 `test:*`/`smoke:*` 스크립트가
  게이트에서 닿는지 감사하고, 낡은 제외 항목도 잡는다. `npm run` 간접과 `npm test` 축약을
  모두 따라간다.

### Phase D — 게이트가 드러낸 결함 (1.3)

- `src/core/npm-pack.mjs`: `normalizeNpmPackResult` / `singleNpmPackEntry` 가 두 형태를
  모두 받는다. 다섯 호출부를 여기로 보낸다.
- `scripts/v1-final-smoke.mjs`: 버전 리터럴을 `VERSION` 으로 바꾼다.
- `test/autopilot/field-matrix.test.mjs`: v1.13.0 에서 네 개가 받은
  `commitBaseline: false` 를 다섯 번째인 이 테스트에도 사유와 함께 적용한다.
- `test/team-dag/entry-gate.test.mjs`: 은퇴한 비공개 OMO 런타임이 없으면 실패가 아니라
  skip 한다. `test/omo/` 와 같은 관례다.

### Phase E — 테스트

- `test/autopilot/spent-policy-recovery.test.mjs`: 보고된 순서를 MCP 표면으로 끝까지
  재현한다. 두 주기 반복과 원장 연속성까지 본다.
- `test/unit/gate-coverage.test.mjs`: 감사가 v1.13.0 구멍을 **재현하는지** 본다. STEPS 를
  주입 가능하게 두지 않으면 감사가 자기 자신과만 합의한다.
- `test/unit/npm-pack.test.mjs`: 두 형태, 빈 결과, 다중 결과, filename 없는 항목.

## 6. 실행 기록

### Phase A — 수명주기와 원자성

`src/core/autopilot.mjs` 에 `isSpentAutopilotBinding` 과 `assertAutopilotActivatable` 을
더했고 `autopilotStatus` 가 `spent` 를 낸다. `src/mcp/handlers.mjs` 의 `approveManually`
가 `approveScopeProposal` 보다 먼저 활성화 가능성을 확인한다.

### Phase B — 원장 연속성

`activateAutopilot` 의 `createEvent(null, …)` 를 `createEvent(existingState ?? null, …)`
로 바꿨다. **이 결함은 격리된 단위 테스트가 아니라 보고된 순서를 끝까지 재현하는
테스트에서만 드러났다.** Phase A 만으로는 교착이 사라지지 않고 approve 에서 verify 로
옮겨갔다. 수정을 격리해서 검증하면 수정이 만든 새 경로를 보지 못한다.

### Phase C — 게이트 커버리지

스텝 17 → 23. `scripts/release-verify-steps.mjs` 가 `STEPS` 와 두 제외 기록을 갖는다.
`scripts/test-suite-coverage.mjs` 는 처음 돌렸을 때 `test/adapter` 를 미커버로
보고했는데, 감사 자신이 `npm test` 축약형(`npm run` 없는 형태)을 따라가지 못한
것이었다. 감사가 자기 결함을 먼저 잡았다.

`auditCoverage` 는 `STEPS` 를 주입받는다. 모듈 상수를 직접 읽게 두었을 때는 합성
입력으로 v1.13.0 구멍을 재현해도 "구멍 없음" 을 보고했다. 게이트를 검사하는 코드가
자기 자신과만 합의하면 아무것도 증명하지 못한다.

### Phase D — 게이트가 드러낸 결함

- `src/core/npm-pack.mjs` 신설, 다섯 호출부 교체. 이 머신의 `/usr/bin/npm` 은 npm 10
  이라 OMP 테스트는 옛 배열 형태만 밟고 있었다. 리포 자신의 `npm run` 은 npm 12 다.
- `packages/omp-main-harness` 의 `/usr/bin/npm` 하드코딩 네 곳을 `defaultNpmCommand()`
  로 바꿨다. 그 경로가 있으면 그대로 쓰므로 여기서는 동작이 바뀌지 않고, 없는 러너에서만
  PATH 로 내려간다. 이 결함도 `test:omp-main` 이 이번에 처음 게이트에 들어가며 드러났다.
- `scripts/v1-final-smoke.mjs` 의 `1.0.0` 리터럴 제거.
- `test/autopilot/field-matrix.test.mjs` 에 `commitBaseline: false`. 자동 커밋이 제품
  파일 내용을 바꾸지 않는다는 것은 직접 측정해서 확인했다. 작업 트리 바이트는 동일하고
  HEAD 만 앞으로 가며 새 커밋의 부모가 직전 HEAD 라 `git reset --soft HEAD~1` 로 정확히
  복원된다. 테스트가 비교하는 지문이 HEAD 를 포함할 뿐이다.
- `test/team-dag/entry-gate.test.mjs` 는 은퇴한 비공개 OMO 런타임이 없으면 skip 한다.

### Phase E — CI

`.github/workflows/ci.yml` 이 손으로 적은 부분집합 대신 `npm run release:verify` 를
돈다. PR 이 릴리스보다 약한 목록으로 통과하던 것은 게이트 구멍과 같은 결함이었다.
`release-verify.yml` 은 태그에서만 돌므로 PR 시점에는 아무 역할도 하지 못했다.

### 보고된 상태로 직접 검증 (2026-09-19)

수정본의 테스트는 **새로 승인하는** 경로만 덮는다. 보고된 워크트리는 수정본이 더는
만들지 못하는 상태다. 그래서 `800d01b` 로 워크트리를 만들어 그 상태를 실제로 재현했다.

```
approve 오류      : ERR_AUTOPILOT_ACTIVE - A different autopilot policy is already active
릴리스 상태       : LOCKED 1.0.3
autopilot 바인딩  : 1.0.2 / RELEASE_CLOSED
자동조종 원장     : #1 activated | #2 decision | #3 decision | #4 release-closed  (모두 1.0.2)
1.0.3 활성화 이벤트: 없음
```

그 고정물에 이 빌드를 그대로 붙인 결과:

```
shipping_status -> LOCKED 1.0.3 / autopilot enabled=false spent=true
shipping_verify -> decision=SHIPPABLE blockers=0
shipping_close  -> state=CLOSED released=false
원장             -> 5개 이벤트, 단절 0개, #5 human.release-closed rel=1.0.3
```

즉 복구 절차는 상태 조작 없이 **MCP 서버 재기동 → status → verify → close** 다. 종료
이벤트가 `human.` 접두사로 남는 것이 중요하다. 소진된 정책은 아무것도 닫지 않는다.
이 경로를 `test/autopilot/spent-policy-recovery.test.mjs` 에 고정했다. 그 테스트는
하네스가 직접 쓴 자동조종 상태와 원장 바이트를 쌍으로 되돌려 같은 형태를 만든다.
손으로 계산한 값은 없다.

### 게이트

`npm run release:verify` 23/23 통과. `test:team-dag` 의 skip 1건은 WARNING 으로
드러난다 — 비공개 OMO 런타임이 이 머신에 없기 때문이며, 숨기지 않는 것이 규칙이다.

`docs/reports/v1-security-inventory.json` 은 `--record` 로 다시 기록했다. 바뀐 값은
`criticalFiles.autopilotRuntime` 다이제스트 하나뿐이고, `src/core/autopilot.mjs` 를
고쳤으니 의도된 변경이다.

### 정직하게 남길 것

- lock 프리플라이트가 AC-11382~85 는 이미 베이스라인에서 통과한다고 경고했다. 이 리포는
  구현을 마친 뒤 잠그는 순서로 자신을 도그푸딩하므로 구조적으로 그렇다. 경고가 옳다.
- 이 릴리스는 원래 v1.13.8 태그를 달고 PR #16 까지 열린 채 **닫히지 않은 상태**였다.
  종료 사슬에서 `node $H close --json | grep -o … | head -1` 를 썼고 파이프라인의 종료
  코드는 `head` 의 것이라 항상 0 이었다. `verify` 가 TRIAGE 를 냈는데도 `&&` 사슬이
  계속 돌아 영수증 없는 태그와 거짓 "close" 커밋이 원격까지 나갔다. 그 태그와 커밋은
  제거했다. 이후 모든 게이트는 파이프 없이 종료 코드를 직접 읽는다.
- v1.12.0 단계에서 "release:verify 가 usability 스위트를 돌리지 않는다" 는 보고를 이미
  받았고 고치지 않았다. 다섯 릴리스를 그대로 통과시킨 직접 원인이다.
