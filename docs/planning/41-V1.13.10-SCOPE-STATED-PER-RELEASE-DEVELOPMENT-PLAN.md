# Shipping Harness v1.13.10 — 릴리스마다 범위를 다시 말한다

## 1. 문제

### 1.1 준비된 릴리스가 남의 범위를 들고 태어난다

`prepareNextRelease` 는 다음 계약을 `{...current, release, goal}` 로 만든다. `plan` 만
지우고 **`scope` 는 통째로 물려준다.** 그래서 모든 DRAFT 가 직전 릴리스의 범위 문장과
경로 허용목록을 그대로 들고 시작한다.

이 리포는 v1.8.2 의 범위를 v1.13.8 까지 끌고 왔다. 증상이 없었던 이유는 구현이 잠금보다
앞서기 때문이다. 범위 검사는 잠금 기준선 이후의 변경만 본다. v1.13.8 에서 처음으로 잠금
**이후** 작업이 생기자 범위 블로커 7개로 터졌고 정정(AMEND-1.13.8-001)이 필요했다.

### 1.2 비우는 것만으로는 더 나빠진다

`analyzeScope` 는 `policy.include.length > 0` 일 때만 허용목록을 적용한다. 즉 **빈
허용목록은 "아무것도 허용 안 함" 이 아니라 "제한 없음" 이다.** 준비 단계에서 그냥 비우면
조용히 낡은 범위가 조용히 없는 범위로 바뀔 뿐이다.

### 1.3 스모크 둘이 아직 게이트 밖이다

v1.13.9 에서 `SKIPPED:` 관례를 만든 이유가 바로 돌 수 없는 스텝을 게이트에 넣기
위해서였다. 그런데 정작 그 관례가 필요했던 `smoke:remote` 와 `smoke:stable` 은 여전히
`UNGATED_SCRIPTS` 에 남아 있었다. 내가 만든 수단을 그 수단이 겨냥한 사례에 적용하지
않았다.

## 2. 목표

릴리스는 자기 범위를 스스로 말한다. 말하지 않으면 잠기지 않는다.

## 3. 고정 원칙

- 빈 허용목록은 좁은 범위가 아니다. 제한이 없는 것이다.
- 구조적 거부 목록(`.git/**`, `node_modules/**`, `.shipping/contract.yaml` 등)은
  릴리스별 정보가 아니므로 유지한다.
- 돌 수 없는 스텝은 제외가 아니라 skip 이다.

## 4. 구현 단계

### Phase A — 범위 초기화

- `unstatedScope()` 가 `scope.include`, `scope.exclude`, `scope.paths.include` 를 비우고
  `paths.exclude` 를 남긴다. `prepareNextRelease` 가 이것을 쓴다.

### Phase B — 미기재 잠금 거부

- `lockContract` 가 `scope.paths.include` 또는 `scope.include` 가 비면
  `ERR_SCOPE_UNSTATED` 로 거부한다. 메시지가 빈 목록이 제한 없음을 뜻한다는 것을 직접
  말한다. Phase A 를 안전하게 만드는 것이 이 검사다.
- MCP 승인 경로는 항상 허용목록을 채우므로 영향이 없음을 먼저 측정해 확인했다.

### Phase C — 스모크 둘 게이트 편입

- `privateOmoRuntimeAvailability` 를 `test/omo/helpers.mjs` 에서
  `packages/internal-omo-bridge/availability.mjs` 로 옮긴다. 테스트 안에 있어서 스크립트가
  같은 질문을 할 수 없었던 것이 두 스모크가 제외됐던 이유다. 헬퍼는 재수출한다.
- `skipWithoutPrivateOmoRuntime()` 이 `SKIPPED:` 한 줄을 내고 멈춤 여부를 알린다.
- 두 스크립트에 가드를 넣고 `STEPS` 로 옮긴다. 23 → 25 스텝.

## 5. 완료조건
