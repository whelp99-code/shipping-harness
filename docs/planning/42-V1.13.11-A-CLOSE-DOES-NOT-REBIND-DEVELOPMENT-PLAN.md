# Shipping Harness v1.13.11 — close 는 바인딩을 다시 쓰지 않는다

## 1. 문제

v1.13.8 수정본으로 1.0.3 교착을 푼 세션이 관찰 하나를 보고했다. 닫힌 1.0.2 트레인의
`releaseTrainHash` 와 `baselineSha` 가 바인딩에 그대로 남아 있다는 것이었다.

측정해 보니 그보다 한 겹 더 있었다. `completeManualAutopilotClosure` 가 닫히는 릴리스를
바인딩의 `currentRelease` 에 **덮어쓴다.**

정상 경로에서는 무해하다. 정책이 그 릴리스를 승인했으니 두 값이 이미 같다. 문제는
정책이 소진된 경우다. 상대 세션의 상태를 그대로 재현해 측정한 결과다.

```
close 직전 : spent=true  enabled=false SUPERSEDED_BY_CLOSED_RELEASE currentRelease=1.0.2
close 직후 : spent=false enabled=true  BINDING_MISMATCH             currentRelease=1.0.3
```

닫기 한 번으로 판정이 뒤집힌다. 소진 판정은 "묶인 릴리스 ≠ 현재 릴리스" 를 보는데,
close 가 묶인 릴리스를 현재 릴리스로 바꿔 버리니 같아진다. 그런데
`releaseTrainHash` 와 `baselineSha` 는 1.0.2 것 그대로다. **존재한 적 없는 바인딩이
만들어진다.**

결과는 1.0.2 를 승인했을 뿐 아무 권한도 없는 죽은 정책이 1.0.3 에 대해
`enabled: true` 를 보고하는 것이다.

동작 자체는 여전히 닫힌 채로 실패한다. 여섯 값 비교가 해시 불일치로
`BINDING_MISMATCH` 를 내므로 자동조종 권한을 쓰려는 어떤 경로도 거부된다. 다음 릴리스를
준비하면 다시 소진으로 판정된다. 하지만 **표면이 거짓말한다.** AGENTS.md 가 금지하는
false user state 이고, v1.13.5 에서 `plan status` 를 고친 것과 같은 종류다.

다음 단계로 1.1.0 을 자동조종으로 시작하려는 세션이 `autopilot.enabled: true` 를 읽으면
없는 정책이 살아 있다고 믿게 된다.

## 2. 목표

정책이 어느 릴리스에 묶였는지는 활성화가 정한다. close 는 릴리스가 닫혔다는 사실만
기록한다.

## 3. 고정 원칙

- 절반만 갱신된 상태를 만들지 않는다. 바인딩은 통째로 참이거나 통째로 옛것이다.
- 동작이 닫힌 채로 실패한다는 것은 표면이 거짓이어도 된다는 뜻이 아니다.
- 멱등성 키는 의미가 맞는 값이어야 한다. 소진된 바인딩의 `currentRelease` 는 키가 아니다.

## 4. 구현 단계

### Phase A — 덮어쓰기 제거

- `completeManualAutopilotClosure` 의 `currentRelease: closeResult.receipt.release` 를
  뺀다. 정상 경로에서는 이미 같은 값이라 변화가 없다.

### Phase B — 멱등성 키 교체

- 중복 판정이 `current.currentRelease === receipt.release` 만 보면 소진된 경우를 놓친다.
  원장의 마지막 이벤트가 이 릴리스의 `human.release-closed` 인지도 함께 본다.

### Phase C — 테스트

- 상대 세션의 상태를 그대로 만든다. 자동조종 상태·원장·정책 세 파일을 하네스가 직접 쓴
  바이트로 짝지어 복원한다. 정책까지 복원해야 한다. 앞선 재현에서 정책만 1.0.3 의
  MANUAL 로 바뀌어 있어 `enabled` 가 우연히 false 로 나왔고, 결함을 놓칠 뻔했다.
- close 이후에도 `currentRelease`, `spent`, `enabled`, `bindingReason`, 두 해시가 모두
  1.0.2 의 것으로 남는지 본다.
