# Shipping Harness v1.13.12 — 쓰기 측 수정은 디스크를 치료하지 않는다

## 1. 문제

v1.13.11 을 내보내며 상대 세션에 "재기동하면 spent=true, enabled=false,
currentRelease=1.0.2 로 돌아옵니다" 라고 알렸다. **검증하지 않은 주장이었고 틀렸다.**

v1.13.11 은 close 가 앞으로 도장을 찍지 못하게 막는다. 이미 찍힌 도장은 지우지 않는다.
상대 세션의 close 는 v1.13.10 에서 이미 실행됐고 `currentRelease: 1.0.3` 이 디스크에
기록된 뒤였다. 재기동해도 그대로다.

```
v1.13.11 재기동 후: enabled=true spent=false BINDING_MISMATCH currentRelease=1.0.3
```

그리고 v1.13.8 의 판정 규칙 때문에 이 상태는 **영원히 회복되지 않는다.** 소진 판정이
"묶인 릴리스 ≠ 현재 릴리스" 를 요구하는데, 도장 때문에 둘이 같아졌기 때문이다. 죽은
정책이 계속 살아 있다고 읽히고, 1.1.0 을 자동조종으로 승인하려 하면
`ERR_AUTOPILOT_ACTIVE` 로 거부된다. v1.13.8 의 "잠금 전 거부" 덕분에 교착까지 가지는
않지만 자동조종 경로가 막힌다.

이 창으로 close 한 모든 저장소가 같은 상태다.

## 2. 목표

이미 쓰인 상태가 읽히는 순간 스스로 회복되게 한다. 디스크를 고쳐 쓰지 않는다.

## 3. 고정 원칙

- `.shipping/` 를 읽으면서 고쳐 쓰지 않는다. 판정이 상태를 해석할 뿐이다.
- 종료 영수증이 없는 바인딩은 여전히 닫힌 채로 실패한다. 이것이 변조를 막는 가드다.
- 넓히는 것이 자동화가 건드릴 수 있는 범위를 넓히면 안 된다.

## 4. 구현 단계

### Phase A — 판정 규칙

`isSpentAutopilotBinding` 에서 "묶인 릴리스 ≠ 현재 릴리스" 조건을 뺀다. 종료 영수증
존재 여부만 본다.

안전한 이유는 이렇다. 넓어지는 것은 "종료 영수증이 있는 릴리스에 묶인 바인딩" 뿐이다.
종료 영수증이 있다는 것은 그 릴리스가 닫혔다는 뜻이고, 닫힌 릴리스에는 애초에 아무것도
실행할 수 없다. 영수증이 없는 경우는 그대로 소진이 아니며 닫힌 채로 실패한다.

`spent` 를 소비하는 곳은 두 군데뿐임을 먼저 확인했다. `activateAutopilot` 의 교체 허용과
`assertAutopilotBindingCurrent` 의 보고다. 열차 전진(`rotateAutopilotPolicy`)은 `spent`
를 보지 않고 `phase` 와 권한만 본다. 따라서 다중 릴리스 열차 흐름은 영향이 없다.

### Phase B — 테스트

- `test/autopilot/spent-policy-recovery.test.mjs`: 옛 빌드가 찍은 도장을 재현하고 읽기
  만으로 회복되는지 본다. 상태 해시는 로더가 검증하는 그 함수로 계산해 production 검증
  경로를 실제로 통과시킨다.
- `test/adversarial/autopilot-spent-policy.test.mjs`: 옛 규칙을 단언하던 테스트를 새
  규칙으로 바꾸고, 영수증 없는 경우가 여전히 닫힌 채로 실패하는지 별도로 고정한다.

## 5. 완료조건

- AC-113121 옛 빌드가 남긴 바인딩의 읽기 시점 회복과 변조 가드 유지.
- AC-113122 `npm run release:verify` 전체 통과.
- AC-113123 문서 감사와 공백 검사.

## 6. 실행 기록

### Phase A

조건 하나를 뺐다. `spent` 소비처가 둘뿐이고 열차 전진이 그것을 보지 않는다는 것을 먼저
확인했기 때문에 넓혀도 안전하다고 판단할 수 있었다. 확인하지 않았다면 다중 릴리스 열차를
깨뜨릴 수 있는 변경이었다.

### 재현 — 이 빌드가 만든 상태로는 증명할 수 없다

핵심은 **옛 빌드가 남긴 상태** 여야 한다는 점이다. 이 빌드는 그런 상태를 더는 만들지
못한다. v1.13.10 태그로 워크트리를 만들어 실제로 생성했다.

```
v1.13.10 이 디스크에 남긴 상태: currentRelease=1.0.3 phase=RELEASE_CLOSED
                                profile=LOCAL_REVERSIBLE enabled=true
v1.13.11 로 읽은 결과         : enabled=true spent=false BINDING_MISMATCH
v1.13.12 로 읽은 결과         : enabled=false spent=true SUPERSEDED_BY_CLOSED_RELEASE
```

그 상태에서 다음 릴리스를 자동조종으로 승인해 끝까지 밀었다.

```
1.1.0 제안         READY_FOR_APPROVAL
1.1.0 자동조종 승인 LOCKED
새 바인딩          currentRelease=1.1.0, trainHash·baselineSha 모두 교체
원장               6개, 단절 0
승인 후 상태       enabled=true spent=false CURRENT
```

v1.13.8, v1.13.11 에 이어 세 번째로 같은 방법이 결함을 잡았다. 옛 태그로 상태를 만들고
새 빌드로 읽는다.

### Phase B

`test/adversarial/autopilot-spent-policy.test.mjs` 의 "현재 릴리스를 가리키는 바인딩은
소진이 아니다" 를 뒤집었다. v1.13.8 당시에는 맞는 판단이었다. close 가 도장을 찍고
있다는 사실을 몰랐기 때문이다. 영수증 없는 경우가 여전히 닫힌 채로 실패하는지는 별도
테스트로 떼어 고정했다.

### 정직하게 남길 것

v1.13.11 을 내보내며 상대 세션에 "재기동하면 돌아옵니다" 라고 알렸다. 측정하지 않은
주장이었고 틀렸다. 상대 세션이 실측으로 반증해 주지 않았다면 그대로 남았을 것이다.
수정을 내보낼 때 그 수정이 **이미 존재하는 상태** 에 무엇을 하는지는 새 상태에 무엇을
하는지와 다른 질문이며, 따로 측정해야 한다.
