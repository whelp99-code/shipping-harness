# Shipping Harness v1.13.13 — 사람이 읽는 것과 잠기는 것을 같게

## 1. 문제

운영 세션이 하루에 세 가지를 보고했다. 모두 같은 모양이다. **사람이 읽는 것과 실제로
잠기는 것이 다르다.**

### 1.1 요청한 계획이 조용히 버려진다

계획 단계의 `size` 에 `MINOR` 를 넣었더니 파일 전체가 `ERR_PLAN_INVALID` 로 거부되고
제안이 조용히 PATCH 로 격하됐다. 범위는 계획이 아니라 일반 템플릿에서 왔는데 결과는
`READY_FOR_APPROVAL` 이다. 설명은 `diagnostics` 에만 있었다.

측정해 보니 더 나쁜 경우가 있었다. **`stageId` 나 `planPath` 를 명시적으로 넘겨도
마찬가지로 조용히 버려진다.** 호출자는 그 단계에서 나온 범위를 달라고 했는데 다른 것을
받고, 그것이 승인 가능한 상태로 서 있다.

### 1.2 승인 화면이 잠길 범위를 보여주지 않는다

계획 단계에 제대로 묶인 제안인데도 `approvalBrief.included` 와
`oneScreenApproval.included` 가 고정 문구 세 줄을 돌려준다. 계약의 `scope` 에는 계획이
적은 실제 범위가 들어 있다.

원인은 순서였다.

```js
const approvalBrief = buildApprovalBrief(decision);                       // 먼저
const contract = bindPlanStageContract(compileDecisionContract(...), ctx); // 나중
```

승인 브리프가 계획 결속 **이전** 의 decision 으로 만들어진다. 뒤에서 SCOPE_DRIFT_ZERO
를 판정할 기준은 계약인데 사람은 그것을 본 적이 없다. 이 화면은 하네스가 사람을 부르는
유일한 지점이라 가장 심각하다.

### 1.3 초심자 투영이 통째로 사라진다

같은 응답에서 `plainBrief` 가 `PLAIN_BRIEF_QUALITY_FAILED` 로 죽는다.
`boundedOutput: false`, 9078 바이트로 8192 한도 초과다.

각 섹션에는 항목 상한이 있는데 **`factGraph` 에는 개수 상한도 바이트 상한도 없었다.**
한국어 범위 문장이 길어지면 사실 그래프가 3003 바이트까지 자란다. 이 리포 규칙은 모든
표면에 예산을 둔다는 것인데 여기가 비어 있었다.

보고자는 고정 문구 반복이 원인일 것으로 추정했지만 실측해 보니 아니었다. 1.2 를 고쳐도
크기는 내려가지 않았다.

## 2. 목표

승인 화면은 잠길 계약을 보여준다. 요청한 것을 줄 수 없으면 다른 것을 주지 않고 거부한다.
가장 덜 기술적인 독자를 위한 투영이 길이 때문에 사라지지 않는다.

## 3. 고정 원칙

- 요청을 못 들어줄 때 비슷한 것으로 대체하지 않는다. 거부하고 이유를 말한다.
- 격하는 허용하되 조용해서는 안 된다.
- 무엇을 잘랐으면 몇 개 잘랐는지 말한다.

## 4. 구현 단계

### Phase A — 못 들어줄 계획 요청은 거부

`planPath` 나 `stageId` 가 명시된 채 계획을 읽지 못하면 `ERR_PLAN_REQUEST_UNMET` 로
거부하고 "아무것도 제안되지 않았다" 를 알린다. 아무도 요청하지 않은 계획이 깨진 경우는
계속 격하한다 — 계획 없이 제안하는 것은 정당하다.

### Phase B — 격하를 사람이 읽는 면에 올린다

계획이 로드에 실패하면 `shippingPlan` 투영 자체가 없어 경고를 걸 곳이 없었다. 브리프가
제안의 `diagnostics` 를 직접 읽어 `PLAN_FILE_INVALID` 항목을 만든다.

### Phase C — 승인 화면은 계약을 보여준다

계약을 먼저 컴파일하고 `buildApprovalBrief(decision, contract)` 에 넘긴다. 계약이 알려져
있으면 그 `scope` 가 이긴다. `planStageId` 를 브리프에 담고 텍스트에 `Plan stage: S-01`
로 표기한다. 단계가 자기 범위를 적지 않았으면 파생 범위로 되돌아간다 — 빈 화면이 되면
안 된다.

### Phase D — 브리프는 사라지는 대신 맞춘다

예산을 넘으면 `buildBriefFactGraph` 가 우선순위 순으로 낸 사실을 뒤에서부터 덜어내고
`factsTruncated` 로 몇 개인지 기록한다. `CANONICAL_STATE` 와 `PRIMARY_NEXT_ACTION` 은
절대 자르지 않는다.
