# Shipping Harness v1.13.14 — 어느 빌드가 답하고 있는가

## 1. 문제

운영 세션이 v1.13.13 의 승인 화면 수정을 확인하려고 rescan 했는데 화면이 그대로였다.
`changed: false`, `planStageId` 없음, 텍스트에 `Plan stage:` 없음, 그리고 `plainBrief`
가 **정확히 같은 숫자로** 다시 죽었다 — structuredBytes 9339, renderedBytes 2119.

그 세션이 원인을 스스로 찾아냈다. 붙어 있던 MCP 서버 프로세스가 수정보다 먼저 떠서
모듈을 그때 코드로 이미 읽어 들인 상태였다. STDIO 서버는 모듈을 한 번 읽고 계속 그것을
제공한다. 설치본 심볼릭 링크를 갈아도 살아 있는 프로세스는 바뀌지 않는다. rescan 은
서버 안에서 도는 호출이라 재기동 없이는 새 코드에 닿을 수 없다.

직접 세어 보니 이 저장소를 상대로 **여섯 개** 의 서버가 돌고 있었고 그중 셋은 9월
16~17일에 뜬 것이었다. 사흘 넘게 옛 코드를 제공해 온 것이다.

### 1.1 알아챌 방법이 응답 어디에도 없다

`initialize` 응답에는 `MCP_SERVER_INFO` 로 버전이 실린다. 그러나 사흘 전에 붙은 세션이
그것을 다시 볼 이유가 없고, 이후 어떤 응답도 어느 빌드가 답하는지 말하지 않는다.

그 세션은 결국 설치본 소스에서 수정을 확인하고, 프로세스 시작 시각을 읽고, 심볼릭
링크와 살아 있는 프로세스의 관계를 추론해서 답에 도달했다. **누구도 그런 진단을 해야
해서는 안 된다.** 게다가 "고쳤다" 는 보고가 거짓처럼 보이게 만든다.

## 2. 목표

어떤 세션이든 응답 하나로 어느 빌드가 답하고 있는지 알 수 있게 한다.

## 3. 고정 원칙

- 프로세스를 죽이거나 재연결하지 않는다. 같은 바이너리로 뜬 서버가 여럿이고 다른 세션이
  붙어 있을 수 있다. 사용자 결정이다.
- 도구 정의와 동결 스키마는 건드리지 않는다.

## 4. 구현 단계

`shipping_status` 응답에 `harnessVersion` 을 담는다. 값은 `src/version.mjs` 의
`VERSION`, 즉 **이 프로세스가 읽어 들인** 버전이다. 디스크에 설치된 것이 아니다.

`shipping-harness version` 은 매번 새 프로세스라 항상 설치본을 보고한다. 둘을 비교하면
서버가 낡았는지 즉시 드러난다.

`state.schema.json` 은 `.shipping/state.json` 을 고정하지 응답을 고정하지 않으므로 표면
동결과 무관하다. 먼저 확인했다.

## 5. 완료조건

- AC-113141 모든 상태 응답이 답하는 빌드를 보고하고, `initialize` 가 알리는 값과 같으며,
  저장소 초기화 여부와 무관하다.
- AC-113142 `npm run release:verify` 전체 통과.
- AC-113143 문서 감사와 공백 검사.
