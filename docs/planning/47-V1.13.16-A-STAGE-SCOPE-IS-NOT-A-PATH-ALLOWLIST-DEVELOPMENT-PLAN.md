# Shipping Harness v1.13.16 — 단계 범위는 경로 허용목록이 아니다

## 1. 문제

운영 세션이 v1.13.15 의 측정 결과("확장자 있는 파일명은 목표 문장에서 인식된다")를 자기
상황에 적용하려다 틀렸고, 그 과정에서 하나를 더 찾았다.

그쪽 계약의 범위 밖 경로가 정확히 하나였다.

```
scopeWarning.outside = ["uv.lock"]
```

그래서 계획 단계 S-02B 의 `scopeInclude` 에 `uv.lock` 을 적고 계획을 revision 9 로 올린
뒤 rescan 했다. 결과는 이렇다.

```
contract.scope.include       ← 새 문장이 올라옴
contract.scope.paths.include ← 한 글자도 안 변함
```

원인은 `applyPlanStageToContract` 다.

```js
scope: { ...contract.scope, include: …, exclude: … }
```

`paths` 는 펼쳐진 채 그대로 통과한다. **계획 단계가 바꾸는 것은 산문 범위뿐이고 경로
허용목록은 구조 탐지에서 온 값이 끝까지 유지된다.**

### 1.1 이 설계는 옳다

계획 파일이 경로 허용목록을 넓힐 수 있게 되면 계획 파일이 가져서는 안 될 권한을 갖는다.
보고자도 같은 판단이었고 경로 추출을 계획 단계에 걸어 달라고 요청하지 않았다.

### 1.2 문제는 아무도 말해 주지 않는다는 것

보고자는 **소스를 읽고서야** 알았다. 그 전까지는 계약의 산문 범위에 문장이 올라온 것을
보고 반영됐다고 판단할 수 있었다. 확인하지 않았다면 나중에 verify 에서 범위 이탈로
알게 됐을 것이다.

v1.13.15 에서 `GOAL_PATH_REFUSED` 에 "`scope.paths.include` 에 안 들어가서 그 아래
변경이 scope drift 로 잡힌다" 를 붙인 것과 정확히 같은 자리다.

## 2. 목표

단계 범위가 경로를 지목했는데 허용목록이 그것을 덮지 않으면 말한다. 넓히지는 않는다.

## 3. 고정 원칙

- 계획 파일은 경로 허용목록을 넓히지 않는다. 이 릴리스는 그 경계를 바꾸지 않는다.
- 이것은 진단이지 게이트가 아니다. 제안을 막지 않는다.
- 산문 한 줄마다 후보가 쏟아지면 안 된다. 보수적 추출기가 받아들인 토큰만 센다.

## 4. 구현 단계

`stageScopePathDiagnostics(stage, scopePaths)` 를 `plan-proposal.mjs` 에 더한다.
`scopeInclude` 와 `scopeExclude` 의 각 문장에 `extractGoalPaths` 를 걸고, 받아들여진
토큰 중 `matchesAnyGlob` 으로 허용목록에 덮이지 않는 것만 보고한다. 경로당 한 번이다.

`bindPlanStageContract` 가 계약을 만든 **직후** 에 호출한다. 그 시점이 단계 범위와 게이트가
실제로 측정할 허용목록을 함께 볼 수 있는 첫 지점이다.

문구는 세 가지를 말한다 — 단계 범위는 허용목록을 넓히지 않는다는 것, 거기 변경은 범위
이탈로 잡힌다는 것, 그리고 넣으려면 계약의 `scope.paths.include` 에 직접 적거나 목표
문장에 쓰라는 것.

## 5. 완료조건

- AC-113161 덮이지 않은 경로 보고, 덮인 경로 침묵(글롭 포함), 산문·분수·URL 무반응,
  경로당 한 번.
- AC-113162 `npm run release:verify` 전체 통과.
- AC-113163 문서 감사와 공백 검사.

## 6. 실행 기록

`stageScopePathDiagnostics` 는 순수 함수라 단위 테스트로 직접 고정했다. 덮인 경로, 글롭에
덮인 경로, 정확히 일치하는 항목, 분수(`3/4`), URL, 빈 단계, 빈 허용목록까지 본다.

`bindPlanStageContract` 가 `tiers.diagnostics` 에 결과를 이어 붙인다. 계약이 만들어진
직후가 단계 범위와 실제 허용목록을 함께 볼 수 있는 첫 지점이기 때문이다. 그 앞
(`compilePlanTiers`)에는 계약이 아직 없고, 그 뒤에는 진단이 이미 조립된 뒤다.

빈 허용목록은 여기서 아무것도 덮지 않는 것으로 취급한다. `analyzeScope` 에서 빈 목록이
"제한 없음" 이 되는 것과 반대 방향인데, 그쪽은 게이트 판정이고 이쪽은 "이 경로가 목록에
있느냐" 는 질문이라 다르다. v1.13.10 이 빈 허용목록으로는 잠글 수 없게 만들었으므로
실제 잠긴 계약에서는 생기지 않는 경우다. 테스트에 그 이유를 적어 두었다.

### 이 릴리스가 온 경로

보고자가 v1.13.15 의 측정을 자기 상황에 적용했고, 그 적용이 틀렸다. 틀린 이유를 찾으려고
소스를 읽다가 이것을 발견했다. 그리고 **경로 추출을 계획 단계에 걸어 달라고 요청하지
않았다** — 그러면 계획 파일이 더 큰 권한을 갖게 된다는 것을 스스로 짚었다. 요청은 침묵을
없애 달라는 것이었고 그것이 정확히 맞는 요청이었다.

보고자는 틀린 주장을 담은 커밋을 이미 푸시했다는 것도 밝히고 정정 커밋을 따로 냈다.
