# Shipping Harness v1.13.19 — v1.13.18 기록 정정

## 1. 문제

v1.13.18 의 CHANGELOG 항목이 이렇게 단정한다.

> A reporting session running 569s against a 600s budget, with a suite that had just grown
> by 186 tests, **worked out for itself that verify was about to fail for the timeout**
> rather than for the work.

**verify 는 실패할 상황이 아니었다.** 보고자가 실제로 재서 알려 왔다.

```
1971 passed, 3 skipped in 386.01s (0:06:26)
386 / 600 = 64%
```

64% 는 v1.13.18 의 80% 임계 아래다. 경고는 뜨지 않는 것이 맞고, timeoutSeconds 를 올릴
필요도 명령을 쪼갤 필요도 없었다.

### 1.1 569 초는 다른 나무의 숫자였다

보고자의 정정에 따르면 569 초는 현재 트리에서 잰 것이 아니라 소스 HEAD `d4cbdda` 기준의
볼트 기록이었다. 다른 커밋, 다른 시점, 부하 상태 미상이다. 그것을 현재 트리의 1,971 개에
선형 외삽했으니 비교 대상이 처음부터 어긋나 있었다. 실제로 테스트가 10% 늘었는데 시간은
32% 줄었다 — 개수가 지배 변수가 아니다.

### 1.2 기능은 그대로 옳다

v1.13.18 이 고친 것은 "사전검사가 실행 시간을 재고 예산도 알면서 이미 넘긴 경우에만
말한다" 는 공백이다. 그 공백은 보고자의 특정 기준이 예산에 임박했는지와 무관하게 실재한다.
보고자도 같은 판단이다.

> 하네스가 실측값을 행에 담게 된 것 자체는 여전히 옳습니다 — 제가 오늘 한 실수가 정확히
> "그 환경의 실측값 대신 기록된 숫자를 썼다" 인데, lock 이 그 값을 직접 말해 주면 저
> 같은 사람이 외삽할 이유가 없어집니다.

되돌릴 코드는 없다. 386/600 에서 침묵하는 것을 확인했다.

### 1.3 그러나 기록은 틀린 채로 남아 있다

이 리포의 주장은 증거로 증명된 완료다. 닫힌 릴리스의 기록이 남의 저장소에 대해 사실이
아닌 것을 사실로 단정하고 있으면 그 주장이 약해진다.

## 2. 목표

기록을 다시 쓰지 않고 정정한다.

## 3. 고정 원칙

- 닫힌 릴리스의 계획 문서는 건드리지 않는다. 그때 쓴 것을 지우면 역사 위조다.
- 정정은 더하는 것이지 바꾸는 것이 아니다. 보고자가 자기 커밋 메시지를 정정 커밋으로
  처리한 것과 같은 방식이다.
- 코드는 바꾸지 않는다. 고칠 것이 없다.

## 4. 구현 단계

CHANGELOG 의 1.13.19 항목에 정정을 적는다. 1.13.18 항목이 무엇을 주장했는지, 실측이
무엇인지, 그래서 기능 판단은 왜 그대로인지를 함께 쓴다. 1.13.18 항목 자체는 그대로 둔다.

## 5. 완료조건

- AC-113191 문서 감사와 공백 검사.
- AC-113192 `npm run release:verify` 전체 통과. (동작 변경이 없음을 증명한다)

## 6. 실행 기록

소스 변경 없음. CHANGELOG 항목 하나와 이 문서.

`release:verify` 25/25 를 수용기준에 넣은 것은 동작이 바뀌지 않았음을 증명하기 위해서다.
문서만 고친 릴리스라도 그것이 사실인지는 기계가 말해야 한다.

### 되돌릴 것이 없음을 먼저 쟀다

```
386960ms / 600s → 경고 0건 (침묵이 맞음)
임계까지 여유 93초
```

보고자의 실측값을 그대로 넣어 v1.13.18 이 침묵하는지 확인했다. 침묵한다. 기능은 옳고
정정할 것은 내가 쓴 문장뿐이다.

### 왜 고쳐 쓰지 않고 더했는가

v1.13.18 의 계획 문서와 CHANGELOG 항목은 그대로 두었다. 그때 내가 그렇게 썼다는 것이
사실이기 때문이다. 지우면 두 번째 거짓이 된다. 보고자가 자기 커밋 메시지의 틀린 주장을
정정 커밋(28a69d5)으로 처리한 것과 같은 방식이고, 내가 오늘 영수증 없는 태그를 지운 뒤
그 사실을 계획 문서에 남긴 것과도 같다.

다만 계획 문서 49 는 보고자의 메시지를 인용한 부분이 있는데, 그것은 정확한 인용이므로
손대지 않았다. 사실로 단정한 것은 그 주변의 내 문장이고, 정정 대상은 그쪽이다.

### 오늘 세 번째 같은 실수

보고자가 짚었듯 이것은 "기록된 숫자를 현재 상태의 측정 대신 쓴 것" 이다. 나도 오늘 같은
실수를 했다 — v1.13.11 을 내보내며 "재기동하면 돌아옵니다" 라고 측정하지 않은 주장을
보냈고, v1.13.12 가 그것을 고쳤다. 그때 배운 것을 남의 숫자를 받아 적을 때는 적용하지
않았다.
